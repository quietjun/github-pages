GCP 3-Tier 구축 가이드 (무료 플랜 실무형)

네트워크 망 분리 + Multi-AZ 구조를 100% 무료 리소스(H2, Nginx)로 시뮬레이션 해보기

🏗️ GCP Free Tier Architecture (실무 시뮬레이션)

💡 실무 아키텍처와 무료 시뮬레이션의 차이점
이 가이드는 망 분리(VPC/Subnet), 다중 가용영역(Multi-AZ) 같은 실무형 네트워크 뼈대는 그대로 가져가되, 비용이 발생하는 Cloud SQL이나 L7 로드밸런서, Cloud NAT 대신 Nginx, H2 DB, 임시 외부 IP 등 100% 무료 우회 기술을 사용하여 요금 폭탄을 방지합니다. (참고: GCP 평생 무료 `e2-micro`는 리전당 1대이므로, 3대 사용 시 월 약 $10 정도의 요금이 발생할 수 있으나, 가입 시 제공되는 $300 크레딧에서 차감됩니다.)
1
실무형 망 분리 (VPC & Subnet)

🏗️ Phase 1 진행 상황: 격리된 VPC 망 및 서브넷 구축

🎯 이 단계의 목표 모든 인프라의 기반이 되는 격리된 네트워크 망(Custom VPC)을 구축한다. Nginx용 망과 백엔드(Spring Boot)용 망을 논리적으로 분리한다.

🌐 VPC (Virtual Private Cloud) 란?
클라우드상에 구축하는 나만의 격리된 가상 네트워크 공간이다. 가상 서버(VM)들이 공용 인터넷에 무방비하게 노출되지 않도록 사설 IP 대역을 직접 정의한다. 외부 침입을 1차적으로 차단하는 가장 기본적인 보안 성벽 역할을 한다.

🕸️ 서브넷 (Subnet) 이란?
VPC라는 큰 성벽 내부를 여러 개의 구역(하위 네트워크)으로 다시 쪼갠 것이다.
  • 왜 쪼개서 사용하나?: 성문 입구(Public Subnet, 웹서버 망)와 가장 안전한 안방(Private Subnet, WAS/DB 망)을 구분하기 위함이다. 외부 침입자가 우연히 성문(Nginx)을 뚫고 들어오더라도, 중요 데이터나 비즈니스 로직(WAS) 서버가 있는 안방까지 다이렉트로 침투할 수 없게 차단벽을 치는 망 분리(Network Segmentation)의 핵심 수단이다.
💡 GCP 콘솔 메뉴 찾기 팁
GCP 콘솔 왼쪽 상단의 탐색 메뉴(☰ 삼선 아이콘)를 누르고 스크롤을 내려 '네트워크' 섹션의 'VPC 네트워크'를 선택하거나, 콘솔 상단 검색창에 'VPC 네트워크'를 검색하면 빠르게 이동할 수 있습니다.

Step 1-0: GCP 프로젝트 생성 및 선택

  • GCP 리소스의 기본 단위 '프로젝트'
    GCP의 모든 리소스(VPC, VM 등)는 반드시 하나의 프로젝트 내부에서 생성됩니다. 실습 중 다른 리소스와 섞이는 것을 방지하고 나중에 한 번에 삭제하기 쉽도록, 전용 실습 프로젝트를 만드는 것이 좋습니다.
  • 프로젝트 준비 단계
    - GCP 콘솔 상단 왼쪽 로고 옆의 프로젝트 선택 드롭다운을 클릭합니다.
    - 새 프로젝트(New Project)를 클릭하고 프로젝트 이름(예: free-3tier-demo)을 입력한 뒤 생성합니다.
    - 생성 완료 알림이 뜨면 상단 드롭다운에서 방금 만든 프로젝트가 활성화(선택)된 상태인지 반드시 확인하세요.

Step 1-1: Custom VPC 생성

  • VPC 네트워크 → VPC 네트워크 생성
    - 이름: `free-prd-vpc`
    - 서브넷 생성 모드: 맞춤설정(Custom)
  • 계층별 서브넷(Subnet) 구성
    보안을 위해 역할을 분리하여 2개의 서브넷을 생성합니다. (리전은 모두 무료 티어인 us-central1 사용)
    💡 IP 범위(CIDR) 표기법 쉽게 읽기
    GCP에서 네트워크 대역을 설정할 때 사용하는 /16, /24 등의 단위를 CIDR(사이더)라고 한다. IP 주소 뒤에 고정할 비트 수를 지정하는 방식이다.
    - /16 (VPC 전체): 10.250.0.0/16은 10.250.0.0 ~ 10.250.255.255 (약 6만 5천 개 IP) 범위를 의미한다.
    - /24 (서브넷 단위): 10.250.1.0/24는 10.250.1.0 ~ 10.250.1.255 (총 256개 IP) 범위를 의미한다.
    - /32 (단일 IP 장비): 특정 PC나 서버 1대의 고유 IP만 지정할 때 사용한다.
    - 0.0.0.0/0 (인터넷 전체): 고정 비트가 없으므로 전 세계 모든 IP 주소를 뜻한다. (공개 서비스용)
    💡 리전(Region)과 영역(Zone) 쉽게 이해하기
    - 리전 (Region): 데이터 센터들이 위치한 지리적인 도시 단위다. 예: us-central1 (미국 아이오와)
    - 영역 (Zone): 하나의 리전 내부에서 전력과 네트워크가 완전히 독립된 개별 데이터 센터 건물이다. 예: us-central1-a, us-central1-c
    - 이중화 배포의 목적: 지진이나 정전 등으로 특정 건물(Zone A)이 통째로 중단되더라도, 다른 건물(Zone C)에 살아있는 서버가 즉시 트래픽을 넘겨받아 서비스 무중단(고가용성)을 달성하기 위함이다.
    서브넷 이름 IP 범위 용도 (티어)
    free-snet-public-web 10.250.1.0/24 Nginx LB (Frontend)
    free-snet-private-was 10.250.2.0/24 Spring Boot (Backend)
  • VPC 생성 완료
    서브넷 2개를 모두 추가했다면, 화면 맨 아래로 스크롤하여 [만들기(Create)] 버튼을 클릭합니다. 네트워크가 최종 생성되어 GCP 콘솔에 반영되어야만 이후 단계(방화벽 생성 등)에서 우리가 정의한 VPC(free-prd-vpc)를 선택할 수 있게 됩니다.

Step 1-2: IAP 및 기본 방화벽 설정

🔐 IAP (Identity-Aware Proxy) 란?
외부 공인 IP가 전혀 없는 사설망 내부의 VM에 구글 로그인을 통해 안전하게 원격 접속할 수 있게 해주는 구글의 완전 관리형 보안 프록시 서비스다.

💡 왜 사용하나? (개발자의 딜레마와 해결책)
사설망 내부에 있는 free-snet-private-was에 외부에서 접근하려면 원래 외부망인 free-snet-public-web을 거쳐야 한다. 일반 웹 사용자에게는 이것이 정상적인 흐름이지만, 앱을 배포하고 서버를 관리해야 하는 개발자에게는 적당한 구조가 아니다. 원격 제어(SSH 등)를 해야 하는데 일반 사용자가 지나다니는 웹 서버에 관리용 통로를 열어두는 것은 보안상 매우 위험하기 때문이다.

이 문제를 해결하기 위해 기존(예: AWS 등)에는 Bastion Host라고 하는 우회용 가상 서버를 공인 IP 대역에 띄워두고 우회 접속해서 사용해 왔다. 하지만 이는 추가적인 서버 관리 비용이 들고, 해킹 공격을 당할 수 있는 관문이 하나 더 생긴다는 단점이 있다.

반면, GCP의 IAP를 이용하면 이러한 우회용 서버(Bastion Host) 없이 구글 계정 인증 및 권한 확인만 거쳐 안전하게 사설 VM으로 바로 터널링 접속이 가능하다.
  • 필수 방화벽 규칙 생성 (총 3회 반복하여 개별 생성)
    VPC 네트워크 → 방화벽 → 방화벽 규칙 만들기
    이 가이드의 실습 환경을 위해 총 3개의 독립적인 방화벽 규칙을 각각 따로 클릭하여 생성해야 합니다. 아래 표에 나열된 순서대로 각각 폼을 채운 뒤 [만들기]를 눌러 완료해 주세요.
    방화벽 규칙 이름 네트워크 대상 (Targets) 소스 IPv4 범위 허용할 프로토콜/포트 목적 (설명)
    allow-iap-private-ssh free-prd-vpc 네트워크의 모든 인스턴스 35.235.240.0/20
    (구글 IAP 터널링 대역)    		 TCP: 22 외부 IP가 없는 사설 WAS 서버에 개발자가 웹 콘솔을 통해 안전하게 SSH 원격 접속하기 위함 (보안 우회 통로)
    allow-http free-prd-vpc 네트워크의 모든 인스턴스 0.0.0.0/0
    (인터넷 전체 오픈)    		 TCP: 80, 443 일반 웹 사용자들이 Nginx 웹 서버(포트 80, 443)에 브라우저로 접근할 수 있게 개방 (공개용 대문)
    allow-internal-vpc free-prd-vpc 네트워크의 모든 인스턴스 10.250.0.0/16
    (우리 VPC 내부 대역)    		 TCP: 8080 VPC 내부의 Nginx 웹 서버와 백엔드 WAS 서버끼리 내부망 통신을 허용하기 위함 (내부 통로)
2
Nginx 로드밸런서 (비싼 ALB 대체)

🏗️ Phase 2 진행 상황: Nginx 웹 서버 및 로드밸런서 VM 생성

🌐 Nginx(엔진엑스)란 무엇인가요?
Nginx는 기본적으로 고성능 웹 서버(Web Server)로서 사용자의 최초 요청을 받아들이는 웹 계층(Presentation Tier)을 담당한다. 동시에 클라이언트의 요청을 대리하여 백엔드 서버로 중개해 주는 리버스 프록시(Reverse Proxy) 역할을 수행하는 초경량 오픈소스 소프트웨어다.

⚡ 막강한 내장 기능: 로드 밸런서(Load Balancer)
Nginx는 여기에 추가적으로 매우 강력한 로드 밸런서 역할을 수행할 수 있는 기능을 내장하고 있다. 원래 실무에서는 트래픽 분산을 위해 클라우드 서비스사에서 제공하는 고가의 L7 로드 밸런서(GCP HTTP(S) Load Balancing 등)를 사용해야 한다. 하지만 무료 실습 환경 구성을 위해, 무료 VM 위에 Nginx를 직접 설치하여 L7 로드 밸런서(부하 분산기) 역할을 하도록 우회 구현한다.

결과적으로 Nginx는 추후 Vue.js 같은 프론트엔드 정적 파일 서빙(웹 서버)과 백엔드 WAS(Spring Boot)로 요청을 균등하게 토스해 주는 부하 분산(리버스 프록시) 역할을 한 몸으로 동시에 깔끔하게 처리해 준다.

Step 2-1: Nginx 인스턴스 배포

  • Compute Engine → 인스턴스 → 만들기
    - 이름: nginx-lb-vm
    - 리전/영역: us-central1 / us-central1-a
    - 머신 유형: e2-micro

    ⚙️ 네트워크 설정 (화면 아래로 스크롤)
    화면을 아래로 많이 스크롤하여 [네트워킹, 디스크, 보안, 관리, 단독 테넌시](또는 고급 옵션) 아코디언 메뉴를 찾아 클릭한다.
    - [네트워킹] 탭 클릭 → [네트워크 인터페이스] 기본 설정 항목의 연필(수정) 아이콘 클릭
    - 네트워크: free-prd-vpc
    - 서브넷: free-snet-public-web
    - 외부 IPv4 주소: 임시(Ephemeral) 또는 고정 IP 선택 (외부 접근을 위해 필수)
  • VM 접속 후 Nginx 설치:
    sudo apt-get update sudo apt-get install -y nginx
  • Nginx 설정은 뒷단 WAS 서버들의 IP를 확보한 뒤, Step 3 이후에 구성합니다.
3
백엔드 계층 (Spring Boot Multi-AZ)

🏗️ Phase 3 진행 상황: Private WAS VM 구축 및 임시 인터넷 연결 세팅

⚙️ 역할: 서버 이중화 및 내장 DB(H2) 시뮬레이션 유료인 Cloud SQL 대신, Spring Boot 앱 안에 내장된 H2를 각각 실행합니다. A존과 C존에 분산 배치하여 고가용성 구조를 실습합니다.

Step 3-1: WAS 인스턴스 2대 배포 (NAT 꼼수)

⚠️ 외부 IP 임시 할당 꼼수: 원래 외부 IP가 없는 VM이 인터넷(apt-get 등)을 쓰려면 유료인 Cloud NAT가 필요합니다. 무료로 하려면 VM 생성 시 임시 외부 IP를 부여하고, 세팅 완료 후 외부 IP를 떼어내는 방식을 사용하세요.
⚙️ 공통 네트워크 설정 방법 (2대 동일)
인스턴스 만들기 화면 하단으로 내려 [네트워킹] 탭 ➡️ [네트워크 인터페이스] 기본 설정 항목의 연필(수정) 아이콘을 클릭한 뒤 아래 표의 값을 지정한다.

Step 3-2: 로컬 PC에서 도커 이미지 빌드 및 푸시

  • Spring Boot 프로젝트 빌드
    로컬 프로젝트 루트 폴더에서 패키징(빌드) 명령을 수행하여 app.jar 파일을 생성한다.
  • Dockerfile 작성
    빌드된 jar 파일이 위치한 경로에 아래 내용의 Dockerfile을 작성한다.
    FROM openjdk:21-slim COPY app.jar app.jar ENTRYPOINT ["java", "-jar", "/app.jar"]
  • 도커 이미지 빌드 및 도커 허브 업로드
    본인의 도커 허브(Docker Hub) 계정명을 지정하여 이미지를 빌드하고 업로드(Push)한다.
    docker build -t [도커허브계정명]/free-was-app:latest . docker login docker push [도커허브계정명]/free-was-app:latest

Step 3-3: WAS VM에 Docker 설치 및 컨테이너 구동

  • VM에 Docker 설치
    임시 외부 IP가 붙어있는 2대의 WAS VM(free-was-a, free-was-c)에 각각 접속(SSH)하여 도커를 설치한다.
    sudo apt-get update sudo apt-get install -y docker.io
  • 도커 허브에서 이미지 Pull 및 컨테이너 구동
    도커 허브에 푸시했던 백엔드 이미지를 내려받아 8080 포트로 백그라운드 구동한다.
    sudo docker run -d -p 8080:8080 --name spring-was [도커허브계정명]/free-was-app:latest

Step 3-4: WAS 동작 검증 및 외부 IP 제거

  • 도커 실행 상태 및 로그 확인
    각 WAS VM의 SSH 터미널에서 아래 명령을 실행하여 컨테이너가 정상 구동 중인지와 Spring Boot의 실행 로그를 확인한다.
    # 1. 실행 중인 컨테이너 목록 조회 (Status가 Up 8080->8080 인지 체크) sudo docker ps # 2. Spring Boot 콘솔 로그 실시간 확인 (Tomcat started on port 8080 문구 확인) sudo docker logs -f spring-was
  • 로컬 내부 API 호출 테스트 (curl)
    VM 터미널 내에서 스스로의 API 주소를 찔러 JSON 데이터가 정상 반환되는지 직접 확인한다.
    curl http://localhost:8080/api/users
  • 외부 IP 제거 (사설 격리 완수)
    위 검증 과정에서 Spring Boot가 정상 기동되고 curl 호출에 성공했다면, GCP VM 수정 화면으로 이동하여 임시 외부 IP를 '없음'으로 변경함으로써 백엔드 서버를 사설망 안으로 안전하게 격리 완료한다.
4
로드밸런싱 연동 및 테스트

🏗️ Phase 4 진행 상황: 최종 아키텍처 연동 완료 및 서비스 오픈

Step 4-1: Nginx 프론트엔드 랜딩 페이지 배포

💡 웹 SSH 파일 전송 팁 (먹통 방지)
index.html 파일은 크기가 크기 때문에(약 24KB) 직접 nano 창에 복사-붙여넣기를 실행하면 웹 브라우저 터미널 버퍼 한계로 창이 먹통이 되어 뻗을 수 있다. 따라서 구글 콘솔의 [파일 업로드] 기능을 사용해 전송하는 것을 강력히 권장한다.
  • 웹 SSH 파일 업로드 진행
    구글 클라우드 콘솔의 VM SSH 브라우저 창의 우측 상단 ⚙️(톱니바퀴) 또는 도구 모음에서 [파일 업로드]를 선택하고, 로컬의 index.html 파일을 선택하여 업로드한다.
    - 파일은 VM의 홈 디렉토리(~/index.html)에 안전하게 바로 업로드된다.
  • Nginx 웹 기본 경로로 파일 복사
    VM 터미널 창에서 아래 명령어를 실행하여 업로드된 파일을 Nginx 서빙 경로로 덮어쓰기 복사한다.
    sudo cp ~/index.html /var/www/html/index.html

Step 4-2: Nginx 역방향 프록시(Reverse Proxy) 및 로드밸런서 설정

  • Nginx 기본 설정 파일(/etc/nginx/sites-available/default)을 열어 백엔드 WAS 이중화 및 API 프록시 경로 설정을 완료한다.
    sudo nano /etc/nginx/sites-available/default
  • 기존 내용을 모두 지우고 아래와 같이 새 설정을 입력한 뒤 저장한다.
    # 1. 뒷단의 사설망 WAS VM 2대를 로드밸런싱 그룹으로 묶음 upstream backend_was { server 10.250.2.x:8080; # free-was-a의 실제 내부(사설) IP 입력 server 10.250.2.y:8080; # free-was-c의 실제 내부(사설) IP 입력 } server { listen 80 default_server; listen [::]:80 default_server; # Nginx가 서빙할 프론트엔드 정적 파일(대시보드 index.html) 경로 root /var/www/html; index index.html index.htm; server_name _; # 루트(/) 접속 시 대시보드 서빙 location / { try_files $uri $uri/ =404; } # /api/로 들어오는 모든 요청은 뒷단의 WAS 로드밸런싱 그룹으로 안전하게 포워딩 (리버스 프록시) location /api/ { proxy_pass http://backend_was; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; } }
  • Nginx 설정을 검증하고 서비스를 재시작하여 반영한다.
    sudo nginx -t # 설정 구문 에러 검증 (successful 문구 확인) sudo systemctl restart nginx

Step 4-3: 최종 아키텍처 동작 및 분산 검증 (가장 중요)

  • 대시보드 접속 및 웹 CRUD 테스트
    웹 브라우저를 열어 Nginx 웹 서버의 외부 공인 IP 주소(http://[NGINX_외부_IP])로 접속한다.
    - 화면 왼쪽 폼에 회원 로그인 ID, 이름, 비밀번호를 입력하고 [GCP WAS에 등록 전송] 버튼을 누른다.
    - 회원 등록이 정상 성공하며 콘솔 로그 패널에 성공 초록색 로그가 표시되는지 확인한다.
  • 이중화 데이터 분리 직접 눈으로 목격하기 (꿀잼 포인트)
    우측 회원 명부의 [새로고침] 버튼을 2~3초 간격으로 연속해서 클릭해 본다.
    - 로드밸런서(Nginx)가 요청을 Zone A와 Zone C의 WAS 서버로 교대로 분산 포워딩한다.
    - 이때, 각각의 WAS는 메모리(H2 DB)가 독립되어 있어 **회원 명부에 데이터가 보였다가 안 보였다가(데이터 불일치)** 하는 현상이 교대로 나타나야 정상이다. (VPC 격리 및 물리 분산이 완벽하다는 최고의 반증!)
  • 실시간 로드밸런싱 분산 시뮬레이션
    왼쪽 하단의 [5회 고속 API 호출] 버튼을 클릭한다.
    - Nginx를 통해 5개의 API 트래픽이 연속해서 흘러가면서, spring-was 노드 A와 C가 번갈아가며 응답을 처리하고 그 분산 결과가 로그창에 실시간으로 기록되는 모습을 확인한다.
5
[심화] 외부 DB(시놀로지 NAS MySQL) 연동 및 진짜 이중화

🏗️ Phase 5 진행 상황: 외부 시놀로지 NAS MySQL 연동 및 진짜 이중화

💡 왜 하나? (H2 내장형 DB의 한계 극복)
H2 Memory DB는 WAS VM이 꺼지면 데이터가 모두 유실되고, 각 VM이 자신만의 독립된 DB 메모리를 가져 데이터가 동기화되지 않는 한계가 있다. 집의 시놀로지 NAS MySQL이나 외부 데이터베이스로 연결하면, 두 대의 WAS가 하나의 중앙 DB를 공유하게 되면서 비로소 데이터가 완벽하게 일치하는 진정한 액티브-액티브(Active-Active) 이중화가 구현된다.

Step 5-1: 네트워크 및 접속 장벽 해소

  • 집 공유기 및 NAS 방화벽 설정 (인바운드 오픈)
    - **포트포워딩(Port Forwarding)**: 외부 인터넷에서 집 공유기 IP의 TCP 3306 포트로 들어오는 요청을 시놀로지 NAS 내부 IP의 3306 포트로 토스하도록 설정합니다.
    - **DDNS 연결**: IP가 수시로 바뀌는 가정집 환경이므로, 시놀로지 DDNS(예: 아이디.synology.me)를 설정하여 고정 도메인을 확보합니다.
    - **DB 계정 권한**: MySQL에 접속하여 외부(GCP WAS)에서 접속할 수 있는 계정을 생성합니다.
    CREATE USER 'gcp_user'@'%' IDENTIFIED BY '비밀번호'; GRANT ALL PRIVILEGES ON *.* TO 'gcp_user'@'%'; FLUSH PRIVILEGES;
  • GCP WAS 서버의 인터넷 아웃바운드 회선 확보
    GCP의 사설망 VM들은 기본적으로 외부 인터넷(집 NAS)으로 쿼리를 던질 수 없습니다.
    - **간편한 방법 (무료)**: 각 WAS VM 설정으로 이동하여 일시적으로 떼어냈던 임시 외부 IPv4 주소를 다시 장착해 줍니다.
    - **실무형 방법 (유료)**: GCP의 Cloud NAT를 신규 생성하여 사설 IP 대역의 VM들이 외부 인터넷으로 나갈 수 있게 아웃바운드 게이트웨이를 구성합니다.

Step 5-2: Spring Boot application.properties 수정

  • 로컬 소스 코드의 src/main/resources/application.properties의 H2 설정을 주석 처리하고 아래와 같이 시놀로지 DB 정보를 채워 다시 컴파일 및 배포합니다.
    # 기존 H2 설정은 주석 처리 # spring.datasource.url=jdbc:h2:mem:testdb ... # 시놀로지 NAS MySQL 연결 설정 spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver spring.datasource.url=jdbc:mysql://[본인DDNS].synology.me:3306/[디비명]?useSSL=false&characterEncoding=UTF-8&serverTimezone=Asia/Seoul spring.datasource.username=gcp_user spring.datasource.password=비밀번호 # Hibernate DDL 자동 설정 (최초 실행 시 테이블 자동 생성) spring.jpa.database-platform=org.hibernate.dialect.MySQLDialect spring.jpa.hibernate.ddl-auto=update
🎉 무료 플랜 아키텍처 완성!
요금을 한 푼도 내지 않으면서도 (크레딧 미미하게 소모), 대기업에서 사용하는 VPC 분리, Multi-AZ 배포, 그리고 IAP 보안 터널링 및 L7 프록시 서버의 흐름을 완벽하게 실습해 냈습니다.
