CI/CD 파이프라인 완전 가이드

GitHub Actions와 GitLab CI/CD 환경에서의 지속적 통합·배포 아키텍처, 핵심 문법, 시크릿 보안, 그리고 클라우드 무중단 배포 실전 레퍼런스를 총망라하여 정리한다.

1. CI/CD 개요 (GitHub Actions)

CI/CD 파이프라인은 코드 변경 사항을 검증하는 지속적 통합(CI)과 검증된 빌드 결과물을 실제 운영 환경에 반영하는 지속적 배포(CD)로 구성된다.

GitHub Actions CI/CD 파이프라인 라이프사이클
CI (Continuous Integration)
지속적 통합
  • 코드 변경 시 빌드 및 단위/통합 테스트를 자동으로 수행한다.
  • Pull Request 단계에서 결함과 컴파일 에러를 조기에 발견한다.
  • 코드 품질 정적 분석(Lint, SonarQube) 및 테스트 커버리지를 강제한다.
  • 메인 브랜치 코드베이스의 안정성을 지속적으로 보장한다.
CD (Continuous Deployment)
지속적 배포
  • 검증 완료된 아티팩트를 스테이징 및 프로덕션 환경에 자동으로 배포한다.
  • 인간의 수동 개입을 최소화하여 배포 주기와 소요 시간을 대폭 단축한다.
  • 롤백(Rollback) 및 카나리/블루그린 무중단 배포 전략을 연동한다.
  • 인프라 배포 자동화(IaC) 및 컨테이너 오케스트레이션과 결합한다.

2. 디렉토리 구조 (GitHub Actions)

GitHub Actions의 워크플로우 정의 파일은 반드시 프로젝트 루트의 .github/workflows/ 경로에 위치해야 하며, .yml 또는 .yaml 형식을 사용한다.

표준 디렉토리 트리 권장안 
.github/
├── workflows/                  # 워크플로우 YAML 파일 저장소 (필수)
│   ├── ci.yml                  # CI: 빌드 및 테스트 자동화
│   ├── cd.yml                  # CD: 프로덕션 배포 파이프라인
│   ├── release.yml             # 릴리즈 태그 생성 및 자동 배포
│   └── security.yml            # CodeQL 및 정적 보안 스캔
├── actions/                    # 커스텀 Composite 액션 (선택 사항)
│   └── setup/
│       └── action.yml
└── CODEOWNERS                  # 브랜치/디렉토리별 코드 리뷰 오너 지정

3. Workflow 기본 구성 문법

GitHub Actions 워크플로우의 핵심 키워드는 name, on, env, jobs, runs-on, steps로 이루어진다.

주요 키워드 정의
키워드 설명 예시
name 워크플로우의 명칭으로 GitHub Actions UI 탭에 표시된다. name: CI Pipeline
on 파이프라인 실행을 유발하는 이벤트 트리거 조건을 선언한다. push, pull_request
env 전역 또는 특정 Job/Step 범위에서 사용할 환경변수를 정의한다. NODE_VERSION: '20'
jobs 독립된 가상머신 러너에서 실행되는 작업 단위(기본 병렬 실행)다. build, test
runs-on 해당 Job을 실행할 OS 러너 환경을 지정한다. ubuntu-latest
steps 순차적으로 실행되는 개별 태스크 목록으로 액션(uses) 또는 셸 명령(run)을 실행한다. uses: actions/checkout@v4
.github/workflows/ci.yml (표준 Node.js CI) 
name: CI Pipeline

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

env:
  NODE_VERSION: '20'

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: 소스코드 체크아웃
        uses: actions/checkout@v4

      - name: Node.js 런타임 환경 설정
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      - name: 의존성 패키지 설치
        run: npm ci

      - name: 린트 검증 및 단위 테스트 실행
        run: |
          npm run lint
          npm test -- --coverage
          npm run build

4. 트리거(on) 설정

브랜치 푸시, PR 이벤트뿐 아니라 스케줄 크론(Cron) 및 수동 실행(workflow_dispatch) 매개변수를 지원한다.

push / pull_request

브랜치(branches), 태그(tags), 파일 변경 경로(paths/paths-ignore) 필터를 정밀하게 적용한다.

schedule

표준 UTC Cron 표현식을 기반으로 야간 정기 빌드 및 취약점 검사를 주기적으로 수행한다.

workflow_dispatch

GitHub 웹 UI 또는 API를 통해 사용자가 직접 배포 대상 환경 등의 인자(inputs)를 입력받아 실행한다.

복합 트리거 및 수동 인자 설정 예시 
on:
  push:
    branches: [ main, 'release/**' ]
    paths: [ 'src/**', 'package*.json' ]
    paths-ignore: [ 'docs/**', '**.md' ]

  pull_request:
    types: [ opened, synchronize, reopened ]

  schedule:
    - cron: '0 2 * * 1-5'   # 평일 매일 오전 2시 (UTC) 정기 검증

  workflow_dispatch:
    inputs:
      environment:
        description: '배포 대상 환경'
        required: true
        type: choice
        options: [ staging, production ]
      deploy_tag:
        description: '배포할 이미지 태그'
        required: true
        default: 'latest'

5. Jobs & Steps 심화 (Context & DAG)

Job 간의 실행 순서를 제어하는 needs, 표현식 컨텍스트 참조, 조건부 실행(if) 문법이다.

needs 의존성 및 출력값(outputs) 전달 
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  build:
    needs: test                     # 1단계 test 완료 후 실행
    runs-on: ubuntu-latest
    outputs:
      image_tag: ${{ steps.meta.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - id: meta
        run: echo "tag=v1.0.${{ github.run_number }}" >> $GITHUB_OUTPUT

  deploy:
    needs: [ test, build ]          # test와 build가 모두 성공해야 실행
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: 이전 Job의 출력값 활용 배포
        run: echo "배포할 이미지: ${{ needs.build.outputs.image_tag }}"

6. 환경변수 & 시크릿 관리 (OIDC 인증)

API Key 및 DB 패스워드는 절대 코드에 커밋하지 않고 GitHub Secrets에 등록하여 사용하며, 클라우드 환경에서는 영구 액세스 키 대신 OIDC(OpenID Connect) 단기 토큰 인증을 채택한다.

AWS OIDC 단기 토큰 인증 배포 
permissions:
  id-token: write                  # AWS OIDC 토큰 발급에 필수 권한
  contents: read

jobs:
  deploy-aws:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: AWS 단기 자격증명 수동 발급
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
          aws-region: ap-northeast-2

      - name: AWS ECS 배포 실행
        run: aws ecs update-service --cluster prod --service api --force-new-deployment

7. 실전 예제 모음 (Docker GHCR & Release)

GitHub Container Registry (GHCR) 도커 빌드 & 푸시 
name: Docker Build and Publish

on:
  push:
    branches: [ main ]

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4

      - name: Docker Buildx 설정
        uses: docker/setup-buildx-action@v3

      - name: GHCR 레지스트리 로그인
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: 이미지 빌드 및 GHCR 자동 푸시
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

8. 무중단 배포 전략

Blue-Green 배포

구버전(Blue)과 신버전(Green) 인스턴스를 병렬 가동 후 라우터 트래픽을 일괄 전환하여 롤백 속도를 극대화한다.

Canary 배포

전체 트래픽의 5%~10% 소수 사용자에게 신버전을 우선 노출하여 오류를 조기에 모니터링한다.

Rolling 배포

클러스터 인스턴스를 순차적으로 하나씩 교체하며 무중단 운영을 유지하는 가장 보편적인 방식이다.

9. 보안 체크리스트

필수 워크플로우 보안 수칙
  • permissions 최소 권한 원칙을 전역에 적용한다.
  • 외부 액션 참조 시 Git SHA 40자 핀닝(Pinning)을 적용한다.
  • 로그 출력 시 시크릿 값(echo $TOKEN) 노출을 금지한다.
  • Dependabot을 활성화하여 액션 취약점을 주기적으로 자동 패치한다.
Branch Protection 수칙
  • main 및 develop 브랜치 직접 Push를 전면 차단한다.
  • PR 머지 전 필수 CI 통과(Status Checks)를 강제한다.
  • 최소 1명 이상의 필수 코드 리뷰어 승인을 요구한다.
  • 프로덕션 Environment 승인자(Reviewers) 수동 승인 체계를 구축한다.

1. CI/CD 개요 (GitLab CI/CD)

GitLab CI/CD는 단일 파일 .gitlab-ci.yml로 파이프라인을 정의하며, Stage 기반 순차 실행과 Stage 내부 Job들의 병렬 실행 구조를 가진다.

GitLab CI/CD Stage 파이프라인 흐름
GitLab CI/CD 핵심 아키텍처
GitLab
  • 프로젝트 루트의 단일 .gitlab-ci.yml 파일로 통합 관리한다.
  • stages 키워드로 파이프라인 단계 순서를 명시적으로 제어한다.
  • 내장 Container Registry 및 패키지/아티팩트 스토리지를 기본 제공한다.
  • GitLab Runner(SaaS 공용 러너 또는 Self-hosted 전용 러너)를 지원한다.
GitHub Actions 대비 주요 차이점
비교
  • GitHub Actions는 Job 중심, GitLab CI는 Stage 중심 순차 모델이다.
  • 트리거 조건문으로 on 대신 rules / when을 사용한다.
  • 마켓플레이스 대신 include 템플릿과 YAML 앵커(&, *)를 활용한다.
  • CI/CD Variables를 통해 마스킹(Masked)과 보호(Protected)를 설정한다.

2. 파일 구조 및 include 분리

GitLab CI는 프로젝트 루트의 .gitlab-ci.yml을 메인 진입점으로 사용하며, 대규모 프로젝트의 경우 include를 통해 하위 YAML 모듈로 분할한다.

.gitlab-ci.yml 모듈 분할 구성 
# .gitlab-ci.yml 메인 파일
include:
  - local: '.gitlab/ci/build.yml'           # 로컬 빌드 Job 설정
  - local: '.gitlab/ci/test.yml'            # 로컬 테스트 Job 설정
  - local: '.gitlab/ci/deploy.yml'          # 로컬 배포 Job 설정
  - template: 'Security/SAST.gitlab-ci.yml' # GitLab 내장 SAST 보안 스캔 템플릿

3. Pipeline 기본 구성 문법

GitLab CI의 핵심 키워드는 stages, image, variables, before_script, script, artifacts, cache로 구성된다.

.gitlab-ci.yml 표준 파이프라인 예제 
stages:
  - build
  - test
  - deploy

image: node:20-alpine

variables:
  NODE_ENV: production
  FF_USE_FASTZIP: "true"

cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/
  policy: pull-push

build-job:
  stage: build
  before_script:
    - npm ci
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 week

test-job:
  stage: test
  script:
    - npm run lint
    - npm test -- --coverage
  coverage: '/Statements\s*:\s*(\d+\.?\d*)%/'

deploy-job:
  stage: deploy
  environment:
    name: production
    url: https://app.example.com
  script:
    - echo "Deploying to production"

4. 트리거(rules) 설정

레거시 only/except 대신 rules 키워드를 사용하여 유연한 브랜치 분기 및 수동 승인(when: manual)을 구현한다.

rules 조건부 실행 및 수동 승인 
deploy-staging:
  stage: deploy
  script:
    - ./deploy.sh staging
  rules:
    - if: $CI_COMMIT_BRANCH == "develop"
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

deploy-production:
  stage: deploy
  script:
    - ./deploy.sh production
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual                    # 프로덕션 배포 시 관리자 수동 승인 요구
      allow_failure: false

test-changes:
  stage: test
  script:
    - npm test
  rules:
    - changes:
        - src/**/*
        - package*.json

5. 내장 변수 및 DAG (needs)

GitLab이 자동으로 주입하는 내장 변수($CI_xxx)와 Stage 순서를 초월해 즉시 실행되는 DAG(needs) 파이프라인이다.

GitHub Actions ↔ GitLab CI 변수 1:1 대응표
의미 GitHub Actions GitLab CI/CD
현재 브랜치명 ${{ github.ref_name }} $CI_COMMIT_BRANCH
커밋 단축 SHA ${{ github.sha }} $CI_COMMIT_SHORT_SHA
이벤트 트리거 ${{ github.event_name }} $CI_PIPELINE_SOURCE
저장소/프로젝트명 ${{ github.repository }} $CI_PROJECT_NAME
자동 발급 토큰 ${{ secrets.GITHUB_TOKEN }} $CI_JOB_TOKEN
실행 번호 (ID) ${{ github.run_number }} $CI_PIPELINE_IID

6. GitLab 변수 & 시크릿 관리

GitLab UI(Settings ➔ CI/CD ➔ Variables)에서 등록하며, Masked(로그 마스킹)와 Protected(보호 브랜치 전용) 옵션을 필수로 활성화한다.

GitLab Container Registry 로그인 및 배포 
# 내장 CI 레지스트리 자동 로그인 및 빌드 푸시
docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

7. GitLab Pages 자동 배포 예제

정적 웹사이트를 빌드하여 GitLab Pages로 호스팅할 때는 반드시 Job 명칭을 pages로 선언하고 아티팩트 경로를 public/으로 지정한다.

GitLab Pages 배포 설정 
stages:
  - build
  - deploy

build-site:
  stage: build
  image: node:20-alpine
  script:
    - npm ci && npm run build
  artifacts:
    paths:
      - public/

pages:                          # Job 이름이 반드시 'pages' 여야 함
  stage: deploy
  script:
    - echo "Deploying to GitLab Pages"
  artifacts:
    paths:
      - public/
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

8. 동적 Review Apps 배포 전략

Merge Request마다 독립된 임시 테스트 환경을 동적으로 생성하고, MR이 닫힐 때 환경을 자동으로 정리(Tear down)한다.

Review Apps 동적 프로비저닝 및 자동 종료 
deploy-review:
  stage: deploy
  script:
    - ./deploy.sh review $CI_ENVIRONMENT_SLUG
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_ENVIRONMENT_SLUG.example.com
    on_stop: stop-review
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

stop-review:
  stage: deploy
  script:
    - ./teardown.sh $CI_ENVIRONMENT_SLUG
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
  when: manual

9. GitLab 보안 및 SAST 스캔

GitLab 변수 & 러너 보안
  • 민감 변수에 Masked 및 Protected 옵션을 필수로 적용한다.
  • $CI_JOB_TOKEN 접근 범위를 최소한의 프로젝트로 격리한다.
  • Runner 태그를 활용해 운영 배포 전용 러너를 물리적으로 분리한다.
내장 보안 스캔 자동화
  • SAST(정적 소스코드 분석) 템플릿을 파이프라인에 포함한다.
  • Dependency Scanning을 통해 취약한 라이브러리를 탐지한다.
  • Secret Detection으로 코드 내 시크릿 오커밋을 사전에 차단한다.
