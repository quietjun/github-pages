JSP(Jakarta Server Pages) & MVC 아키텍처 핵심 요약

서블릿 기반 화면 구현의 한계를 극복하는 JSP의 동작 원리와 스크립트 요소, 4대 웹 스코프 및 Attribute 관리, 그리고 Model 2 MVC 아키텍처와 forward / redirect의 이동 메커니즘을 체계적으로 복습합니다.

1. Servlet의 한계와 JSP의 본질

왜 JSP(Jakarta Server Pages)를 사용하는가?
구분 Servlet (서블릿) JSP (Jakarta Server Pages)
코드 형태 Java 코드 중심에 HTML 태그를 문자열로 결합
out.println("<html><body>...");		 HTML 태그 중심에 필요한 부분만 Java 코드를 삽입
<h1>환영합니다 <%= name %></h1>
주요 역할 비즈니스 로직 연산, 요청 제어, DB 연동 (Controller) 사용자 화면 표현, UI 프레젠테이션 (View)
장단점 로직 구현과 디버깅이 쉬우나 화면 디자인 수정이 극히 불편함 화면 작성이 직관적이고 쉬우나 비즈니스 로직 작성 시 복잡성 증가

2. JSP의 동작 원리와 라이프사이클 (중간단계로서의 JSP)

"JSP는 중간단계! 최종 산출물은 Servlet이다."

브라우저가 .jsp 파일을 요청하면 컨테이너(WAS)는 JSP 파일을 그대로 실행하지 않고, Java 서블릿 소스코드로 자동 변환(Translation)한 뒤 바이트코드로 컴파일(Compilation)하여 실행합니다.

1단계
변환 (Translation)
xxx.jsp 파일이 xxx_jsp.java (서블릿 클래스 소스)로 변환됨
2단계
컴파일 (Compilation)
xxx_jsp.java가 xxx_jsp.class 바이트코드로 컴파일되어 메모리 로드
3단계
실행 (Execution)
_jspService() 메서드가 요청마다 호출되어 HTML 응답 스트림 출력
JSP 생명주기 메서드 3가지
메서드 호출 시점 역할 및 특징
jspInit() 서블릿 인스턴스 생성 후 1회 JSP 페이지의 초기화 작업 수행 (서블릿의 init()에 해당)
_jspService() 클라이언트 요청마다 매번 JSP 내부의 HTML 템플릿과 스크립트릿 로직이 실행되어 응답을 생성하는 핵심 메서드
jspDestroy() 서블릿 인스턴스 소멸(재배포/코드 수정/서버 종료) 시 1회 점유 자원을 해제하고 소멸 (서블릿의 destroy()에 해당)

3. JSP 지시자(Directive)와 스크립트 요소

지시자 (Directive): 컨테이너에 페이지 환경 정보 전달
<%-- page 지시자: 인코딩 및 패키지 임포트 선언 --%>
<%@ page language="java" contentType="text/html; charset=UTF-8" pageEncoding="UTF-8"%>
<%@ page import="java.util.*, java.time.LocalDateTime"%>
JSP 스크립트 3대 요소 비교 (서블릿 변환 위치가 핵심!)
스크립트 요소 문법 형태 서블릿 변환 위치 용도 및 주의사항
Scriptlet
(스크립트릿)		 <% 자바코드; %> _jspService() 메서드 내부
(로컬 영역)		 일반 로직 처리, 내장 객체 직접 참조 가능, 로컬 변수로 선언됨
Declaration
(선언문)		 <%! 선언코드; %> 서블릿 클래스 바디
(멤버 변수/메서드 영역)		 인스턴스 필드/메서드 선언. 모든 스레드가 공유하므로 상태 관리 절대 금지
Expression
(표현식)		 <%= 출력값 %> out.print(출력값)으로 변환 변수값, 연산식, 반환값이 있는 메서드 호출 결과 출력 (세미콜론 ; 생략)

※ JSP 주석(<%-- --%>) vs HTML 주석(<!-- -->): JSP 주석은 서블릿 변환 시 완전히 제거되어 클라이언트 브라우저의 소스보기에서 보이지 않지만, HTML 주석은 브라우저로 그대로 전송되어 노출됩니다.

4. Built-in Object(내장 객체)와 4대 Web Scope

내장 객체(Built-in Object)의 개념

JSP가 서블릿으로 변환될 때 _jspService() 메서드 내부에 로컬 변수로 이미 선언되어 제공되는 객체들입니다. 별도의 new 생성 없이 바로 사용할 수 있습니다.
• 주요 객체: request (HttpServletRequest), response (HttpServletResponse), session (HttpSession), application (ServletContext), out (JspWriter), pageContext (PageContext)

4대 웹 스코프(Web Scope)와 데이터 생명주기
웹 스코프 담당 내장 객체 유효 범위 및 생명주기 주요 활용 예시
page pageContext 해당 JSP 페이지가 실행되는 동안에만 유효 페이지 내부 임시 변수
request request 하나의 클라이언트 HTTP 요청이 완료될 때까지 유효 (forward 시 유지됨) 컨트롤러가 조회한 목록/결과 데이터 전달
session session 동일 클라이언트(브라우저)가 유지되는 동안 유효 (세션 타임아웃 또는 브라우저 종료 시 소멸) 로그인 사용자 정보, 장바구니
application application (ServletContext) 웹 애플리케이션(Context) 전체에서 서버가 종료될 때까지 유효 전역 설정, 공통 리소스 풀, 전체 방문자 수
Request Parameter vs Attribute 핵심 비교 (Slide 16)
비교 항목 Request Parameter Request Attribute
데이터 생성 주체 클라이언트 (브라우저 form 입력값, URL 쿼리스트링) 서버 개발자 (서블릿, JSP 내부 로직)
저장 데이터 타입 언제나 문자열(String) 또는 String[] 모든 자바 객체(Object) (DTO, List 등)
수정 가능 여부 읽기 전용 (클라이언트 전송 후 변경 불가) 읽기/쓰기 자유로움 (추가, 수정, 삭제 가능)
조작 API getParameter(name) setAttribute(name, obj), getAttribute(name)

5. MVC 패턴과 Model 1 vs Model 2 아키텍처

Model 1과 Model 2 아키텍처 비교
아키텍처 구조 및 처리 방식 장단점 및 실무 적용
Model 1 JSP가 클라이언트 요청 접수(Controller)와 화면 출력(View)을 동시에 수행하며 Service/DAO(Model) 호출 구조가 단순하여 빠른 개발이 가능하지만, JSP 내에 자바 비즈니스 로직이 뒤섞여 유지보수가 극히 어려움
Model 2 (표준 MVC) Servlet이 Controller를 맡아 요청 접수 및 비즈니스 조절을 전담하고, JSP는 오직 화면(View)만 렌더링 관심사 분리(SoC)로 역할이 명확하여 대규모 협업 및 유지보수성이 매우 뛰어남 (실무 표준)
Model 2 MVC 처리 3단계 흐름
Step 1
Controller (Servlet)
요청 접수, 파라미터 유효성 검증, 비즈니스 서비스 호출
Step 2
Model (Service/DAO)
업무 로직 연산 수행, DB 영속성 질의 처리 후 DTO/결과 반환
Step 3
View (JSP)
서블릿이 request.setAttribute()에 담아 forward한 데이터를 화면에 출력

6. 웹 컴포넌트 호출 방식: forward vs sendRedirect

두 이동 방식의 내부 메커니즘 완벽 비교 (핵심)
구분 RequestDispatcher#forward HttpServletResponse#sendRedirect
동작 주체 서버 내부에서 제어권만 다음 컴포넌트로 위임 서버가 브라우저에게 302 상태 코드를 보내어 브라우저가 새 요청 재전송
브라우저 URL 변경되지 않음 (클라이언트는 내부 이동을 모름) 새로운 URL로 변경됨
Request 객체 기존 request, response 객체가 유지됨 기존 request는 소멸되고 새로운 request가 생성됨
데이터 전달 request.setAttribute()에 담은 데이터 확인 가능 이전 요청의 request.setAttribute() 데이터 전달 불가
이동 범위 동일 컨테이너 내부 리소스만 가능 서버 내부뿐 아니라 외부 사이트(ex: http://google.com)도 가능
적합한 업무 데이터 조회(SELECT), 폼 화면 렌더링 데이터 변경(INSERT, UPDATE, DELETE) 후 새로고침 중복 방지 (PRG 패턴) 
// 1. forward 코드 예시 (데이터 유지 이동)
request.setAttribute("result", guguData);
RequestDispatcher dispatcher = request.getRequestDispatcher("/gugu-result.jsp");
dispatcher.forward(request, response);

// 2. sendRedirect 코드 예시 (새로운 요청 생성 이동)
response.sendRedirect(request.getContextPath() + "/board/list");
Review Case 1: 회원 등록 후 새로고침할 때마다 동일 회원이 중복 가입되는 사고
🚨 발생 증상 (Trouble Scenario)
"회원 가입 서블릿을 개발하여 배포했습니다. 그런데 사용자가 가입 완료 화면에서 F5(새로고침)를 누를 때마다 DB에 동일한 회원이 계속해서 추가 삽입되는 심각한 중복 결함 사고가 발생했습니다. 코드를 보고 원인을 찾아보세요." 
@WebServlet("/member/regist")
public class MemberRegistController extends HttpServlet {
    @Override
    protected void doPost(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        String id = request.getParameter("id");
        String name = request.getParameter("name");

        // 비즈니스 로직: DB에 회원 정보 INSERT
        memberService.registMember(new MemberDto(id, name));

        // 등록 완료 화면으로 이동
        RequestDispatcher dispatcher = request.getRequestDispatcher("/member/regist-success.jsp");
        dispatcher.forward(request, response);
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: 등록 작업 후 forward 오용 (PRG 패턴 미적용)
[원인 분석]
forward()는 브라우저의 URL 주소를 변경하지 않습니다. 따라서 클라이언트 브라우저 주소창에는 여전히 POST /member/regist 요청이 남아 있습니다.
이 상태에서 사용자가 새로고침(F5)을 누르면 직전 요청인 회원 등록 POST 요청이 재전송되어 동일한 INSERT 작업이 반복 실행됩니다.
Refactored Code (개선 코드: PRG 패턴 적용) 
@WebServlet("/member/regist")
public class MemberRegistController extends HttpServlet {
    @Override
    protected void doPost(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        String id = request.getParameter("id");
        String name = request.getParameter("name");

        memberService.registMember(new MemberDto(id, name));

        // [개선] 데이터 변경(POST) 후에는 sendRedirect로 브라우저가 GET 요청을 보내도록 전환
        response.sendRedirect(request.getContextPath() + "/member/regist-success.jsp");
    }
}
Review Case 2: 컨트롤러에서 전달한 조회 데이터가 JSP에서 null로 나오는 장애
🚨 발생 증상 (Trouble Scenario)
"컨트롤러에서 회원 정보를 조회한 뒤 request.setAttribute로 담고 상세 페이지로 이동시켰으나, JSP 화면에 모든 회원 정보가 빈 값으로 나오고 NullPointerException이 발생합니다. 왜 데이터가 전달되지 않았을까요?" 
@WebServlet("/member/detail")
public class MemberDetailController extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        String id = request.getParameter("id");
        MemberDto member = memberService.getMember(id);

        request.setAttribute("member", member);
        response.sendRedirect(request.getContextPath() + "/member/detail.jsp");
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: Request Scope 전달 시 sendRedirect 오용
[원인 분석]
response.sendRedirect()는 브라우저에게 302 응답을 보내어 완전히 새로운 HTTP GET 요청을 발생시킵니다.
이 과정에서 첫 번째 요청의 HttpServletRequest 객체와 그 안에 담아둔 속성(Attribute)은 소멸되므로, 새 요청을 수신한 detail.jsp에서는 member 객체를 찾을 수 없어 null이 반환됩니다.
Refactored Code (개선 코드) 
@WebServlet("/member/detail")
public class MemberDetailController extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        String id = request.getParameter("id");
        MemberDto member = memberService.getMember(id);

        request.setAttribute("member", member);

        // [개선] request 속성을 유지하여 화면을 그릴 때는 forward를 사용
        RequestDispatcher dispatcher = request.getRequestDispatcher("/member/detail.jsp");
        dispatcher.forward(request, response);
    }
}
Review Case 3: JSP 페이지에서 방문자 수가 다른 사용자와 꼬이는 동시성 장애
🚨 발생 증상 (Trouble Scenario)
"JSP 페이지에서 사용자의 해당 페이지 방문 횟수를 표시하기 위해 카운터를 구현했습니다. 그런데 사용자 A가 새로고침을 하지 않았는데도 숫자가 제멋대로 증가하거나 다른 사용자의 카운트와 뒤섞이는 현상이 발생합니다. 코드를 보고 원인을 찾아보세요." 
<%@ page language="java" contentType="text/html; charset=UTF-8"%>
<%! 
    // 방문 횟수 카운터 선언
    int pageVisitCount = 0; 
%>
<html>
<body>
    <h2>현재 페이지 방문 횟수: <%= ++pageVisitCount %></h2>
</body>
</html>
원인 분석 및 리팩토링 코드 확인
핵심 결함: JSP 선언문(<%! %>)으로 상태 관리 변수 선언
[원인 분석]
<%! %>(선언문) 안에 작성된 코드는 서블릿으로 변환될 때 _jspService() 로컬 변수가 아니라, 서블릿 클래스의 인스턴스 멤버 변수(필드)로 변환됩니다.
JSP 서블릿 역시 싱글톤 객체이므로 모든 클라이언트 요청 스레드가 pageVisitCount 멤버 변수를 공유하여 심각한 Race Condition과 데이터 왜곡이 발생했습니다.
Refactored Code (개선 코드) 
<%@ page language="java" contentType="text/html; charset=UTF-8"%>
<html>
<body>
    <%
        // [개선] 개별 사용자 방문 수는 세션 스코프에서 관리하거나 서블릿 로직에서 처리
        Integer userCount = (Integer) session.getAttribute("userCount");
        userCount = (userCount == null) ? 1 : userCount + 1;
        session.setAttribute("userCount", userCount);
    %>
    <h2>나의 세션 방문 횟수: <%= userCount %></h2>
</body>
</html>
Review Case 4: JSP 작성 후 페이지 요청 시 500 컴파일 에러 발생
🚨 발생 증상 (Trouble Scenario)
"JSP 페이지를 작성하고 브라우저로 요청했으나, 콘솔에 'Duplicate local variable request'라는 서블릿 컴파일 에러가 발생하며 HTTP 500 에러 화면이 출력되었습니다. 왜 컴파일에 실패했을까요?" 
<%@ page language="java" contentType="text/html; charset=UTF-8"%>
<html>
<body>
    <%
        String request = "사용자 요청 메시지";
        String out = "출력 내용";
    %>
    <p><%= request %> - <%= out %></p>
</body>
</html>
원인 분석 및 리팩토링 코드 확인
핵심 결함: JSP 내장 객체 예약어와 로컬 변수명 충돌
[원인 분석]
JSP가 서블릿으로 변환될 때 _jspService() 메서드 내부에는 이미 HttpServletRequest request와 JspWriter out이라는 로컬 변수가 기본으로 선언되어 있습니다.
스크립트릿(<% %>) 역시 _jspService() 내부로 들어가므로, 내장 객체와 동일한 이름으로 로컬 변수를 선언하면 변수명 중복 선언(Duplicate local variable) 에러가 발생합니다.
Refactored Code (개선 코드)

<html>
<body>

        String userMsg = "사용자 요청 메시지";
        String printContent = "출력 내용";
    %>
    <p><%= userMsg %> - <%= printContent %></p>

Q1. Servlet과 JSP의 차이점 및 각각의 장단점과 최적의 역할을 설명해 주세요. 답변 확인 ▼
[두괄식 결론]
Servlet은 자바 코드 중심의 비즈니스 로직 및 제어(Controller)에 적합하고, JSP는 HTML 태그 중심의 UI 화면 표현(View)에 최적화된 기술입니다.
[핵심 동작 차이와 발전]
서블릿은 자바 클래스 내에서 HTML을 문자열 스트림으로 출력해야 하므로 화면 작성이 극히 비효율적입니다. 반면 JSP는 HTML 템플릿 기반에 필요한 자바 코드만 삽입하므로 화면 생산성이 우수합니다.
그러나 JSP에 모든 비즈니스 로직을 몰아넣으면 유지보수가 무너지므로, 실무에서는 서블릿이 비즈니스 연산과 데이터 조회를 제어하고, JSP는 오직 request 속성을 받아 화면만 출력하는 MVC (Model 2) 협업 구조로 운영합니다.

Q2. RequestDispatcher의 forward와 HttpServletResponse의 sendRedirect의 차이점을 상세히 비교해 주세요. 답변 확인 ▼
[두괄식 결론]
forward는 서버 내부에서 제어를 위임하여 URL과 request 객체가 유지되는 방식이고, sendRedirect는 브라우저에게 302 응답을 주어 새로운 GET 요청을 유도하는 방식입니다.
[3대 핵심 차이점]
1. URL 변화: forward는 브라우저 주소창이 유지되지만, redirect는 새 URL로 변경됩니다.
2. Request 객체 및 데이터: forward는 기존 request와 response가 그대로 전달되어 request.setAttribute() 데이터를 공유할 수 있지만, redirect는 새 요청이 발생하므로 이전 request 데이터가 소멸됩니다.
3. 적합한 업무: forward는 단순 조회(SELECT) 및 결과 뷰 렌더링에 적합하며, redirect는 데이터 생성/수정/삭제 후 새로고침 중복을 막는 PRG 패턴에 필수입니다.
🎯 꼬리 질문 대비
"redirect 시에도 다음 페이지에 일회성 메시지(예: '가입 성공')를 전달하고 싶다면 어떻게 하나요?" → "request 대신 session.setAttribute()에 담아두고 꺼낸 뒤 삭제(Flash Attribute)하거나, URL 뒤에 쿼리스트링 파라미터로 넘겨 처리합니다."
Q3. 웹 애플리케이션의 4대 Web Scope(page, request, session, application)의 유효 범위와 생명주기를 비교해 주세요. 답변 확인 ▼
[두괄식 결론]
상태 데이터를 공유하는 범위에 따라 page(단일 페이지), request(단일 요청), session(사용자 브라우저 세션), application(전체 웹앱)의 4단계로 구분됩니다.
[범위별 생명주기 및 용도]
• page: 해당 JSP 실행 중에만 유지되며 가장 좁은 범위입니다.
• request: 클라이언트의 1개 HTTP 요청이 끝나거나 브라우저 응답이 완료될 때까지 유지되며, forward 이동 시에도 공유되어 컨트롤러와 뷰 사이의 데이터 전달 표준으로 사용됩니다.
• session: 동일 브라우저의 접속 유지 시간 동안 지속되며 로그인 사용자 세션 정보나 장바구니에 활용됩니다.
• application: 톰캣 컨텍스트 기동부터 종료까지 서버 메모리에 상주하며 전역 설정 및 공통 캐시 공유에 사용됩니다.
🎯 꼬리 질문 대비
"데이터를 저장할 때 무조건 session이나 application에 넣으면 편하지 않나요?" → "세션과 애플리케이션 스코프는 서버 메모리(Heap)에 상주하므로 대규모 동시 접속 시 메모리 고갈(OOM)을 유발합니다. 따라서 데이터의 생명주기에 맞는 가장 좁은 스코프(가급적 request)를 사용하는 것이 원칙입니다."
Q4. 웹 폼 처리 시 Post-Redirect-Get(PRG) 패턴이 필요한 이유와 동작 흐름을 설명해 주세요. 답변 확인 ▼
[두괄식 결론]
POST 요청 후 새로고침(F5) 시 동일한 데이터 등록이나 결제 트랜잭션이 중복 실행되는 사고를 방지하기 위한 핵심 웹 아키텍처 패턴입니다.
[동작 흐름과 원리]
클라이언트가 POST로 등록 요청을 보내면 서블릿이 DB 작업을 수행한 뒤, forward하지 않고 sendRedirect를 통해 302 응답과 함께 결과 조회 URL(GET)을 전달합니다.
브라우저는 자동으로 해당 URL로 GET 요청을 재전송하여 화면을 띄우므로, 주소창의 최신 요청이 GET으로 갱신됩니다. 따라서 이후 사용자가 새로고침을 누르더라도 안전하게 GET 조회만 재수행되어 중복 결제나 중복 가입이 원천 차단됩니다.

Q5. MVC Model 1과 Model 2의 차이점 및 실무에서 Model 2를 채택하는 이유를 설명해 주세요. 답변 확인 ▼
[두괄식 결론]
Model 1은 JSP가 컨트롤러와 뷰를 모두 처리하는 구조이고, Model 2는 서블릿이 컨트롤러, JSP가 뷰를 맡아 역할을 엄격히 분리한 구조입니다.
[실무에서 Model 2를 쓰는 이유]
Model 1은 초기 구축은 빠르지만 JSP 안에 자바 비즈니스 로직과 HTML이 뒤섞여 디버깅이 어렵고 디자이너와 개발자 간 협업이 불가능합니다.
Model 2는 서블릿이 요청 분기와 비즈니스 호출을 전담하고 JSP는 순수 화면 표현만 전담하므로 관심사가 완벽히 분리됩니다. 이 구조는 유지보수성과 확장성이 우수하며, 현대적인 프레임워크(Spring MVC 등)의 근간 아키텍처가 됩니다.
🎯 꼬리 질문 대비
"Model 2에서 컨트롤러(서블릿)와 뷰(JSP) 사이의 데이터 전달은 어떤 방식을 사용하나요?" → "서블릿에서 비즈니스 로직 결과를 request.setAttribute()에 객체로 저장한 뒤, RequestDispatcher#forward()를 호출하여 JSP로 제어권을 넘겨 화면을 렌더링합니다."
