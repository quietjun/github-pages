Backend Programming • EL & JSTL

EL & JSTL 및 페이지 모듈화 핵심 요약

스크립트릿을 걷어내고 뷰를 태그화하는 EL과 JSTL 코어 태그, 그리고 include directive를 통한 프래그먼트 모듈화까지 교안의 전 내용을 체계적으로 복습합니다.

1. EL(Expression Language)의 본질과 스코프 탐색

JSP를 진정한 태그 중심 뷰로 만드는 EL

JSP 내부에 복잡한 자바 코드(스크립트릿 <% %>, 표현식 <%= %>)를 완전히 제거하고, 웹 디자이너나 퍼블리셔도 쉽게 읽을 수 있는 출력 전용 간결한 표현식입니다.

문법
기본 표기법
${attribute_name} 형태로 작성하며, 값이 없거나 null인 경우 null을 출력하지 않고 빈 공백("")으로 안전하게 렌더링
탐색
4대 스코프 자동 탐색
작은 범위에서 큰 범위로 확장하며 처음 발견된 값 사용:
pageScope → requestScope → sessionScope → applicationScope
지정
명시적 스코프 지정
스코프 간 속성명이 겹칠 경우 명시적으로 스코프 객체 사용 가능:
${sessionScope.userName}, ${requestScope.list}
💡 JavaScript 템플릿 리터럴과의 충돌 주의:
JSP 파일 내의 ${...}는 서버가 먼저 EL로 인식하여 파싱합니다. 클라이언트 자바스크립트의 ES6 백틱 템플릿 리터럴(`${item.name}`)로 전달하려면 반드시 \${item.name} 형태로 역슬래시 이스케이프(Escape) 처리를 해야 합니다.

2. EL 내장 객체, 프로퍼티 접근법 및 연산자

주요 EL 내장 객체 (Built-in Objects)
EL 내장 객체 객체 타입 표현 데이터 및 사용 예시
pageContext PageContext 현재 JSP의 PageContext 객체 (ex: ${pageContext.request.contextPath})
pageScope / requestScope
sessionScope / applicationScope		 Map 각 스코프에 바인딩된 속성(Attribute) 맵 (ex: ${requestScope.member})
param / paramValues Map 클라이언트 요청 파라미터의 단일 값(String) 및 다중 배열(String[])
header / headerValues Map HTTP 요청 헤더 정보
cookie Map 현재 요청의 쿠키 정보 (ex: ${cookie.JSESSIONID.value})
객체 프로퍼티 접근법과 연산자 특성

• 프로퍼티 접근: ${member.name}은 필드에 직접 접근하는 것이 아니라 내부적으로 자바빈 규칙에 따라 getName() getter 메서드를 호출합니다. (Record 객체는 필드명 그대로 접근, Map 계열은 key 값으로 접근)
• 메서드 직접 호출: ${users.size()}, ${users.contains("hong")}처럼 일반 메서드 호출도 지원합니다.

연산자 Java와의 결정적인 차이점 및 특징
산술 덧셈 (+) 문자열 연결(Concatenation)을 지원하지 않음! 무조건 숫자로 자동 캐스팅하여 계산함.
ex) ${"1" + "2"} → 3, 문자가 섞인 ${"1" + "b"}는 오류 발생
나눗셈 (/, div) 정수끼리 나누어도 실수를 반환함. ex) ${5 / 2} → 2.5
비교 연산자 수치 비교뿐 아니라 문자열 사전식 비교도 지원함. ex) ${"CAT" > "DOG"} → false
empty 연산자 다음에 해당하는 경우 모두 true로 평가:
① null, ② 빈 문자열(""), ③ 길이가 0인 배열, ④ 비어있는 Collection/Map 객체

3. JSTL(JSP Standard Tag Library) 코어 태그

라이브러리 설정과 Core 태그 선언 (Jakarta EE 10+ 스펙)
<!-- pom.xml 의존성 선언 -->
<dependency>
    <groupId>jakarta.servlet.jsp.jstl</groupId>
    <artifactId>jakarta.servlet.jsp.jstl-api</artifactId>
    <version>3.0.0</version>
</dependency>
<dependency>
    <groupId>org.glassfish.web</groupId>
    <artifactId>jakarta.servlet.jsp.jstl</artifactId>
    <version>3.0.1</version>
</dependency>

<!-- JSP 페이지 상단 태그라이브러리 지시자 선언 -->
<%@ taglib prefix="c" uri="jakarta.tags.core"%>
핵심 JSTL 태그 4종 활용법
변수 제어
<c:set> & <c:remove>
스코프 영역에 EL 변수를 생성하거나 삭제
<c:set var="root" value="${pageContext.request.contextPath}"/>
단일 조건
<c:if>
조건식 평가 (else 태그가 없으므로 반대 조건은 empty 연산자로 별도 선언)
<c:if test="${!empty list}">
다중 조건
<c:choose>
Java의 if-else if-else 또는 switch-case 블록 구현
<c:when test="...">, <c:otherwise>
반복문
<c:forEach>
컬렉션/배열 순회 또는 고정 횟수 루프
items="${members}" var="m" varStatus="st"
(st.index: 0부터, st.count: 1부터)

4. include 지시자(<%@ include %>)와 페이지 모듈화

정적 포함(Static Include)의 원리와 공통 컴포넌트 분리

웹 페이지의 공통 영역(Header, Navigation, Footer 등)을 별도의 JSP 프래그먼트 파일로 분리하여 재사용합니다. 

<!-- /fragments/header.jsp -->
<%@ page language="java" contentType="text/html; charset=UTF-8"%>
<%@ taglib prefix="c" uri="jakarta.tags.core"%>
<link href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css" rel="stylesheet">
<c:set var="root" value="${pageContext.request.contextPath}" />

<!-- 본문 JSP에서 정적 포함 -->
<%@ include file="/fragments/header.jsp"%>
<h2>메인 페이지 콘텐츠</h2>
⚠️ 정적 include의 내부 동작 원리 (Slide 31, 33):
<%@ include file="..."%>는 JSP가 서블릿 자바 소스코드(.java)로 변환(Translation)되는 시점에 포함될 파일의 내용이 물리적으로 그대로 복사되어 하나의 단일 서블릿 파일로 병합됩니다.
따라서 포함하는 파일과 포함되는 파일이 동일한 서블릿 메서드 영역을 공유하므로, header.jsp에서 선언한 root EL 변수나 공통 CSS/JS를 본문 JSP에서 바로 참조할 수 있습니다.
Review Case 1: 문자열을 이어 붙이려다 발생한 NumberFormatException 500 장애
🚨 발생 증상 (Trouble Scenario)
"회원 목록 화면에서 성(lastName)과 이름(firstName)을 연결하여 표시하려고 JSP를 작성했습니다. 그런데 페이지 요청 시 'Cannot convert string to number'라는 NumberFormatException과 함께 500 에러 화면이 발생했습니다. 왜 그럴까요?" 
<!-- 회원 성과 이름을 결합하여 출력하려는 JSP 코드 -->
<tr>
    <td>회원 성명: </td>
    <td>${user.lastName + user.firstName}</td>
</tr>
원인 분석 및 리팩토링 코드 확인
핵심 결함: EL 산술 덧셈 연산자의 문자열 결합 불가
[원인 분석]
Java와 달리 EL에서 + 연산자는 오직 산술 덧셈만을 수행하며 문자열 연결(Concatenation) 기능을 지원하지 않습니다.
EL 엔진은 +를 만나면 양쪽 피연산자를 숫자로 자동 형변환(Type Coercion)하려고 시도하는데, "김"이나 "철수" 같은 일반 문자열은 숫자로 변환될 수 없으므로 NumberFormatException이 발생합니다.
Refactored Code (개선 코드) 
<!-- [개선 1] EL 표현식을 나란히 배치하여 자연스러운 문자열 결합 유도 -->
<td>${user.lastName} ${user.firstName}</td>

<!-- [개선 2] String의 concat 메서드 호출 활용 -->
<td>${user.lastName.concat(" ").concat(user.firstName)}</td>
Review Case 2: 자바스크립트 템플릿 리터럴이 브라우저에서 빈 값으로 증발하는 버그
🚨 발생 증상 (Trouble Scenario)
"JSP 내의 자바스크립트에서 fetch로 JSON 데이터를 받아 ES6 템플릿 리터럴로 화면을 동적 렌더링하도록 작성했습니다. 콘솔에는 정상적인 데이터 객체가 들어오는데 브라우저 DOM에는 '<li></li>'처럼 데이터 텍스트가 텅 비어서 렌더링됩니다. 원인이 무엇일까요?" 
<script>
fetch('/api/products')
  .then(res => res.json())
  .then(products => {
      let html = '';
      products.forEach(p => {
          // ES6 백틱 템플릿 리터럴 사용
          html += `<li>${p.name} - ${p.price}원</li>`;
      });
      document.getElementById('list').innerHTML = html;
  });
</script>
원인 분석 및 리팩토링 코드 확인
핵심 결함: 서버 사이드 EL 파서와 클라이언트 템플릿 리터럴 문법 충돌
[원인 분석]
JSP 파일 내의 모든 ${...} 구문은 브라우저로 전송되기 전에 서버(WAS)의 EL 엔진이 먼저 해석합니다.
서버 측 웹 스코프에는 p.name이라는 자바 속성이 존재하지 않으므로, EL 엔진은 이를 빈 문자열("")로 치환하여 브라우저에 내려보냅니다. 따라서 클라이언트 JS에는 html += `<li> - 원</li>`;로 전송되어 값이 증발합니다.
Refactored Code (개선 코드) 
<script>
fetch('/api/products')
  .then(res => res.json())
  .then(products => {
      let html = '';
      products.forEach(p => {
          // [개선] 백슬래시(\)를 붙여 서버 EL 평가를 건너뛰고 순수 JS 템플릿 리터럴로 전송
          html += `<li>\${p.name} - \${p.price}원</li>`;
      });
      document.getElementById('list').innerHTML = html;
  });
</script>
Review Case 3: 빈 컬렉션을 ${list != null}로만 검사하여 발생하는 빈 화면/테이블 렌더링 결함
🚨 발생 증상 (Trouble Scenario)
"서블릿에서 검색 결과가 없을 때 new ArrayList<>() 빈 리스트를 반환하여 request에 담았습니다. JSP에서 데이터가 있을 때만 테이블을 출력하려고 <c:if test="${list != null}">로 감쌌는데, 데이터가 0건인데도 테이블 헤더와 빈 테이블 프레임이 화면에 그대로 노출됩니다. 원인이 무엇일까요?" 
<!-- 서블릿: 조회 결과가 없으면 빈 리스트 전달 (List<Article> list = new ArrayList<>()) -->
<c:if test="${list != null}">
    <!-- 데이터가 없는데도 list 인스턴스 자체는 null이 아니므로 헤더가 렌더링됨 -->
    <table class="table">
        <tr><th>번호</th><th>제목</th><th>작성자</th></tr>
        <c:forEach items="${list}" var="article">
            <tr><td>${article.id}</td><td>${article.title}</td><td>${article.author}</td></tr>
        </c:forEach>
    </table>
</c:if>
<c:if test="${list == null}">
    <p>조회된 게시글이 없습니다.</p>
</c:if>
원인 분석 및 리팩토링 코드 확인
핵심 결함: 컬렉션 인스턴스 존재(null 여부)와 실제 요소 포함(isEmpty) 혼동
[원인 분석]
new ArrayList<>()로 생성된 빈 컬렉션은 힙 메모리에 인스턴스가 존재하므로 null이 아닙니다.
따라서 ${list != null} 평가는 항상 true가 되어 원치 않는 빈 테이블 헤더가 렌더링됩니다.
EL의 empty 연산자는 객체의 null 여부뿐 아니라 Collection.isEmpty()(size == 0)까지 동시에 안전하게 검사하므로, 컬렉션 검사에는 반드시 empty를 사용해야 합니다.
Refactored Code (개선 코드) 
<!-- [개선] EL의 empty 연산자를 활용하여 null 및 빈 컬렉션을 한 번에 분기 -->
<c:choose>
    <c:when test="${!empty list}">
        <table class="table">
            <tr><th>번호</th><th>제목</th><th>작성자</th></tr>
            <c:forEach items="${list}" var="article">
                <tr><td>${article.id}</td><td>${article.title}</td><td>${article.author}</td></tr>
            </c:forEach>
        </table>
    </c:when>
    <c:otherwise>
        <p>조회된 게시글이 없습니다.</p>
    </c:otherwise>
</c:choose>
Review Case 4: boolean 프로퍼티 접두사(is) 중복 호출로 발생한 PropertyNotFoundException 500 장애
🚨 발생 증상 (Trouble Scenario)
"회원 DTO에 탈퇴 여부를 나타내는 boolean isDeleted 필드가 있습니다. JSP에서 ${user.isDeleted}로 접근하여 상태를 표시하려 했는데, 페이지 로딩 시 Property [isDeleted] not found on type [UserDto]라는 500 에러가 발생했습니다. DTO 필드명 그대로 작성했는데 왜 이런 예외가 발생할까요?" 
// UserDto.java
public class UserDto {
    private boolean isDeleted;

    // 자바빈 규약에 따른 getter
    public boolean isDeleted() {
        return isDeleted;
    }
}

<!-- mypage.jsp: 탈퇴 여부 화면 노출 시도 -->
<p>계정 상태: ${user.isDeleted ? '탈퇴 계정' : '정상 계정'}</p>
원인 분석 및 리팩토링 코드 확인
핵심 결함: JavaBeans 스펙의 boolean 프로퍼티 게터(getter) 명명 규칙 오해
[원인 분석]
자바빈즈 규약(JavaBeans Specification)에 따라 boolean 타입의 getter는 is[PropertyName]() 명명 규칙을 갖습니다.
즉, isDeleted() 메서드가 존재할 때 EL 엔진이 인식하는 실제 프로퍼티 이름은 deleted입니다.
JSP에서 ${user.isDeleted}라고 작성하면 EL의 BeanELResolver는 isIsDeleted() 또는 getIsDeleted()를 탐색하게 되며, 해당 메서드가 존재하지 않으므로 jakarta.el.PropertyNotFoundException 500 예외를 던집니다.
Refactored Code (개선 코드) 
<!-- [개선] 자바빈즈 프로퍼티 규약에 맞게 'deleted'로 접근 (내부적으로 isDeleted() 호출) -->
<p>계정 상태: ${user.deleted ? '탈퇴 계정' : '정상 계정'}</p>
Review Case 5: 쿼리스트링 파라미터를 EL 속성 스코프에서 찾아 값이 나오지 않는 결함
🚨 발생 증상 (Trouble Scenario)
"게시판 검색 후 URL이 /board/list?keyword=Java로 전달되었습니다. JSP 화면 상단에 '검색어: Java'를 표시하기 위해 ${keyword}로 작성했는데 아무 값도 출력되지 않고 빈 공백으로 나옵니다. 컨트롤러에서 setAttribute를 거치지 않은 요청 파라미터는 어떻게 꺼내야 할까요?" 
<!-- 브라우저 요청: /board/list?keyword=Java&page=1 -->
<div class="search-info">
    <!-- 속성(Attribute) 스코프를 탐색하므로 쿼리 파라미터가 검색되지 않음 -->
    <span>입력한 검색어: [${keyword}]</span>
</div>
원인 분석 및 리팩토링 코드 확인
핵심 결함: HttpServletRequest의 Parameter(요청 파라미터)와 Attribute(요청 속성) 구분 미흡
[원인 분석]
일반적인 ${keyword} 표기는 4대 웹 스코프(pageScope → requestScope → sessionScope → applicationScope)의 속성(Attribute) 저장소만 순차 탐색합니다.
URL 쿼리스트링이나 <form> 전송 데이터는 request.getParameter()로 얻는 파라미터(Parameter)이므로 기본 스코프 탐색 대상에 포함되지 않아 null(빈 공백)로 평가됩니다.
요청 파라미터에 접근할 때는 EL의 내장 객체인 param(또는 다중 값의 경우 paramValues)을 명시해야 합니다.
Refactored Code (개선 코드) 
<!-- [개선] EL 내장 객체 param을 사용하여 request.getParameter("keyword") 조회 -->
<div class="search-info">
    <span>입력한 검색어: [${param.keyword}]</span>
    <span>현재 페이지: ${param.page}</span>
</div>

Q1
EL에서 ${"10" + "20"} 표현식의 결과값은 문자열 "1020"이다. (O / X)
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: X (결과값: 30)
EL의 + 연산자는 문자열 결합을 지원하지 않고 무조건 숫자로 형변환하여 산술 덧셈을 수행하므로 정수 30이 반환됩니다. 문자열을 결합하려면 ${"10"}${"20"}처럼 나란히 작성해야 합니다.
Q2
EL에서 ${user.name}을 호출했을 때 내부적으로 자바빈(JavaBean) 규약에 따라 호출되는 자바 메서드는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: user.getName()
EL은 필드에 직접 접근하지 않고 getter 메서드를 자동 호출합니다. (boolean 프로퍼티의 경우 isName() 호출)
Q3
스코프를 명시하지 않고 ${data}로 접근할 때, EL 엔진이 가장 먼저 검색하는 스코프 영역은?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: pageScope (페이지 스코프)
탐색 우선순위는 pageScope → requestScope → sessionScope → applicationScope 순서로 작은 범위부터 확장됩니다.
Q4
Jakarta EE 10+ (JSTL 3.0) 환경에서 JSTL Core 태그라이브러리를 선언할 때 지정해야 하는 최신 표준 URI는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: jakarta.tags.core
과거 Java EE 시절의 http://java.sun.com/jsp/jstl/core 대신 최신 규격인 jakarta.tags.core를 사용해야 합니다.
Q5
JSTL에서 다중 조건 분기(if-else if-else)를 구성하는 최상위 컨테이너 태그는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: <c:choose>
<c:choose> 내부에서 <c:when test="...">로 조건을 검사하고 마지막 기본 분기는 <c:otherwise>로 처리합니다.
Q6
EL의 empty 연산자가 true로 판정하는 4가지 데이터 상태는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: null, 빈 문자열(""), 길이가 0인 배열, 비어있는 Collection/Map
객체가 null인 경우뿐 아니라 길이가 0이거나 비어있는 컬렉션까지 null-safe하게 검사할 수 있습니다.
Q7
<%@ include file="..."%> 지시자를 사용한 페이지 포함은 런타임이 아니라 JSP가 서블릿 자바로 변환되는 컴파일 시점에 물리적으로 병합된다. (O / X)
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: O (정적 include)
변환 시점에 소스코드가 합쳐져 하나의 단일 서블릿으로 생성되므로, header.jsp에 선언한 태그라이브러리나 EL 변수를 부모 페이지가 그대로 공유합니다.
Q8
클라이언트가 URL 쿼리스트링이나 폼으로 전송한 요청 데이터(String)와, 서블릿이 setAttribute()에 바인딩한 모델 객체(Object)에 각각 접근하기 위해 사용하는 EL 내장 객체는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: param (파라미터) / requestScope (요청 속성)
param은 request.getParameter()(String)를 조회하고, requestScope는 request.getAttribute()(Object)를 조회합니다.

Q1. JSP에서 Scriptlet(<% %>) 대신 EL과 JSTL을 사용하는 이유와 이점을 설명해 주세요. 답변 확인 ▼
[두괄식 결론]
JSP 화면에서 복잡한 자바 코드를 완전히 제거하고 순수 태그 기반 뷰를 완성하여, 관심사 분리와 유지보수성을 극대화하기 위해서입니다.
[핵심 이점 3가지]
1. 가독성 및 퍼블리셔 협업: <% %> 자바 문법 대신 HTML과 유사한 XML 태그(JSTL)와 간결한 ${}(EL)을 사용하여 디자이너 및 퍼블리셔와의 협업 효율이 대폭 향상됩니다.
2. Null-Safety: 스크립트릿에서 null 객체의 메서드를 호출하면 NullPointerException이 발생하지만, EL은 null 데이터를 자동으로 빈 공백("")으로 처리하여 예외 없이 안전합니다.
3. 타입 캐스팅 생략: request.getAttribute()로 꺼낸 Object 타입을 자바빈 타입으로 일일이 강제 형변환할 필요 없이 getter 프로퍼티를 자동 호출합니다.

"EL에서 프로퍼티를 찾을 때 get 메서드가 없으면 어떻게 되나요?" → "PropertyNotFoundException 예외가 발생하므로, 반드시 자바빈 표준 네이밍 규약(getter/setter)을 준수해야 합니다."
Q2. EL의 스코프 탐색 우선순위 메커니즘과 명시적 스코프 지정이 필요한 이유를 설명해 주세요. 답변 확인 ▼
[두괄식 결론]
EL은 스코프 생명주기가 가장 좁은 영역부터 넓은 영역 순으로 자동 탐색하므로, 속성명 중복에 따른 데이터 오염을 방지하기 위해 명시적 스코프를 지정합니다.
[탐색 순서와 주의점]
EL은 ${data}를 만났을 때 pageScope → requestScope → sessionScope → applicationScope 순서로 탐색하며 가장 먼저 발견된 값을 반환합니다.
만약 세션에 담긴 로그인 사용자 정보와 이번 요청(request)에서 새로 조회한 정보의 속성명이 동일하다면, 의도치 않은 상위 스코프의 데이터가 덮어씌워져 출력될 수 있습니다. 따라서 스코프가 충돌할 여지가 있는 데이터는 ${requestScope.data}처럼 명시적으로 스코프 객체를 선언해야 안전합니다.
🎯 꼬리 질문 대비
"param과 requestScope의 차이는 무엇인가요?" → "param은 클라이언트가 쿼리스트링이나 폼으로 전송한 요청 파라미터(String)를 가리키고, requestScope는 서버 내부에서 request.setAttribute()로 저장한 자바 객체(Object)를 가리킵니다."
Q3. EL 표현식(${user.name})이 DTO의 private 필드 데이터를 화면에 출력하는 내부 메커니즘과, DTO에 getter 메서드가 반드시 존재해야 하는 이유를 설명해 주세요. 답변 확인 ▼
[두괄식 결론]
EL 엔진은 자바 리플렉션과 자바빈(JavaBeans) 규약에 따라 내부적으로 getter 메서드(getName())를 호출하여 값을 읽어오므로, 객체지향 캡슐화를 유지하면서 프로퍼티를 조회하기 위해 getter가 필수적입니다.
[내부 동작 메커니즘과 필수 이유]
• BeanELResolver의 프로퍼티 탐색: EL은 ${user.name}을 만났을 때 DTO의 private 필드에 직접 접근하지 않습니다. 내부의 BeanELResolver가 Java Reflection을 통해 get + Name()(boolean 타입의 경우 is + Name()) 형태의 getter 메서드를 찾아 동적으로 호출합니다.
• Getter 부재 시 500 장애: 만약 DTO에 getter가 누락되어 있다면 필드를 읽을 수 있는 공식 통로가 없으므로 jakarta.el.PropertyNotFoundException 예외가 발생하며 페이지 렌더링이 중단됩니다.
• 캡슐화 준수: 뷰(JSP) 영역이 모델(DTO)의 내부 필드 구현에 직접 결합되지 않고, getter 인터페이스를 통해서만 안전하게 데이터를 조회할 수 있도록 보장합니다.
🎯 꼬리 질문 대비
"Java 16+의 Record 객체를 DTO로 넘기면 EL에서 동작하나요?" → "Record는 getName()이 아닌 name() 메서드를 갖지만, 최신 Jakarta EL(Servlet 6.0+) 엔진은 Record 클래스를 인식하여 ${user.name} 호출 시 name() 메서드를 정상적으로 호출해 줍니다."
