서블릿 심화: Front Controller, Filter, Listener & 멀티스레드 핵심 요약

개별 서블릿 1:1 매칭의 한계를 극복하는 Front Controller 패턴부터, 규칙 기반 부가 기능 제어(Filter), 애플리케이션 라이프사이클 모니터링(Listener), 멀티스레드 동시성 및 공유 자원 제어까지 교안의 핵심을 체계적으로 복습합니다.

1. 기존 서블릿 방식의 한계와 Front Controller 패턴

기존 1:1 서블릿 매칭의 문제점
문제 1
서블릿 수의 폭증
요청마다 새로운 서블릿이 1:1로 필요하여 클래스 상속 및 메서드 재정의 루틴이 반복됨
문제 2
공통 로직 중복
로깅, 예외 처리, 인코딩 설정, 인증 검사 등 공통 작업이 각 서블릿마다 분산되어 중복 발생
문제 3
유지보수성 저하
전체 요청 처리 흐름이 산발적으로 흩어져 애플리케이션의 개발 생산성과 가독성이 급격히 저하됨
Front Controller 패턴의 장점

Front Controller란: 전면에서 모든 클라이언트 요청을 대표로 받아들이는 단일 창구 서블릿입니다.

장점 세부 내용
단일 진입점 모든 요청을 Front Controller에서 접수하므로 전체 요청 흐름의 일관성 보장
공통 처리 일원화 로깅, 파라미터 사전 분석, 응답 인코딩, 보안 검사 등 필요한 전/후 작업을 일괄 처리
유연한 확장성 신규 기능 추가 시 새로운 서블릿을 등록하지 않고 기존 구조 내에서 쉽게 확장 가능
코드 간결성 서블릿 개수가 대폭 감소하며, 비즈니스 로직은 일반 클래스(POJO Controller)나 메서드로 깔끔하게 위임

2. 요청 구분 방식과 URL 매핑 우선순위

Front Controller에서 요청을 식별하는 2가지 방식
Case 1
URL 파라미터 기반
URL에 작업 식별용 파라미터(ex: action) 추가
/main?action=gugu&dan=3
/main?action=login
Case 2
와일드카드 URL 매핑
경로 또는 확장자 기반으로 패턴 매핑
/main/* (도메인 경로)
*.do (확장자 매핑)
/ (기본 디폴트 매핑)
와일드카드 URL 매핑 특성과 우선순위
URL 매핑 패턴 특성 및 식별 방식 주의사항 및 비고
1. 정확한 매핑
/main/hello		 지정된 경로와 정확히 일치하는 요청만 수신 우선순위가 가장 높음
2. 경로 매핑
/main/*, /board/*		 도메인 경로 아래의 모든 요청 접수
→ request.getPathInfo()로 하위 세부 경로 파악		 ⚠️ /* 형태로 선언 시 정적 리소스(CSS, 이미지)까지 흡수하는 블랙홀 문제 발생!
3. 확장자 매칭
*.do, *.action		 특정 확장자 기반 요청 처리 (경로 무관)
→ request.getServletPath()로 호출 경로 파악		 경로 구분자 /를 함께 결합할 수 없음 (ex: /main/*.do 불가)
4. 디폴트 매핑
/		 앞선 규칙에 매핑되지 않은 모든 요청 처리 기본 정적 리소스 처리 재정의 필요 (Spring MVC 기본 매핑 방식)
Front Controller 구현 패턴 (ControllerHelper)
// 공통 인터페이스: 로깅, 파라미터 추출, 공통 응답 처리 default 메서드 제공
public interface ControllerHelper {
    default String getActionParameter(HttpServletRequest req, HttpServletResponse resp) {
        System.out.printf("##요청 경로: %s, 요청 방식: %s##\n", req.getRequestURI(), req.getMethod());
        String action = req.getParameter("action");
        return (action == null || action.isBlank()) ? "index" : action;
    }

    default void responseHtml(String title, String content, HttpServletResponse resp) throws IOException {
        resp.setContentType("text/html;charset=UTF-8");
        resp.getWriter().write("<html><body><h1>%s</h1>%s</body></html>".formatted(title, content));
    }
}

@WebServlet("/main")
public class MainController extends HttpServlet implements ControllerHelper {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String action = getActionParameter(req, resp);
        switch (action) {
            case "gugu" -> gugu(req, resp);
            default     -> responseHtml("메인", "환영합니다", resp);
        }
    }
}

3. Filter와 Filter Chain

Filter의 개념과 도입 배경

여러 컨트롤러에 부분적으로 필요한 공통 기능(로그인 인증, CSRF 방어, XSS 방지, 인코딩 변환 등)은 상속이나 클래스 계층 구조로 모듈화하기 어렵습니다. 따라서 특정 URL 규칙을 기반으로 요청/응답을 가로채는 Filter를 사용합니다.

정의
Filter란?
서블릿/JSP 등 웹 컴포넌트가 실행되기 전/후에 요청과 응답을 가로채서 부가적인 기능을 수행하는 웹 컴포넌트
연결
Filter Chain
여러 필터가 체인 형태로 연결되어 순차적으로 전처리 수행 후 서블릿 실행, 다시 역순으로 후처리 수행
주요 용도
적용 분야
• 인증/권한 검사 (비로그인 차단)
• 요청/응답 로깅
• 보안 (XSS 방지, 입력값 검증)
Filter 생명주기와 구현 흐름
@WebFilter(dispatcherTypes = { DispatcherType.REQUEST }, urlPatterns = { "/*" })
public class PerformanceFilter extends HttpFilter implements Filter {
    @Override
    public void init(FilterConfig filterConfig) throws ServletException {
        // 필터 객체 생성 시 1회 초기화
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        
        // 1. 전처리 (요청 가로채기): 서블릿 실행 전 로직
        long start = System.currentTimeMillis();

        // 2. 체인 진행: 다음 필터 또는 대상 서블릿으로 제어 전달 (필수 호출!)
        chain.doFilter(request, response);

        // 3. 후처리 (응답 가로채기): 서블릿 실행 후 응답 반환 시 로직
        long end = System.currentTimeMillis();
        System.out.println("소요 시간: " + (end - start) + "ms");
    }

    @Override
    public void destroy() {
        // 필터 소멸 시 1회 자원 정리
    }
}

• 등록 방법: @WebFilter 애너테이션 또는 web.xml의 <filter>, <filter-mapping> 선언
• DispatcherType: 필터가 적용될 시점 지정 (기본값: REQUEST - 클라이언트 직접 요청 시)

4. XSS 공격 방어와 HttpServletRequestWrapper

XSS(Cross-Site Scripting) 방어 원리

사용자 입력값에 악의적인 스크립트 코드(<script> 등)가 포함되어 웹 페이지에 렌더링될 때 브라우저에서 실행되는 보안 취약점입니다.
이를 방지하기 위해 입력 문자열에서 < → &lt;, > → &gt; 등으로 HTML 엔티티 치환을 수행해야 합니다.

HttpServletRequestWrapper를 활용한 요청 래핑

HttpServletRequest의 파라미터는 읽기 전용이므로 직접 수정할 수 없습니다. 따라서 HttpServletRequestWrapper를 상속하여 getParameter() 메서드를 재정의하고, 필터에서 래퍼 객체로 교체하여 체인에 전달합니다. 

// 1. 파라미터 값을 가공하는 RequestWrapper 작성
public class XssRequestWrapper extends HttpServletRequestWrapper {
    public XssRequestWrapper(HttpServletRequest request) {
        super(request);
    }

    @Override
    public String getParameter(String name) {
        String value = super.getParameter(name);
        if (value != null) {
            value = value.replace("<", "&lt;").replace(">", "&gt;");
        }
        return value;
    }
}

// 2. 필터에서 래퍼 객체로 감싸서 다음 컴포넌트로 전달
@WebFilter("/*")
public class XssRequestFilter extends HttpFilter implements Filter {
    @Override
    public void doFilter(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        chain.doFilter(new XssRequestWrapper(request), response);
    }
}

5. Listener와 애플리케이션 이벤트 모니터링

웹 애플리케이션 이벤트 감시자 (Listener)

웹 애플리케이션의 특정 라이프사이클 이벤트(컨텍스트 생성/소멸, 세션 생성/소멸 등)가 발생할 때 자동으로 호출되는 모니터링 객체입니다.

리스너 인터페이스 주요 역할 및 활용 사례
ServletContextListener 웹 애플리케이션(Context)의 생성(시작) 및 소멸(종료) 시점 모니터링
• contextInitialized(ServletContextEvent sce): 서버 구동 시 개별 서블릿 동작 전에 초기화 비용이 큰 공유 자원(DB 커넥션 풀 등)의 일괄 초기화에 주로 사용
• contextDestroyed(ServletContextEvent sce): 서버 종료 시 자원 안전 반납 
@WebListener
public class MyContextListener implements ServletContextListener {
    @Override
    public void contextInitialized(ServletContextEvent sce) {
        System.out.println("context 초기화: 애플리케이션 전체 초기화 및 무거운 공유 자원 준비");
    }

    @Override
    public void contextDestroyed(ServletContextEvent sce) {
        System.out.println("context 소멸: 점유 자원 해제 및 정리");
    }
}

• 등록 방식: 클래스 상단 @WebListener 또는 web.xml의 <listener> 선언

6. Servlet과 Multi-Thread (공유 자원과 동시성)

서블릿 멀티스레드 모델과 데이터 보호

서블릿은 하나의 객체만 생성(싱글톤)되어 멀티스레드에 의해 공유됩니다. 따라서 서블릿은 Thread-Safe하지 않습니다.

기법 1
뮤텍스 (Mutex)
공유 구역에 들어갈 수 있는 통로가 단 하나 (자리가 1개뿐인 화장실과 열쇠 1개)
ex: synchronized 블록
기법 2
세마포어 (Semaphore)
공유 구역에 들어갈 수 있는 통로가 여러 개 (자리가 여러 개인 유료 주차장과 주차권)
ex: Connection Pool
⚠️ 서블릿 동시성 제어의 핵심 결론:
서블릿 내부에서 synchronized 키워드로 동기화하면 데이터는 보호할 수 있으나, 모든 요청 스레드가 줄을 서서 대기하므로 멀티스레드 동시 처리 성능이 급락합니다.
따라서 "가급적 서블릿에는 멤버 변수를 통해 상태를 관리하지 않는다(무상태/Stateless 원칙)"가 웹 서버 아키텍처의 필수 규칙입니다.
Review Case 1: 필터 적용 후 브라우저가 무한 대기하거나 빈 화면만 반환되는 장애
🚨 발생 증상 (Trouble Scenario)
"요청 실행 시간을 측정하기 위해 신규 필터를 구현하여 배포했습니다. 그런데 웹 사이트 접속 시 서블릿이 전혀 실행되지 않고 브라우저에 빈 화면(White Page)만 나타납니다. 코드를 보고 원인을 찾아보세요." 
@WebFilter("/*")
public class LoggingFilter extends HttpFilter implements Filter {
    @Override
    public void doFilter(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        
        System.out.println("요청 접수: " + request.getRequestURI());
        
        long start = System.currentTimeMillis();
        long end = System.currentTimeMillis();
        System.out.println("소요 시간: " + (end - start) + "ms");
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: 필터 체인 중단
[원인 분석]
필터는 다음 필터나 최종 대상 서블릿으로 요청을 전달하기 위해 반드시 chain.doFilter(request, response)를 호출해야 합니다.
코드에서 chain.doFilter(...) 호출이 누락되어 제어가 서블릿으로 넘어가지 못하고 필터 내부에서 요청 처리가 끝나버려 브라우저에 아무런 응답도 전송되지 않았습니다.
Refactored Code (개선 코드) 
@WebFilter("/*")
public class LoggingFilter extends HttpFilter implements Filter {
    @Override
    public void doFilter(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        
        System.out.println("요청 접수: " + request.getRequestURI());
        long start = System.currentTimeMillis();

        // 다음 필터 또는 서블릿으로 제어를 정상 전달
        chain.doFilter(request, response);

        long end = System.currentTimeMillis();
        System.out.println("소요 시간: " + (end - start) + "ms");
    }
}

Review Case 3: 동시성 보호를 위해 synchronized를 적용한 후 시스템 마비
🚨 발생 증상 (Trouble Scenario)
"방문자 수 카운터의 동시성 오류를 막기 위해 doGet 메서드에 synchronized 키워드를 붙여 배포했습니다. 그런데 동시 접속자가 50명만 넘어가도 전체 사용자의 응답 시간이 10초 이상 지연되며 서버가 사실상 마비되었습니다. 왜 그럴까요?" 
@WebServlet("/main")
public class MainController extends HttpServlet {
    private long visitCount = 0;

    @Override
    protected synchronized void doGet(HttpServletRequest req, HttpServletResponse resp) 
            throws ServletException, IOException {
        
        visitCount++;
        // 무거운 비즈니스 로직 연산 및 DB 조회 수행...
        resp.getWriter().println("방문자 수: " + visitCount);
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: 성능 급락 안티패턴
[원인 분석]
서블릿은 싱글톤 인스턴스 1개만 존재합니다. 여기에 synchronized를 걸면 수많은 클라이언트 요청 스레드가 병렬로 처리되지 못하고 단 하나의 스레드만 메서드를 실행하는 직렬(Queue) 대기 상태가 됩니다.
웹 서버의 가장 큰 장점인 멀티스레드 동시 처리 능력이 상실되므로, 서블릿 메서드 자체에 동기화를 거는 것은 심각한 안티패턴입니다.
Refactored Code (개선 코드) 
@WebServlet("/main")
public class MainController extends HttpServlet {
    // [개선] 서블릿은 무상태(Stateless)로 유지하며, 필수 카운터는 Atomic 클래스 활용
    private final AtomicLong visitCount = new AtomicLong(0);

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) 
            throws ServletException, IOException {
        
        long count = visitCount.incrementAndGet();
        // synchronized 없이 병렬로 안전하고 빠르게 실행
        resp.getWriter().println("방문자 수: " + count);
    }
}
Review Case 4: 필터에서 파라미터 값 변경 불가로 인한 XSS 치환 실패
🚨 발생 증상 (Trouble Scenario)
"XSS 공격을 막기 위해 필터에서 파라미터 값을 꺼내 < 태그를 &lt;로 치환한 뒤 다시 request에 세팅하려고 했으나 컴파일 에러가 발생하거나 서블릿에 원래의 위험한 악성 스크립트가 그대로 전달됩니다. 왜 그럴까요?" 
@WebFilter("/*")
public class BadXssFilter extends HttpFilter implements Filter {
    @Override
    public void doFilter(HttpServletRequest request, HttpServletResponse response, FilterChain chain) 
            throws IOException, ServletException {
        
        String raw = request.getParameter("content");
        if (raw != null) {
            String clean = raw.replace("<", "&lt;");
            // request에는 setParameter() 메서드가 존재하지 않아 수정 불가능!
        }
        chain.doFilter(request, response);
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: Request 객체 불변성 위반
[원인 분석]
HttpServletRequest의 파라미터 맵은 컨테이너가 불변(Immutable) 상태로 캡슐화하여 setParameter() 같은 수정 API를 제공하지 않습니다.
따라서 파라미터 값을 가공하려면 HttpServletRequestWrapper를 상속받아 getParameter()를 오버라이드한 후, 이 래퍼 인스턴스를 체인에 전달해야 합니다.
Refactored Code (개선 코드) 
public class XssRequestWrapper extends HttpServletRequestWrapper {
    public XssRequestWrapper(HttpServletRequest request) { super(request); }

    @Override
    public String getParameter(String name) {
        String val = super.getParameter(name);
        return (val != null) ? val.replace("<", "&lt;").replace(">", "&gt;") : null;
    }
}

@WebFilter("/*")
public class XssFilter extends HttpFilter implements Filter {
    @Override
    public void doFilter(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        // 래퍼 객체를 전달하여 투명하게 치환 처리
        chain.doFilter(new XssRequestWrapper(request), response);
    }
}

웹 애플리케이션의 시작과 종료 라이프사이클 이벤트를 감지하여 전체 애플리케이션 수준의 공통 자원을 초기화/해제하는 리스너입니다.
[서블릿 init() 대비 이점]
개별 서블릿의 init()은 해당 서블릿이 처음 호출될 때 실행되므로, DB 커넥션 풀 등 초기화 비용이 큰 무거운 자원을 서블릿에 두면 첫 번째 사용자의 응답 지연이 심해집니다.
반면 ServletContextListener의 contextInitialized()는 서버 기동 시점(어떤 서블릿도 호출되기 전)에 실행되므로, 애플리케이션 전체에서 공유할 자원을 미리 안전하게 준비할 수 있습니다.

Q5. 서블릿 동시성 제어 시 synchronized 메서드를 지양하고 무상태(Stateless) 설계를 권장하는 이유는 무엇인가요? 답변 확인 ▼
[두괄식 결론]
서블릿은 싱글톤으로 운영되므로 메서드에 synchronized를 적용하면 동시 요청이 직렬화되어 대규모 트래픽 처리 성능이 치명적으로 저하되기 때문입니다.
[아키텍처 원칙]
수천 명의 동시 사용자를 처리해야 하는 웹 애플리케이션에서 스레드가 락(Lock)을 획득하기 위해 대기하면 심각한 병목(Bottleneck)이 발생합니다.
따라서 서블릿 인스턴스 필드(멤버 변수)에 상태를 두지 않고, 모든 요청 데이터는 메서드 내부의 지역 변수(Local Variable)나 request 스코프에 격리하여 스레드 간 간섭이 없는 무상태(Stateless) 아키텍처를 유지해야 합니다.
