Backend Programming • Servlet-1

서블릿(Servlet) 기초 및 백엔드 아키텍처 핵심 요약

3-Tier 아키텍처, WAS와 컨테이너, Maven 빌드 관리, 서블릿 생명주기 및 요청/응답 API까지 교안의 핵심 내용을 체계적으로 복습하고 실전 코드 리뷰와 면접 훈련을 진행합니다.

1. 웹 프로그램과 3-Tier 아키텍처

3-Tier 아키텍처: Frontend • Backend • Database 계층 분리 운영

웹 프로그램은 네트워크 너머의 서버에 존재하며 웹을 통해 서비스되는 시스템으로, 역할과 책임에 따라 Frontend, Backend, Database 3대 계층(Tier)으로 분리하여 개발 및 운영됩니다.

Tier 1 • Frontend
Presentation Tier (표현 계층)
• 구성: 웹 브라우저, Web Server (Apache, Nginx)
• 기술: HTML(구조), CSS(디자인), JS(상호작용)
• 역할: 사용자 인터페이스(UI/UX) 제공 및 정적 리소스 즉시 전송
Tier 2 • Backend
Application Tier (로직 계층)
• 구성: WAS (Tomcat 등 서블릿 컨테이너)
• 기술: Java, Servlet, JSP, Spring, REST API
• 역할: 동적 요청 처리, 핵심 비즈니스 로직 연산, 트랜잭션 및 인증 제어
Tier 3 • Database
Data Tier (영속 계층)
• 구성: DBMS (MySQL, Oracle, PostgreSQL 등)
• 기술: SQL, JDBC, MyBatis, JPA
• 역할: 비즈니스 데이터의 영속성(Persistence) 보장, 데이터 CRUD 및 무결성 관리
계층 구분 대표 컴포넌트/서버 주요 사용 기술 핵심 책임 및 처리 대상
Frontend
(Presentation Tier)		 웹 브라우저 (Client)
+ Web Server		 HTML5, CSS3, JavaScript, Web Server 사용자 화면 렌더링, 사용자 입력 및 이벤트 감지, 정적 리소스(HTML, CSS, 이미지) 고속 캐싱 및 응답
Backend
(Application Tier)		 Web Application Server (WAS)
(Tomcat / Servlet Container)		 Java, Servlet API, JSP, Business Service 클라이언트의 동적 요청 처리, 비즈니스 로직 연산, 데이터베이스 연동 및 동적 뷰/데이터(JSON) 생성
Database
(Data Tier)		 DBMS
(MySQL, Oracle 등)		 SQL, JDBC, 커넥션 풀(DBCP) 데이터의 영속성(Persistence) 관리, 트랜잭션(ACID) 제어, 대용량 데이터 질의 및 무결성 보장
💡 3-Tier 계층 분리의 핵심 이점: 각 계층이 독립된 물리적/논리적 인프라에서 실행되므로 모듈 간 결합도가 낮아집니다. 따라서 다른 계층에 영향을 주지 않고 특정 계층만 개별 개발·배포·스케일아웃(확장)이 가능하여 대규모 서비스 운영 및 유지보수에 매우 유리합니다.

요청 URL 체계 구조 분석
# 요청 주소 체계 및 계층 분해 (각 항목 중앙 매핑)
http://localhost:8080/BE_01/index.html
   │       │      │     │       │
   │       │      │     │       └─ URL Mapping (개별 서블릿 또는 요청 리소스 식별 경로)
   │       │      │     └───────── Context Root (웹 애플리케이션 격리/배포 경로: 기본 프로젝트명)

• Context Root   : /BE_01/ (컨테이너 내에서 개별 프로젝트가 실행되는 기본 경로)

4. 서블릿(Servlet)의 특징과 URL 매핑

서블릿의 정의 및 주요 장단점
구분 세부 내용
Servlet이란? WAS에서 실행되는 Java Web Component (jakarta.servlet.http.HttpServlet 상속)
주요 장점 • Java OOP 기반: 플랫폼 독립적이며 유지보수성 및 재활용성 우수
• 높은 성능: 하나의 서블릿 객체만 생성(싱글톤)하며 멀티스레딩을 지원하여 요청의 동시 처리 가능
• 확장성: 필터(Filter)를 통한 전/후처리, 리스너(Listener) 이벤트 제어, 프레임워크와 통합 용이
주요 단점 비즈니스 로직과 프리젠테이션 로직(HTML 코드)이 섞여서 나타남 → Servlet + JSP의 Model 2 방식으로 처리
서블릿 등록 및 URL 매핑 방식 2가지
1) 애너테이션 방식 (Servlet 3.0+ 권장)

서블릿 클래스 선언부에 @WebServlet 애너테이션을 선언하여 매핑. 별도의 XML 작성 없이 자바 소스코드 내에서 직관적으로 관리 (실무 표준)

2) web.xml 배포 서술자 방식

<servlet>과 <servlet-mapping> 태그를 활용하여 XML에 서블릿 이름과 URL 패턴을 매핑 (자바 컴파일 없이 설정 교체 가능)

@WebServlet 애너테이션 주요 속성
속성 (Attribute) 타입 (Type) 설명 및 작성 규칙
urlPatterns / value String[] 서블릿에 매핑할 요청 URL 경로 목록 (필수).
• 기본 속성이므로 @WebServlet("/hello")처럼 속성명 생략 가능
• 복수 경로 지정 시 urlPatterns = {"/hello", "/hi"}로 작성
• 경로 규칙: 반드시 '/'로 시작해야 함
loadOnStartup int 서블릿 사전 로딩 우선순위. 기본값(-1)은 최초 요청 시 생성되지만, 0 이상의 양수를 지정하면 WAS 기동 시 즉시 로드되어 init()을 선제 호출
initParams WebInitParam[] 서블릿 초기화 시 전달할 설정 파라미터(@WebInitParam(name="key", value="val")) 지정
경로의 종류와 '/'의 차이점 (Container Root vs Context Root)
Container root 컨테이너의 경로
  • 기준 시점: Servlet 배우기 전에 사용했던 '/'는 container root
  • 해당 경로: <a>, <link>, <form>, <script>의 경로 등 (브라우저 기준 http://localhost:8080/)
  • 주의사항: 특정 context를 호출하기 위해서는 /context_name/ 처럼 context_name을 반드시 개입시켜야 함
Context root 개별 Context 경로
  • 기준 시점: servlet을 배우고 나서 배우는 경로는 '/'가 context root
  • 해당 경로: servlet url mapping (@WebServlet), web.xml의 경로, include-directive의 경로 등
  • 특징: 현재 애플리케이션 내부를 기준으로 하므로 context name을 제외하고 /hello처럼 직접 매핑

5. 서블릿 생명주기(Life Cycle) 관리

컨테이너에 의한 라이프사이클 제어

개발자는 Servlet을 만들지만 객체를 만들거나 호출하지 않음 → Container가 life cycle에 따라 관리하며, 개발자가 작성한 각 라이프사이클 훅을 Container가 호출합니다.

최초 1회
1. init()
서블릿 객체 생성 후 최초 1회 호출되어 초기화 작업 수행
매 요청마다
2. service()
요청마다 호출되어 HTTP 요청 방식을 판단하고 doGet() 또는 doPost() 호출
종료 시 1회
3. destroy()
컨테이너가 종료되거나 서블릿이 소멸될 때 호출되어 자원 정리 수행

6. HttpServletRequest & HttpServletResponse 및 처리 흐름

HTTP Request와 Response 추상화 인터페이스
인터페이스 핵심 개념 및 특징 주요 메서드 및 설명
HttpServletRequest HTTP 요청 추상화 (헤더, 파라미터, 속성 및 요청 본문 접근)
• HTTP Method: form 데이터 전달 방식 결정 (GET: 멱등, POST: 비멱등)
• Request parameter: 언제나 문자열(String), 클라이언트 설정 후 조작 불가		 • request.getParameter(name): 단일 값 조회
• request.getParameterValues(name): 복수 값 배열 조회
• request.getParameterMap(): 전체 파라미터 맵 조회
• request.getMethod(), request.getContextPath()
HttpServletResponse HTTP 응답 추상화 (헤더 조회/설정, 응답 상태, 응답 전송 처리)
• Http Status: 처리 결과 카테고리별 숫자 코드 반환
• Content-Type: 데이터 형식 사전 안내
• Character Encoding: 기본 ISO-8859-1 → UTF-8 필요		 • response.setContentType("text/html;charset=UTF-8"): 출력 스트림 생성 전에 설정 필수!
• response.getWriter(): PrintWriter 획득 후 append/println 수행
• response.setStatus(code)
서블릿 표준 구조 및 요청 처리 5단계 흐름
@WebServlet(description = "계산기 서블릿", urlPatterns = { "/calc" })
public class AddServlet extends HttpServlet {

    @Override
    public void init() throws ServletException {
        // [Lifecycle] 서블릿 인스턴스 생성 후 최초 1회 호출 (초기화 및 자원 준비)
        System.out.println("AddServlet init() 초기화 완료");
    }

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        // 1. 요청 파라미터 조회 (logging 및 validation 포함)
        String sNum1 = request.getParameter("num1");
        String sNum2 = request.getParameter("num2");

        // 2. 요청에 대한 business logic 처리
        int result = Integer.parseInt(sNum1) + Integer.parseInt(sNum2);

        // 3. 필요 시 persistence logic 연동 (DB 저장/조회 등)

        // 4. 응답 준비: content type 및 encoding 설정 (출력 전 설정 필수!)
        response.setContentType("text/html;charset=UTF-8");

        // 5. 응답을 위한 presentation logic 처리
        PrintWriter out = response.getWriter();
        out.append("<html><body><h2>결과: " + result + "</h2></body></html>");
    }

    @Override
    public void destroy() {
        // [Lifecycle] 컨테이너 종료 또는 서블릿 소멸 시 1회 호출 (자원 해제 및 정리)
        System.out.println("AddServlet destroy() 자원 정리 완료");
    }
}
Review Case 1: 동시 접속 부하 테스트 중 타인의 개인정보가 노출되는 사고
🚨 발생 증상 (Trouble Scenario)
"부하 테스트를 진행하던 중, 사용자 '철수'가 로그인하여 마이페이지를 조회했는데 화면에 엉뚱하게 사용자 '영희'의 이름과 방문 횟수가 노출되는 심각한 데이터 오염 사고가 발생했습니다. 코드를 보고 원인을 찾아보세요." 
@WebServlet("/visit")
public class VisitServlet extends HttpServlet {
    private int visitCount = 0;
    private String lastUser = "";

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        lastUser = request.getParameter("name");
        visitCount++;

        response.setContentType("text/html;charset=UTF-8");
        PrintWriter out = response.getWriter();
        out.println("<p>환영합니다, " + lastUser + "님!</p>");
        out.println("<p>누적 방문: " + visitCount + "</p>");
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: 치명적 동시성 결함
[원인 분석]
서블릿 컨테이너는 메모리 절약과 고성능을 위해 서블릿 객체를 단 하나만 생성(싱글톤)하여 모든 요청 스레드가 공유합니다.
인스턴스 변수인 lastUser는 모든 스레드가 동시에 읽고 쓰므로, 철수의 요청 스레드가 변수에 값을 넣고 출력하기 직전에 영희의 요청 스레드가 값을 덮어써 버리는 Race Condition(경쟁 상태)이 발생했습니다.
Refactored Code (개선 코드) 
@WebServlet("/visit")
public class VisitServlet extends HttpServlet {
    private final AtomicInteger visitCount = new AtomicInteger(0);

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        String currentUser = request.getParameter("name");
        int currentCount = visitCount.incrementAndGet();

        response.setContentType("text/html;charset=UTF-8");
        PrintWriter out = response.getWriter();
        out.println("<p>환영합니다, " + currentUser + "님!</p>");
        out.println("<p>누적 방문: " + currentCount + "</p>");
    }
}
Review Case 2: 브라우저 화면에 한글이 전부 ??? 로 깨져 나오는 장애
🚨 발생 증상 (Trouble Scenario)
"분명히 코드에 setContentType과 charset=UTF-8을 명시해 두었는데도, 사용자의 브라우저 화면에는 '안녕하세요' 대신 '???' 문자가 깨져서 출력됩니다. 왜 그럴까요?" 
@WebServlet("/greet")
public class GreetServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        PrintWriter out = response.getWriter();

        response.setContentType("text/html;charset=UTF-8");
        out.println("<h1>안녕하세요! 서블릿 서비스입니다.</h1>");
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: 응답 스트림 순서 버그
[원인 분석]
response.getWriter()를 호출하는 시점에 서블릿 컨테이너는 당시 설정된 문자 인코딩(기본값 ISO-8859-1)으로 고정하여 출력 스트림 객체를 생성합니다.
스트림이 이미 생성된 뒤에 setContentType(...)을 호출하더라도 이미 만들어진 스트림의 인코딩은 변경되지 않으므로 한글이 깨지게 됩니다.
Refactored Code (개선 코드) 
@WebServlet("/greet")
public class GreetServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        
        response.setContentType("text/html;charset=UTF-8");
        PrintWriter out = response.getWriter();

        out.println("<h1>안녕하세요! 서블릿 서비스입니다.</h1>");
    }
}
Review Case 3: 신규 서블릿 추가 후 서버 구동 시 배포 실패
🚨 발생 증상 (Trouble Scenario)
"새로운 기능 개발을 위해 서블릿을 작성하고 톰캣 서버를 기동했으나, 콘솔에 IllegalArgumentException: Invalid urlPatterns 오류가 발생하며 애플리케이션 배포가 전면 중단되었습니다. 어느 부분이 원인일까요?" 
@WebServlet(name = "UserServlet", urlPatterns = {"user/profile"})
public class UserServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        response.getWriter().println("User Profile");
    }
}
원인 분석 및 리팩토링 코드 확인
핵심 결함: 어노테이션 문법 누락
[원인 분석]
서블릿 공식 명세상 모든 서블릿 URL 패턴은 반드시 '/'(정확한 디렉터리 경로 매핑)로 시작하거나 '*.'(확장자 매핑)로 시작해야 합니다.
"user/profile"처럼 슬래시 없이 상대 경로 형식으로 지정하면 컨테이너가 배포 시점에 유효하지 않은 매핑으로 판단하고 즉시 구동을 거부합니다.
Refactored Code (개선 코드) 
@WebServlet(name = "UserServlet", urlPatterns = {"/user/profile"})
public class UserServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        response.getWriter().println("User Profile");
    }
}
Review Case 4: index.html에서 서블릿 호출 링크 클릭 시 404 Not Found 발생
🚨 발생 증상 (Trouble Scenario)
"컨텍스트 패스(Context Path)가 '/BE_01'인 웹 애플리케이션에서 서블릿 클래스는 @WebServlet('/hello')로 정상 매핑해 두었는데, index.html에서 <a href='/hello'>서블릿 호출</a> 링크를 클릭하면 브라우저에 404 Not Found 오류가 발생합니다. 왜 서블릿을 찾지 못할까요?" 
<a href="/hello">Hello 서블릿 호출</a>
원인 분석 및 리팩토링 코드 확인
핵심 결함: 경로 컨텍스트 누락
[원인 분석]
HTML 태그(<a>, <form>)에서 슬래시(/)로 시작하는 경로는 브라우저가 Container Root (http://localhost:8080/) 기준으로 해석합니다.
따라서 브라우저는 http://localhost:8080/hello로 요청을 보내게 되며, 애플리케이션의 Context Root(/BE_01)가 누락되어 톰캣이 해당 리소스를 찾지 못하고 404를 반환합니다.
Refactored Code (개선 코드) 
<!-- [개선 1] 컨텍스트 루트를 포함한 절대 경로 작성 -->
<a href="/BE_01/hello">Hello 서블릿 호출</a>

<!-- [개선 2] 현재 폴더 기준의 상대 경로 작성 -->
<a href="hello">Hello 서블릿 호출</a>

정답: http://localhost:8080/shop/order
전체 요청 URL은 http://[Container Root]/[Context Root]/[URL Mapping] 구조로 조합됩니다.
Q3
서블릿의 생명주기 메서드 중 서블릿 객체가 메모리에 로드된 후 초기화 작업을 위해 '최초 1회만' 호출되는 메서드는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: init()
init()은 서블릿 생성 직후 자원 준비를 위해 1회 호출되며, 요청 처리는 service()가 매번 호출되고, 소멸 시에는 destroy()가 호출됩니다.
Q4
정적 파일(HTML, CSS, JS, Image)은 반드시 WEB-INF 폴더 안에 위치시켜야 외부 웹 브라우저에서 직접 URL로 접근할 수 있다. (O / X)
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: X
WEB-INF 디렉터리는 보안 영역으로 브라우저에서 직접 URL로 접근할 수 없습니다. 브라우저가 직접 접근해야 하는 정적 리소스는 src/main/webapp/ 바로 아래에 위치시켜야 합니다.

단일 값은 getParameter()로 문자열을 수신하지만, 다중 값은 getParameterValues()를 통해 문자열 배열(String[])로 수신합니다.

Maven의 pom.xml에서 jakarta.servlet-api 의존성의 scope를 'provided'로 지정하는 이유는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: 톰캣(WAS) 런타임이 서블릿 라이브러리를 자체 제공하므로 패키징 충돌을 방지하기 위해
컴파일 시에는 서블릿 문법 검사를 위해 필요하지만, 최종 WAR 파일 패키징 시에는 컨테이너의 라이브러리와 중복되지 않도록 제외시키는 설정입니다.
Q7
HTTP Method 중 동일한 요청을 여러 번 전송하더라도 서버의 리소스 상태가 매번 동일하게 유지되는 특성을 무엇이라 하는가?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: 멱등성 (Idempotence)
GET, PUT, DELETE 등은 멱등한 메서드이며, 호출할 때마다 새로운 데이터가 생성되는 POST는 비멱등(Non-idempotent) 메서드입니다.

Q1. Web Server와 Web Application Server(WAS)의 차이점과, 둘을 연동하여 구성하는 이유를 설명해 주세요. 답변 확인 ▼
[두괄식 정의]
Web Server는 정적 콘텐츠를 신속하게 처리하는 서버이며, WAS는 서블릿 컨테이너를 내장하여 비즈니스 로직과 동적 데이터를 처리하는 서버입니다.
[연동하는 3대 핵심 이유]
1. 부하 분산: 이미지나 HTML 등 단순 정적 파일 요청을 앞단 웹 서버에서 즉시 응답함으로써, WAS가 값비싼 동적 연산과 DB 처리에만 스레드를 집중하도록 최적화합니다.
2. 보안 강화: WAS를 외부 인터넷에 직접 노출하지 않고 웹 서버를 리버스 프록시로 배치하여 내부 인프라 구조를 은닉합니다.
3. 무중단 배포: 앞단의 웹 서버가 로드밸런싱을 수행하여 여러 대의 WAS 인스턴스를 순차적으로 재시작할 수 있습니다.

Q2. 서블릿의 생명주기(Lifecycle)와 클라이언트 요청 처리 과정을 설명해 주세요. 답변 확인 ▼
[두괄식 정의]
서블릿은 컨테이너에 의해 생성 → 초기화(init) → 요청 처리(service) → 소멸(destroy)의 4단계를 거칩니다.
[구체적 동작 흐름]
클라이언트의 최초 요청 시 서블릿 클래스가 메모리에 로드되고 기본 생성자와 init() 메서드가 딱 한 번 호출됩니다. 이후 요청이 올 때마다 서블릿 컨테이너는 스레드 풀에서 작업 스레드를 할당하여 service()를 실행하고, 요청 메서드에 따라 doGet()이나 doPost()로 라우팅합니다. 서버가 종료되거나 컨텍스트가 리로드될 때 destroy()가 호출되어 자원을 정리합니다.
🎯 꼬리 질문 대비
"최초 요청 시 init()이 실행되면 첫 사용자의 응답 시간이 지연될 텐데 해결 방법이 있나요?" → "load-on-startup 속성(또는 @WebServlet(loadOnStartup = 1))을 설정하면 첫 요청 전 서버 기동 시점에 미리 서블릿을 초기화하여 응답 지연을 방지할 수 있습니다."
Q3. 서블릿에서 멤버 변수(인스턴스 필드)를 지양해야 하는 이유와 멀티스레드 안전성(Thread-Safety) 확보 방안은? 답변 확인 ▼
[두괄식 결론]
서블릿은 단일 인스턴스(싱글톤)로 생성되어 모든 요청 스레드가 공유하므로, 상태를 가지는 멤버 변수를 선언하면 동시성 문제(Race Condition)와 데이터 오염이 발생하기 때문입니다.
[안전한 설계 방안]
서블릿은 원칙적으로 무상태(Stateless)로 설계해야 합니다. 각 요청에서 발생하는 데이터는 doGet/doPost 메서드 내부의 지역 변수(Local Variable)로 선언하여 스레드별 독립적인 스택 메모리 영역에 격리해야 합니다. 상태 유지가 필요한 경우라면 HttpServletRequest나 HttpSession 스코프 객체를 활용해야 합니다.
🎯 꼬리 질문 대비
"동기화(synchronized) 블록을 적용하면 멤버 변수도 안전하게 쓸 수 있지 않나요?" → "안전성은 확보할 수 있으나 모든 요청이 직렬화(병목)되어 멀티스레드 기반 웹 서버의 동시 처리 성능이 급격히 저하되므로 웹 환경에서는 권장하지 않습니다."
Q4. HTML에서 작성하는 '/' 경로와 서블릿 매핑의 '/' 경로의 차이점을 설명해 주세요. 답변 확인 ▼
[두괄식 결론]
해석 주체가 브라우저냐 WAS냐에 따라 루트의 기준이 완전히 다릅니다.
[상세 차이점]
HTML 태그(<a>, <form>)에서 사용하는 /는 브라우저가 해석하므로 Container Root (http://host:port/)를 가리킵니다. 따라서 컨텍스트 루트가 누락되지 않도록 /context_name/path 형태로 명시해야 합니다.
반면 서블릿의 @WebServlet("/")이나 web.xml에서 사용하는 /는 WAS가 해석하므로 Context Root (http://host:port/context_name/)를 기준으로 매핑됩니다.
🎯 꼬리 질문 대비
"JSP나 서블릿 환경에서 컨텍스트 루트를 하드코딩하지 않고 유연하게 지정하는 방법은?" → "request.getContextPath() 메서드나 JSTL/EL의 ${pageContext.request.contextPath}를 활용하여 동적으로 경로를 결합합니다."
Q5. Maven pom.xml에서 서블릿 라이브러리의 scope를 'provided'로 설정하는 이유는 무엇인가요? 답변 확인 ▼
[두괄식 결론]
컴파일 단계에서는 API 클래스 참조를 위해 필요하지만, 런타임에는 톰캣 컨테이너가 자체 라이브러리를 이미 제공하므로 중복 패키징을 막기 위해서입니다.
[상세 이유]
만약 기본 스코프(compile)로 지정하여 WAR 파일 내부의 WEB-INF/lib에 서블릿 API JAR가 함께 배포되면, 톰캣 자체 클래스로더의 서블릿 API와 웹앱 클래스로더의 서블릿 API가 충돌하여 클래스 캐스팅 에러나 런타임 예외가 발생할 수 있습니다. provided를 통해 최종 패키징 산출물에서 제외시킵니다.
🎯 꼬리 질문 대비
"Maven에서 scope의 종류(compile, runtime, provided, test) 간의 차이를 간단히 말씀해 주세요." → "compile은 빌드/런타임 전체 포함, runtime은 실행 시에만 필요(JDBC 드라이버 등), provided는 런타임 환경이 제공, test는 단위 테스트 수행 시에만 참조되는 스코프입니다."
