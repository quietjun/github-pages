Backend Architecture • Cookie & Session

백엔드 상태 관리: Cookie & Session, 예외 처리 아키텍처 핵심 요약

HTTP 무상태(Stateless) 한계 극복을 위한 Cookie와 Session 메커니즘부터 보안 옵션(SameSite, HttpOnly, Secure), 4대 Scope 라이프사이클, 로그인/인증 필터 구현, 그리고 엔터프라이즈 예외 처리 아키텍처까지 교안의 전 핵심을 완벽하게 정리합니다.

1. HTTP Stateless 특성과 상태 관리 메커니즘

📌 HTTP 무상태(Stateless) 프로토콜의 배경과 보완

기본적으로 HTTP 프로토콜은 Stateless(무상태)로 동작합니다. 서버는 클라이언트의 이전 요청 상태를 기억하지 않으며, 각 요청은 완전히 독립된 단위로 처리됩니다.

Stateless 설계 이유 상세 특징 및 효과
단순성 (Simplicity) 요청 간의 연결 및 과거 컨텍스트를 추적할 필요가 없어 서버 구조가 간결해지고 처리 속도가 향상됩니다.
확장성 (Scalability) 서버 간 공유해야 할 세션 상태가 없으므로 여러 서버로 요청을 자유롭게 분산(로드 밸런싱)하고 수평 확장(Scale-out)이 매우 용이합니다.
신뢰성 (Reliability) 각 요청이 상호 독립적이므로 특정 요청 처리 실패나 한 서버의 장애가 다른 트랜잭션에 전파되지 않습니다.
자원 절약 (Resource Saving) 수천~수만 명의 접속자 상태를 서버 메모리에 계속 유지하지 않으므로 서버 자원을 효율적으로 보존합니다.

💡 상태 관리의 필요성: 전자상거래 장바구니, 로그인 인증 유지, 사용자 맞춤 설정 등 실제 비즈니스 로직은 사용자의 식별과 연속된 상태 유지를 필수로 요구합니다. 이를 해결하기 위해 Cookie와 Session 기술이 도입되었습니다.

2. Cookie: 구조, 동작 흐름 및 핵심 프로퍼티

📌 Cookie의 라이프사이클 및 전송 흐름

쿠키는 웹 서버가 생성하여 HTTP 응답 헤더를 통해 클라이언트(웹 브라우저)에 전달하고, 브라우저 로컬에 저장되는 key-value 형태의 데이터입니다. (클래스: jakarta.servlet.http.Cookie)

Step 1
최초 요청
클라이언트가 서버 특정 리소스로 첫 HTTP 요청을 전송
Step 2
쿠키 생성
서블릿에서 new Cookie(name, value)로 생성 후 설정
Step 3
Set-Cookie 헤더 응답
response.addCookie(cookie)를 통해 응답 헤더로 브라우저에 전달
Step 4
브라우저 저장
브라우저의 쿠키 저장소에 도메인 및 경로별로 쿠키 보관
Step 5
이후 요청 시 자동 전송
동일 도메인/경로 요청 시 HTTP 요청 헤더(Cookie)에 실려 자동 전송
📌 Cookie의 핵심 프로퍼티(Property) 명세
프로퍼티 접근 방식 기능 및 제약 사항
name getName() (getter만 제공) 쿠키를 식별하는 고유한 이름. 생성자에서 지정하며 수정 불가.
알파벳, 숫자, 하이픈(-), 언더스코어(_), 물결(~), 점(.) 허용. 공백 및 기타 문자는 인코딩 필요. 동일 이름 설정 시 기존 쿠키를 덮어씁니다.
value getValue() / setValue() 쿠키에 저장되는 실제 값. 한글, 공백 등은 HTTP 헤더 규격상 직접 작성이 불가능하므로 반드시 URLEncoder.encode(val, "UTF-8")로 인코딩하여 저장하고, 읽을 때 URLDecoder.decode()로 복원해야 합니다.
path getPath() / setPath() 쿠키가 전송될 유효 경로.
• 설정 경로 및 하위 경로 요청에 대해서만 브라우저가 쿠키를 전송합니다.
• 미설정 시: 쿠키를 생성한 서블릿의 Context Root가 기본값으로 적용됩니다.
• 컨테이너 루트(/) 지정 시: 동일 호스트 내 다른 컨텍스트 애플리케이션(예: /out_app, /your_app)과 쿠키가 공유되어 보안 이슈가 발생할 수 있습니다.
maxAge getMaxAge() / setMaxAge(int sec) 쿠키의 유효 기간(초 단위).
• 양수: 설정된 시간(초) 동안 디스크/브라우저에 보관되며 시간 만료 시 자동 파기.
• 음수(-1) 또는 미지정: 세션 쿠키(Session Cookie)로 동작하며 브라우저 프로세스 종료 시 자동 파기.
• 0: 브라우저 수신 즉시 삭제 (쿠키 삭제 시 동일한 name과 path로 maxAge를 0으로 설정하여 재전송).
• Chrome 등 모던 브라우저는 최대 유효 기간을 400일로 제한합니다.

3. 쿠키 보안 옵션 3종 세트 & SameSite 매트릭스

📌 웹 공격 대응을 위한 쿠키 보안 3종 속성
🔒 secure
HTTPS 프로토콜 암호화 통신에서만 쿠키 전송 허용.
▶ 공공 Wi-Fi, 중간자 공격(MITM)에 의한 네트워크 스니핑 및 쿠키 가로채기 방지
🛡️ httpOnly
브라우저 JavaScript(document.cookie)에서 접근 불가능하도록 차단.
▶ 악의적 스크립트 삽입을 통한 XSS(Cross-Site Scripting) 세션 탈취 방지
🌐 SameSite
Cross-Site 요청 시 쿠키 전송 허용 범위를 제어(Strict, Lax, None).
▶ 타 사이트로부터의 위조 요청을 차단하는 CSRF(Cross-Site Request Forgery) 방지
📌 SameSite 정책별 요청 유형 전송 매트릭스 (W3C / RFC 6265bis)
요청 상황 (출발지 → 목적지) 요청 방식 Strict Lax (모던 기본값) None (+Secure 필수)
주소창 직접 입력 / 북마크 Direct Navigation ✅ 전송 ✅ 전송 ✅ 전송
같은 사이트 내 이동 (A → A) 모든 요청 방식 ✅ 전송 ✅ 전송 ✅ 전송
타 사이트에서 링크 클릭 (B → A) <a href="A"> ❌ 차단 ✅ 전송 (Top-level) ✅ 전송
타 사이트에서 폼 GET 전송 (B → A) <form method="GET"> ❌ 차단 ✅ 전송 (Safe GET) ✅ 전송
타 사이트에서 폼 POST 전송 (B → A) <form method="POST"> ❌ 차단 ❌ 차단 (CSRF 방어) ✅ 전송
타 사이트에서 리소스 로딩 <img>, <iframe> ❌ 차단 ❌ 차단 ✅ 전송
타 사이트에서 비동기 요청 fetch(), XHR (AJAX) ❌ 차단 ❌ 차단 ✅ 전송
📌 Servlet 6.0+ 표준 Cookie 설정 및 사용 API

Jakarta Servlet 6.0부터 도입된 cookie.setAttribute(String name, String value) 메서드를 통해 표준화된 방식으로 신규 속성을 정의할 수 있습니다. 

Cookie cookie = new Cookie("sessionId", "abc123");

// 1. 값이 있는 속성: "속성=값" 형태로 헤더에 추가
cookie.setAttribute("SameSite", "Strict");    // SameSite=Strict;
cookie.setAttribute("Domain", ".mysite.com"); // Domain=.mysite.com;

// 2. 값이 없는 boolean 속성: 빈 문자열("") 전달 시 이름만 헤더에 표시
cookie.setAttribute("HttpOnly", "");            // HttpOnly;
cookie.setAttribute("Secure", "");              // Secure;

// 3. 속성 제거: null 전달 시 헤더에서 완전히 제거
cookie.setAttribute("SameSite", null);          // 속성 삭제

// 최종 Set-Cookie 헤더:
// Set-Cookie: sessionId=abc123; Domain=.mysite.com; HttpOnly; Secure;
response.addCookie(cookie);
📌 서블릿과 JSP(EL)에서의 쿠키 조회 비교
// [Servlet] request.getCookies() 순회 (클라이언트 전송 시 name과 value만 전달됨)
Cookie[] cookies = request.getCookies();
if (cookies != null) {
    for (Cookie c : cookies) {
        String key = c.getName();
        String val = URLDecoder.decode(c.getValue(), "UTF-8");
        System.out.println(key + " : " + val);
    }
}

4. 웹 애플리케이션의 4대 Scope (영역)

📌 데이터 공유 범위 및 라이프사이클 비교
영역 (Scope) 관리 객체 유효 기간 (Lifecycle) 공유 범위 및 주요 용도
Page 영역 PageContext 하나의 JSP 페이지 실행 동안만 존재 해당 페이지 내부에서만 유효. EL의 기본 탐색 1순위 스코프.
Request 영역 HttpServletRequest 하나의 HTTP 요청이 시작되어 응답할 때까지 서블릿과 포워드(forward)되는 JSP 간의 데이터 전달 (단발성 조회 결과, 폼 오류 메시지 등).
Session 영역 HttpSession 브라우저 세션 유지 시간 또는 비활성 만료 시까지 동일 클라이언트(브라우저)의 여러 연속된 요청 간 공유 (로그인 사용자 정보, 장바구니 등).
Application 영역 ServletContext 웹 애플리케이션 시작부터 서버 종료(shutdown) 시까지 컨텍스트 전체의 모든 사용자와 모든 세션이 전역 공유 (방문자 총 집계, 전역 설정, 공통 코드 캐시 등).

5. Session 동작 원리 및 세션 관리 아키텍처

📌 JSESSIONID를 매개로 한 세션 식별 메커니즘

세션은 상태 값을 클라이언트가 아닌 서버 메모리에 저장하며, 클라이언트와 서버를 연결하는 열쇠(Key)로 JSESSIONID라는 세션 쿠키를 사용합니다.

Step 1
최초 요청
브라우저에 JSESSIONID 쿠키가 없는 상태로 요청 진입
Step 2
세션 생성 & ID 발급
서버 메모리에 세션 객체 생성 후 고유한 JSESSIONID 발급
Step 3
Set-Cookie 헤더 전달
응답 시 Set-Cookie: JSESSIONID=XXXX를 브라우저에 전송
Step 4
브라우저 재요청
이후 요청마다 Cookie: JSESSIONID=XXXX를 서버로 전송
Step 5
세션 확인 및 복원
전달된 키로 서버 메모리에서 기존 세션을 찾아 상태 객체 복원
📌 HttpSession 핵심 메서드 및 유효기간 산정 방식
메서드 시그니처 기능 설명
request.getSession() 현재 세션을 반환하며, 존재하지 않을 경우 새로운 세션을 생성하여 반환 (getSession(true)와 동일). getSession(false)는 없을 시 null 반환.
Object getAttribute(String name) 지정된 이름으로 세션에 저장된 객체를 조회합니다.
void setAttribute(String name, Object val) 세션에 데이터를 key-value로 바인딩합니다.
void removeAttribute(String name) 지정된 이름의 세션 속성만 개별 삭제합니다.
void invalidate() 현재 세션을 완전히 무효화(소멸)시키고 바인딩된 모든 객체를 언바인딩합니다. (로그아웃 처리의 표준)
String getId() WAS가 발급한 세션 고유 식별자 문자열을 반환합니다.
📌 세션 만료 기준과 2가지 타임아웃 설정법

세션은 생성 시각(creationTime)이 아니라, 마지막 클라이언트 접근 시각(lastAccessedTime)으로부터 maxInactiveInterval 동안 추가 요청이 없을 때 소멸합니다. 사용자가 요청을 보낼 때마다 lastAccessedTime은 최신 시각으로 자동 갱신됩니다.

설정 방식 단위 (Unit) 설정 코드 예시 및 적용 범위
web.xml 전역/컨텍스트 설정 분 (Minute) 
<session-config>
    <session-timeout>30</session-timeout> <!-- 30분 -->
</session-config>
자바 프로그래밍 방식 설정 초 (Second) 
HttpSession session = request.getSession();
session.setMaxInactiveInterval(30 * 60); // 1800초 = 30분

6. 인증(Login/Logout) 및 SessionFilter 보안 아키텍처

📌 MVC 기반 로그인 / 로그아웃 처리 흐름

로그인 성공 시 세션에 회원 객체를 바인딩하고 반드시 Redirect(PRG 패턴)를 사용하여 새로고침 시 로그인 POST 요청이 중복 실행되는 것을 방지합니다. 

// [Controller] 로그인 처리
private void login(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    String email = request.getParameter("email");
    String pass = request.getParameter("pass");
    
    Member member = mService.login(email, pass);
    if (member != null) {
        // 로그인 성공: 세션에 사용자 정보 바인딩
        request.getSession().setAttribute("loginUser", member);
        redirect(request, response, "/"); // 메인 페이지로 리다이렉트
    } else {
        // 로그인 실패: request 영역에 안내 메시지 바인딩 후 포워드
        request.setAttribute("alertMsg", "아이디 또는 비밀번호가 일치하지 않습니다.");
        forward(request, response, "/member/login-form.jsp");
    }
}

// [Controller] 로그아웃 처리
private void logout(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    // 세션 완전 무효화
    request.getSession().invalidate();
    redirect(request, response, "/");
}
📌 JSP 화면 분기 렌더링 & SessionFilter 권한 제어
<!-- [JSP] 세션 로그인 여부에 따른 동적 UI 렌더링 -->
<c:if test="${empty loginUser}">
    <a href="${root}/member?action=login-form">로그인</a> |
    <a href="${root}/member?action=regist-member-form">회원가입</a>
</c:if>
<c:if test="${!empty loginUser}">
    <span>${loginUser.name}님 환영합니다!</span> |
    <a href="${root}/member?action=logout">로그아웃</a>
</c:if>

// [Filter] 특정 경로(/auth/*) 인가 제어 필터 구현
@WebFilter("/auth/*")
public class SessionFilter extends HttpFilter {
    @Override
    protected void doFilter(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpSession session = req.getSession();
        if (session.getAttribute("loginUser") != null) {
            chain.doFilter(req, res); // 로그인 상태: 정상 통과
        } else {
            // 미인증 상태: 안내 메시지 설정 후 로그인 폼으로 리다이렉트
            session.setAttribute("alertMsg", "로그인 후 이용 가능한 서비스입니다.");
            res.sendRedirect(req.getContextPath() + "/member?action=login-form");
        }
    }
}

7. 엔터프라이즈 예외(Exception) 처리 아키텍처

📌 예외 처리 정책의 대원칙
🚫 보안 결함 방지
WAS 기본 에러 페이지(Stack Trace, 데이터베이스 스키마, 서버 버전 등)가 클라이언트에 날것으로 노출되면 심각한 보안 취약점이 됩니다.
🖥️ 사용자 친화적 UI
시스템 내부 정보 노출을 배제한 친절한 안내 메시지(예: '일시적인 오류가 발생했습니다')와 함께 이전 페이지 이동, 홈으로 가기 등 다음 행동을 유도하는 공통 에러 화면을 제공합니다.

리뷰 대상 코드 1: 쿠키 삭제 로직 오류 코드
⚠️ 트러블슈팅 상황 시나리오
앞선 요청에서 애플리케이션 전역 경로(setPath(request.getContextPath()))로 브라우저에 recentGugu 쿠키를 발급해 두었습니다. 이후 사용자가 "최근 조회 기록 삭제" 버튼을 눌러 서블릿에서 maxAge(0) 쿠키를 응답 헤더에 담아 전송했는데, 브라우저 개발자 도구(Application > Cookies)를 확인해 보면 기존 쿠키가 전혀 삭제되지 않고 여전히 남아있어 이전 기록이 계속 노출됩니다. 왜 그럴까요? 
// [사전 상태] 앞선 요청에서 contextPath 전역 경로(/BE_05)로 쿠키를 발급해 둔 상태
// Cookie cookie = new Cookie("recentGugu", "7");
// cookie.setPath(request.getContextPath()); // Path: /BE_05
// response.addCookie(cookie);

// [Controller 서블릿] 사용자가 삭제 버튼 클릭 시 실행된 메서드
protected void clearHistory(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    Cookie deleteCookie = new Cookie("recentGugu", "");
    deleteCookie.setMaxAge(0);
    response.addCookie(deleteCookie);
    
    response.sendRedirect(request.getContextPath() + "/main?action=gugu-form");
}
원인 분석 및 개선 코드
쿠키 삭제 시 Path 속성 불일치 결함
원인 분석: 브라우저가 특정 쿠키를 고유하게 식별하는 기준은 [Domain + Path + Name]의 조합입니다. 기존 쿠키를 생성할 때 setPath(request.getContextPath()) 등을 명시했거나 특정 하위 경로에서 생성되었다면, 삭제용 쿠키(maxAge=0)를 생성할 때도 반드시 기존 쿠키와 정확히 일치하는 Path를 설정해야 합니다.
위 코드처럼 setPath()를 생략하면 현재 요청 서블릿의 세부 경로가 기본 path로 지정되어, 기존 쿠키는 그대로 둔 채 다른 경로의 새로운 빈 쿠키를 생성했다가 즉시 파기하는 무의미한 동작이 수행됩니다.
개선 코드 (Refactored) 
protected void clearHistory(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    Cookie deleteCookie = new Cookie("recentGugu", "");
    // 생성 시점과 완전히 동일한 Path를 명시해야 대상 쿠키가 삭제됨
    deleteCookie.setPath(request.getContextPath());
    deleteCookie.setMaxAge(0);
    response.addCookie(deleteCookie);
    
    response.sendRedirect(request.getContextPath() + "/main?action=gugu-form");
}
리뷰 대상 코드 2: 서블릿 쿠키 생성 후 포워드 오류 코드
⚠️ 트러블슈팅 상황 시나리오
사용자가 구구단 연산을 요청하여 서블릿에서 최근 계산한 단수를 쿠키로 저장한 뒤, 결과 화면을 렌더링하는 JSP로 forward했습니다. 그런데 이동한 JSP 화면에서 ${cookie.recentGugu.value}를 출력하면 방금 저장한 단수가 나오지 않고 빈 값이거나 이전에 저장되었던 구 단수 값이 출력됩니다. 왜 그럴까요? 
// [Controller 서블릿] 구구단 연산 처리
protected void calculateGugu(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    int dan = Integer.parseInt(request.getParameter("dan"));
    
    Cookie cookie = new Cookie("recentGugu", String.valueOf(dan));
    cookie.setMaxAge(60 * 60 * 24);
    cookie.setPath(request.getContextPath());
    response.addCookie(cookie);
    
    // 연산 결과는 request attribute에 저장
    request.setAttribute("result", simpleService.getGugu(dan));
    
    // JSP 결과 화면으로 forward
    request.getRequestDispatcher("/gugu-result.jsp").forward(request, response);
}
원인 분석 및 개선 코드
쿠키 라이프사이클 및 클라이언트 전송 시점 오해
원인 분석: 쿠키의 라이프사이클을 이해하지 못한 데서 발생한 결함입니다.
서블릿에서 response.addCookie()를 호출하면 쿠키는 서버 메모리가 아니라 HTTP 응답 헤더(Set-Cookie)에 적재됩니다. 이 쿠키가 브라우저에 저장된 후 다시 서버로 전달되는 시점은 '클라이언트의 다음 HTTP 요청'부터입니다.
하지만 forward는 서버 내부에서 제어권만 JSP로 넘기는 동일 요청 사이클이므로, 현재 HttpServletRequest가 보관하고 있는 쿠키 목록은 요청이 처음 들어왔을 때 클라이언트가 보낸 쿠키들뿐입니다. 따라서 방금 생성한 쿠키는 현재 포워드된 JSP의 ${cookie} 객체에 존재하지 않습니다.
개선 코드 (Refactored) 
protected void calculateGugu(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {
    int dan = Integer.parseInt(request.getParameter("dan"));
    
    // 1. 다음 요청을 위한 상태 유지는 쿠키에 등록
    Cookie cookie = new Cookie("recentGugu", String.valueOf(dan));
    cookie.setMaxAge(60 * 60 * 24);
    cookie.setPath(request.getContextPath());
    response.addCookie(cookie);
    
    // 2. 현재 요청(forward된 뷰)에서 즉시 사용할 데이터는 Request Scope에 바인딩!
    request.setAttribute("recentGugu", dan);
    request.setAttribute("result", simpleService.getGugu(dan));
    
    request.getRequestDispatcher("/gugu-result.jsp").forward(request, response);
}
리뷰 대상 코드 3: 로그인 컨트롤러 세션 타임아웃 오류 코드
⚠️ 트러블슈팅 상황 시나리오
로그인 후 사용자의 세션이 30분 동안 유지되도록 설정하기 위해 컨트롤러에 타임아웃 코드를 추가했습니다. 그런데 사용자가 로그인에 성공한 뒤 페이지 내에서 1분도 채 머물지 않았는데 다른 메뉴를 누르면 갑자기 로그인이 풀리고 로그인 화면으로 튕기는 증상이 지속됩니다. 왜 그럴까요? 
// [Controller 서블릿] 로그인 처리
Member member = mService.login(email, pass);
if (member != null) {
    HttpSession session = request.getSession();
    session.setAttribute("loginUser", member);
    
    // 의도: 세션 유효시간을 30분으로 지정
    session.setMaxInactiveInterval(30); 
    
    response.sendRedirect(request.getContextPath() + "/");
}
원인 분석 및 개선 코드
세션 타임아웃 API 시간 단위 오적용
원인 분석: 설정 위치별 시간 단위의 차이를 혼동하여 발생한 문제입니다.
• web.xml의 <session-timeout> 태그는 유효 시간 단위가 분(Minute)입니다.
• 반면 Java 서블릿의 HttpSession.setMaxInactiveInterval(int interval) 메서드는 단위가 초(Second)입니다.
따라서 setMaxInactiveInterval(30)을 호출하면 30분이 아니라 단 30초 만에 세션이 만료되므로, 사용자가 30초만 지나도 즉시 로그아웃되는 현상이 발생한 것입니다.
개선 코드 (Refactored) 
Member member = mService.login(email, pass);
if (member != null) {
    HttpSession session = request.getSession();
    session.setAttribute("loginUser", member);
    
    // 초 단위이므로 30분 = 30 * 60 = 1800초로 설정
    session.setMaxInactiveInterval(30 * 60); 
    
    response.sendRedirect(request.getContextPath() + "/");
}
리뷰 대상 코드 4: 인증 인가 필터(SessionFilter) 오류 코드
⚠️ 트러블슈팅 상황 시나리오
비로그인 사용자의 보호 자원(/auth/*) 접근을 차단하기 위해 필터를 적용했습니다. 그런데 비로그인 상태로 접근 시 브라우저는 로그인 폼으로 리다이렉트되지만, 톰캣 서버 콘솔에는 java.lang.IllegalStateException: Cannot forward after response has been committed 예외가 주기적으로 출력되며 보호 대상 서블릿의 내부 로직이 계속 실행되는 이상 현상이 발견되었습니다. 왜 그럴까요? 
@WebFilter("/auth/*")
public class SessionFilter extends HttpFilter {
    @Override
    protected void doFilter(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpSession session = req.getSession();
        if (session.getAttribute("loginUser") != null) {
            chain.doFilter(req, res);
        } else {
            session.setAttribute("alertMsg", "로그인 후 사용하세요.");
            res.sendRedirect(req.getContextPath() + "/member?action=login-form");
            chain.doFilter(req, res);
        }
    }
}
원인 분석 및 개선 코드
응답 커밋 후 필터 체인 계속 실행 결함
원인 분석: 1. res.sendRedirect()는 브라우저에 302 상태 코드와 Location 헤더를 전송하여 응답 스트림을 커밋합니다. 그런데 그 직후 chain.doFilter(req, res)를 호출하여 뒤따르는 보호 대상 서블릿을 그대로 실행시켜 버립니다. 이로 인해 서블릿이 다시 forward나 렌더링을 시도하면서 IllegalStateException이 발생하며, 비인증 사용자에게 데이터가 유출될 위험이 있습니다.
2. 리다이렉트 후 반드시 return;을 선언하여 필터 메서드의 제어 흐름을 명시적으로 종료해야 합니다.
개선 코드 (Refactored) 
@WebFilter("/auth/*")
public class SessionFilter extends HttpFilter {
    @Override
    protected void doFilter(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpSession session = req.getSession();
        if (session.getAttribute("loginUser") != null) {
            chain.doFilter(req, res);
        } else {
            session.setAttribute("alertMsg", "로그인 후 사용하세요.");
            res.sendRedirect(req.getContextPath() + "/member?action=login-form");
            return; // ★ 제어 흐름 즉시 종료 (chain.doFilter 미호출)
        }
    }
}

문제 1 / 8
⏱️ 남은 시간: 30초
Q1
(O/X) HTTP는 기본적으로 Stateless(무상태) 프로토콜이므로 이전 요청의 상태를 서버가 자동으로 기억하지 못한다.
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: O

HTTP는 단순성, 확장성, 신뢰성, 자원 절약을 위해 요청 간 상태를 기억하지 않는 Stateless 설계를 취하고 있으며, 상태 유지가 필요할 경우 Cookie 또는 Session을 명시적으로 사용해야 합니다.

Q2
(O/X) Cookie의 name 속성은 생성자에서 설정한 이후 setName() 메서드를 호출하여 언제든지 이름을 변경할 수 있다.
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: X

쿠키의 name은 쿠키를 고유하게 식별하는 유일한 키이므로 getName()만 제공되며 수정 메서드(setName)는 제공되지 않습니다. 반면 value, path, maxAge 등은 getter/setter를 모두 제공합니다.

Q3
(단답형) 쿠키의 유효기간(maxAge)을 브라우저 프로세스가 종료될 때까지만 유지되는 '세션 쿠키(Session Cookie)'로 설정하고자 할 때 setMaxAge()에 전달하는 값은?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: 음수 (또는 -1)

양수는 해당 시간(초) 동안 디스크에 유지되는 영속 쿠키, 0은 즉시 삭제용 쿠키이며, 음수(-1)나 값을 지정하지 않으면 브라우저 종료 시 소멸하는 세션 쿠키가 됩니다.

Q4
(O/X) SameSite 속성을 'Strict'로 설정하면, 타 사이트에 걸려 있는 링크()를 클릭하여 해당 사이트로 접속할 때도 브라우저가 쿠키를 자동으로 전송한다.
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: X

Strict는 오직 동일 사이트(Same-site) 내부 이동에서만 쿠키를 전송하며, 타 사이트의 링크 클릭이나 폼 전송을 완전히 차단합니다. 링크 클릭과 같은 안전한 Top-level 네비게이션에서 쿠키를 전송하려면 Lax(모던 브라우저 기본값)를 사용해야 합니다.

Q5
(단답형) 자바스크립트의 document.cookie를 통한 쿠키 접근을 원천 차단하여 XSS(Cross-Site Scripting) 공격으로부터 세션 탈취를 방어하는 쿠키 보안 속성의 명칭은?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: httpOnly (또는 HttpOnly)

httpOnly가 적용된 쿠키는 오직 HTTP 네트워크 통신 시에만 헤더에 실려 전달되며, 브라우저 콘솔이나 악의적으로 삽입된 스크립트가 document.cookie로 값을 탈취할 수 없습니다.

Q6
(단답형) 서블릿/JSP의 4대 영역(Scope) 중 동일한 브라우저(사용자)가 발생시키는 여러 번의 요청/응답 간에 데이터를 공유하며 브라우저 종료 시점까지 유지되는 영역의 이름은?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: session 영역 (또는 HttpSession)

웹의 4대 영역은 Page(페이지 내부), Request(단일 요청 사이클), Session(단일 사용자 브라우저 세션), Application(서버 구동 전체)으로 구분됩니다.

Q7
(O/X) web.xml의 설정과 서블릿의 session.setMaxInactiveInterval() 메서드는 모두 유효시간 단위로 '초(Second)'를 사용한다.
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: X

web.xml의 <session-timeout>은 '분(Minute)' 단위이며, 자바 코드의 setMaxInactiveInterval()은 '초(Second)' 단위입니다.

Q8
(단답형) 로그아웃 처리 시 세션 객체 자체를 소멸시키고 발급된 JSESSIONID를 완전히 무효화하기 위해 호출하는 HttpSession의 표준 메서드는?
⏰ 30초가 경과했습니다! 정답과 해설을 확인해 보세요.
정답: invalidate()

removeAttribute()는 특정 속성만 지우지만, invalidate()는 현재 세션을 서버 메모리에서 완전히 파기하여 세션 고정(Session Fixation) 공격을 예방합니다.

Q1
(O/X) HTTP는 기본적으로 Stateless(무상태) 프로토콜이므로 이전 요청의 상태를 서버가 자동으로 기억하지 못한다.
정답 및 해설 확인
정답: O

HTTP는 단순성, 확장성, 신뢰성, 자원 절약을 위해 요청 간 상태를 기억하지 않는 Stateless 설계를 취하고 있으며, 상태 유지가 필요할 경우 Cookie 또는 Session을 명시적으로 사용해야 합니다.

Q2
(O/X) Cookie의 name 속성은 생성자에서 설정한 이후 setName() 메서드를 호출하여 언제든지 이름을 변경할 수 있다.
정답 및 해설 확인
정답: X

쿠키의 name은 쿠키를 고유하게 식별하는 유일한 키이므로 getName()만 제공되며 수정 메서드(setName)는 제공되지 않습니다. 반면 value, path, maxAge 등은 getter/setter를 모두 제공합니다.

Q3
(단답형) 쿠키의 유효기간(maxAge)을 브라우저 프로세스가 종료될 때까지만 유지되는 '세션 쿠키(Session Cookie)'로 설정하고자 할 때 setMaxAge()에 전달하는 값은?
정답 및 해설 확인
정답: 음수 (또는 -1)

양수는 해당 시간(초) 동안 디스크에 유지되는 영속 쿠키, 0은 즉시 삭제용 쿠키이며, 음수(-1)나 값을 지정하지 않으면 브라우저 종료 시 소멸하는 세션 쿠키가 됩니다.

Q4
(O/X) SameSite 속성을 'Strict'로 설정하면, 타 사이트에 걸려 있는 링크()를 클릭하여 해당 사이트로 접속할 때도 브라우저가 쿠키를 자동으로 전송한다.
정답 및 해설 확인
정답: X

Strict는 오직 동일 사이트(Same-site) 내부 이동에서만 쿠키를 전송하며, 타 사이트의 링크 클릭이나 폼 전송을 완전히 차단합니다. 링크 클릭과 같은 안전한 Top-level 네비게이션에서 쿠키를 전송하려면 Lax(모던 브라우저 기본값)를 사용해야 합니다.

Q5
(단답형) 자바스크립트의 document.cookie를 통한 쿠키 접근을 원천 차단하여 XSS(Cross-Site Scripting) 공격으로부터 세션 탈취를 방어하는 쿠키 보안 속성의 명칭은?
정답 및 해설 확인
정답: httpOnly (또는 HttpOnly)

httpOnly가 적용된 쿠키는 오직 HTTP 네트워크 통신 시에만 헤더에 실려 전달되며, 브라우저 콘솔이나 악의적으로 삽입된 스크립트가 document.cookie로 값을 탈취할 수 없습니다.

Q6
(단답형) 서블릿/JSP의 4대 영역(Scope) 중 동일한 브라우저(사용자)가 발생시키는 여러 번의 요청/응답 간에 데이터를 공유하며 브라우저 종료 시점까지 유지되는 영역의 이름은?
정답 및 해설 확인
정답: session 영역 (또는 HttpSession)

웹의 4대 영역은 Page(페이지 내부), Request(단일 요청 사이클), Session(단일 사용자 브라우저 세션), Application(서버 구동 전체)으로 구분됩니다.

Q7
(O/X) web.xml의 설정과 서블릿의 session.setMaxInactiveInterval() 메서드는 모두 유효시간 단위로 '초(Second)'를 사용한다.
정답 및 해설 확인
정답: X

web.xml의 <session-timeout>은 '분(Minute)' 단위이며, 자바 코드의 setMaxInactiveInterval()은 '초(Second)' 단위입니다.

Q8
(단답형) 로그아웃 처리 시 세션 객체 자체를 소멸시키고 발급된 JSESSIONID를 완전히 무효화하기 위해 호출하는 HttpSession의 표준 메서드는?
정답 및 해설 확인
정답: invalidate()

removeAttribute()는 특정 속성만 지우지만, invalidate()는 현재 세션을 서버 메모리에서 완전히 파기하여 세션 고정(Session Fixation) 공격을 예방합니다.

Q1. Cookie와 Session의 근본적인 차이점과 각각을 실무에서 선택하는 기준을 설명해 주세요. 답변 확인 ▼
1. 두괄식 결론 (Core Conclusion)

쿠키와 세션의 가장 근본적인 차이는 '상태 데이터의 저장 위치'와 그에 따른 '보안성 및 서버 부하'입니다. 쿠키는 클라이언트(브라우저)에 데이터를 저장하는 반면, 세션은 서버 메모리에 데이터를 저장하고 클라이언트에는 이를 조회할 수 있는 고유 키인 JSESSIONID만 쿠키로 발급합니다.

2. 핵심 근거 및 비교 (Details)

첫째, 보안성 측면에서 쿠키는 클라이언트 로컬에 노출되고 변조 위험이 있으므로 보안에 덜 민감한 단순 상태(아이디 기억하기, 팝업 '오늘 하루 보지 않기', 최근 본 상품 등)에 적합합니다. 반면 세션은 실제 데이터가 서버에 은닉되므로 로그인 인증 객체, 장바구니 등 민감한 비즈니스 데이터에 사용됩니다.
둘째, 성능 및 자원 측면에서 쿠키는 클라이언트가 보관하므로 서버 메모리를 소모하지 않지만 매 HTTP 요청마다 헤더에 실려 네트워크 트래픽을 유발합니다. 세션은 네트워크 부하는 적으나 동시 접속자가 많아질수록 서버 메모리(RAM)를 직접 점유하므로 적절한 타임아웃 관리가 필수적입니다.

3. 정리 및 실무 적용 (Wrap-up)

따라서 실무에서는 보안성과 서버 리소스 트레이드오프를 고려하여, 민감한 인증 정보는 세션으로 보호하고 브라우저 단위의 경량 설정은 만료 기간을 지정한 쿠키로 분리하여 설계합니다.

💬 꼬리 질문 대비 포인트
• 서버를 여러 대 두는 대규모 분산 환경에서는 세션을 어떻게 관리하나요?
▶ Sticky Session(L4 스위치 기반 고정), 세션 클러스터링(WAS 간 세션 복제), 또는 Redis/Memcached 같은 외장 분산 인메모리 캐시 서버에 세션을 저장하는 Session Storage 아키텍처로 확장합니다.
Q2. HTTP는 무상태(Stateless)인데, 세션은 서버에서 사용자를 어떻게 식별하고 상태를 유지하나요? 답변 확인 ▼
1. 두괄식 결론 (Core Conclusion)

세션은 무상태인 HTTP 프로토콜 위에서 동작하기 위해 'JSESSIONID'라는 세션 쿠키를 식별 매개체로 활용하여 클라이언트와 서버 메모리의 세션 객체를 1:1로 매핑합니다.

2. 핵심 근거 및 흐름 (Flow)

1) 클라이언트가 서버에 최초로 접근하여 request.getSession()이 호출되면, WAS는 추측 불가능한 난수 기반의 고유한 JSESSIONID를 생성하고 서버 메모리에 세션 저장 공간을 할당합니다.
2) 서버는 HTTP 응답 헤더에 Set-Cookie: JSESSIONID=XXXX; Path=/; HttpOnly를 실어 브라우저로 보냅니다.
3) 브라우저는 이 쿠키를 세션 쿠키로 저장한 뒤, 이후 동일 호스트로 요청을 보낼 때마다 HTTP Cookie: JSESSIONID=XXXX 요청 헤더에 자동으로 첨부합니다.
4) 서버는 수신된 JSESSIONID를 키(Key)로 자신의 세션 관리 테이블에서 매핑된 HttpSession 인스턴스를 찾아내어 이전 요청의 상태를 그대로 복원합니다.

3. 정리 및 요약 (Wrap-up)

결과적으로 세션은 독자적인 네트워크 프로토콜이 아니라, 쿠키 기술을 서버의 메모리 저장소와 결합하여 상태 연속성을 구현한 고수준의 메커니즘입니다.

💬 꼬리 질문 대비 포인트
• 만약 클라이언트 브라우저가 쿠키 사용을 완전히 차단하면 세션이 동작하지 않나요?
▶ URL 뒤에 세션 ID를 파라미터 형태로 붙여 전달하는 URL 재작성(URL Rewriting, 예: ;jsessionid=...) 기술을 fallback으로 사용할 수 있으나, URL 노출로 인한 세션 하이재킹 위험이 있어 현대 웹에서는 보안상 지양합니다.
Q3. 쿠키의 3대 보안 옵션(HttpOnly, Secure, SameSite)의 역할과 방어하는 보안 취약점을 설명해 주세요. 답변 확인 ▼
1. 두괄식 결론 (Core Conclusion)

쿠키의 보안 3종 세트는 웹의 3대 보안 위협인 XSS(크로스 사이트 스크립팅), 네트워크 도청(스니핑), CSRF(크로스 사이트 요청 위조)를 각각 원천 차단하기 위해 고안된 표준 방어 속성입니다.

2. 세부 속성별 방어 메커니즘 (Details)

• HttpOnly (XSS 방어): 브라우저 JavaScript의 document.cookie 객체를 통한 쿠키 접근을 완전히 차단합니다. 게시판이나 인풋 필드에 악성 스크립트가 삽입되더라도 공격자가 JSESSIONID 등 인증 쿠키를 탈취할 수 없습니다.
• Secure (네트워크 도청 방어): 쿠키가 오직 HTTPS 암호화 채널을 통해서만 전송되도록 강제합니다. 평문 HTTP 통신 구간에서 패킷 스니핑을 통해 쿠키가 노출되는 중간자(MITM) 공격을 방어합니다.
• SameSite (CSRF 방어): 제3자 도메인(Cross-Site)에서 발생한 요청에 대해 쿠키 전송 여부를 제어합니다. Strict는 모든 타 사이트 요청에서 쿠키를 제외하고, 기본값인 Lax는 안전한 탑레벨 네비게이션(링크 클릭, GET 방식 폼)만 허용하고 POST 등 상태 변경 요청은 차단하여 사용자 권한을 도용한 위조 요청을 막습니다.

3. 정리 (Wrap-up)

엔터프라이즈 백엔드 환경에서는 인증 관련 쿠키에 대해 HttpOnly, Secure, SameSite=Lax를 기본 설정하는 것이 표준 보안 가이드라인입니다.

💬 꼬리 질문 대비 포인트
• SameSite=None은 어떤 경우에 사용하며, 이때 주의할 점은 무엇인가요?
▶ 결제 창 연동, 타 도메인 임베디드 iframe 등 서드파티 쿠키 전송이 반드시 필요한 환경에서 사용하며, 보안상 반드시 Secure 속성이 함께 지정되어야 브라우저가 승인합니다.
Q4. 웹 애플리케이션의 4대 Scope(Page, Request, Session, Application)의 생명주기를 비교 설명해 주세요. 답변 확인 ▼
1. 두괄식 결론 (Core Conclusion)

서블릿/JSP 컨테이너는 데이터의 수명과 공유 목적에 따라 Page, Request, Session, Application의 4단계 스코프 계층을 제공하며, 범위가 좁은 곳에서 넓은 곳으로 확장됩니다.

2. 단계별 라이프사이클 비교 (Details)

• Page Scope (PageContext): 현재 JSP 페이지가 클라이언트에 렌더링되는 동안에만 유효하며, 페이지 처리가 끝나면 즉시 소멸합니다.
• Request Scope (HttpServletRequest): 클라이언트의 HTTP 요청이 시작되어 응답이 완료될 때까지 유지됩니다. 특히 서버 내부 forward 시 서블릿과 JSP 간에 모델 데이터를 전달하는 핵심 통로입니다.
• Session Scope (HttpSession): 동일 클라이언트(브라우저)가 서비스에 접속하여 활동하는 동안 여러 요청/응답에 걸쳐 유지되며, 로그아웃(invalidate)이나 설정된 타임아웃 만료 시 소멸합니다.
• Application Scope (ServletContext): 웹 애플리케이션이 톰캣에 배포되어 시작될 때 생성되고 톰캣이 셧다운될 때 소멸하며, 모든 사용자와 모든 세션이 데이터를 공유합니다.

3. 실무 설계 원칙 (Wrap-up)

실무에서는 메모리 누수와 동시성 충돌을 방지하기 위해 '가능한 가장 좁은 스코프'를 선택하는 것이 원칙입니다. 1회성 데이터는 Request에, 로그인 유저는 Session에, 전역 상수는 Application에 배치해야 합니다.

💬 꼬리 질문 대비 포인트
• EL(Expression Language)에서 ${user}처럼 스코프 명시 없이 접근할 때 탐색 순서는 어떻게 되나요?
▶ Page → Request → Session → Application 순으로 좁은 스코프부터 우선 탐색하며, 먼저 발견된 속성을 반환합니다.
Q5. 웹 애플리케이션 예외 처리에서 WAS 기본 에러 페이지 노출을 방지해야 하는 이유와 표준 예외 처리 전략을 설명해 주세요. 답변 확인 ▼
1. 두괄식 결론 (Core Conclusion)

WAS의 기본 에러 페이지는 시스템 내부 스택트레이스, DB 쿼리 구조, 프레임워크 버전 등 민감한 내부 인프라 정보를 노출하여 해킹 공격의 빌미를 제공하므로 반드시 차단해야 합니다. 표준 전략은 '사용자 친화적 커스텀 뷰 제공'과 '서버 내부 전문 로깅'의 이원화입니다.

2. 표준 아키텍처 및 구현 방식 (Architecture)

1) web.xml의 커스텀 에러 페이지 매핑: 404(Not Found), 500(Internal Server Error), 그리고 처리되지 않은 모든 예외를 위한 기본 에러 페이지(<error-page>)를 등록하여 어떠한 예외 상황에서도 날것의 에러가 브라우저에 도달하지 않도록 Fallback 장치를 둡니다.
2) 서버 내부 전문 로깅 및 모니터링: 클라이언트에게는 정제된 에러 화면을 제공하되, 서버 내부에서는 에러 발생 시점의 URL, 파라미터, 전체 스택트레이스를 Logback/Log4j2 등의 로거로 파일이나 모니터링 시스템에 정확히 기록합니다.
3) Controller 계층의 방어적 예외 처리: 비즈니스 로직 상 예측 가능한 검증 예외는 컨트롤러에서 try~catch로 처리하여 사용자에게 구체적인 재입력 안내 메시지를 제공합니다.

3. 정리 (Wrap-up)

결과적으로 완벽한 예외 처리 아키텍처는 클라이언트의 사용자 경험을 보호함과 동시에 내부 시스템 보안성을 극대화하고 운영 트러블슈팅의 신속성을 보장합니다.
