JAVA · OOP DESIGN PRINCIPLES

SOLID 원칙 5가지

객체지향 설계의 5대 원칙 : 클릭해서 원칙별 예제 확인

S Single Responsibility Principle

단일 책임 원칙

  • 단일 책임 : 하나의 클래스는 단 한 가지 역할만 맡아야 한다.
  • 변경의 이유 : 클래스를 변경하는 이유는 오직 하나여야 한다.
  • 효과 : 역할이 나뉘어 있으면 한 곳을 수정해도 다른 곳에 영향을 주지 않아 응집도(Cohesion)는 높아지고 결합도(Coupling)는 낮아진다.
✕ BAD · 책임 혼재
class Report {
    private List<Item> items;

    // 책임 1 : 데이터 계산
    public int calculateTotal() {
        return items.stream()
            .mapToInt(Item::getPrice)
            .sum();
    }

    // 책임 2 : 파일 저장 (다른 이유로 변경됨)
    public void saveToFile(String path) {
        // 파일 IO 로직...
    }

    // 책임 3 : 출력 형식 (또 다른 이유로 변경됨)
    public String toHtml() {
        return "<div>" + calculateTotal() + "</div>";
    }
}
✓ GOOD · 책임 분리
class Report {
    private List<Item> items;
    public List<Item> getItems() { return items; }
}

// 책임 1만 전담
class ReportCalculator {
    public int total(Report r) {
        return r.getItems().stream()
            .mapToInt(Item::getPrice).sum();
    }
}

// 책임 2만 전담
class ReportSaver {
    public void save(Report r, String path) { ... }
}

// 책임 3만 전담
class ReportHtmlPrinter {
    public String print(Report r) { ... }
}
문제점계산 로직 수정 시 → 저장·출력 코드까지 재컴파일 위험 / 테스트 작성 시 3가지 관심사 동시 고려 필요
개선 효과클래스당 변경 이유 1개 → 영향 범위 최소화 / 각 클래스 독립적 테스트 가능

O Open-Closed Principle

개방-폐쇄 원칙

  • 확장(Open) : 새로운 기능 요구사항이 생길 때, 새로운 클래스를 추가하여 기능을 쉽게 확장할 수 있어야 한다.
  • 폐쇄(Closed) : 기능을 확장하더라도 기존의 핵심 코드는 수정하지 않아야 한다.
  • 핵심 도구 : 다형성(Polymorphism)과 추상화(인터페이스)를 활용하여 기능을 갈아끼울 수 있는 유연한 구조를 만든다.
✕ BAD · 조건문 확장
class DiscountService {
    public int discount(String type, int price) {
        if (type.equals("FIXED")) {
            return price - 1000;
        } else if (type.equals("RATE")) {
            return price - (price * 10 / 100);
        }
        // 새 할인 정책 추가 시 → 이 메서드 계속 수정!
        return price;
    }
}
✓ GOOD · 인터페이스 확장
interface DiscountPolicy {
    int apply(int price);
}

class FixedDiscount implements DiscountPolicy {
    public int apply(int price) { return price - 1000; }
}

class RateDiscount implements DiscountPolicy {
    public int apply(int price) { return price - (price*10/100); }
}

// 신규 정책 추가 → 기존 코드 무변경
class VipDiscount implements DiscountPolicy {
    public int apply(int price) { return price / 2; }
}

class DiscountService {
    public int discount(DiscountPolicy p, int price) {
        return p.apply(price);
    }
}
문제점정책 추가할 때마다 → if-else 분기 무한 증가 / 기존 테스트 회귀 위험 상승
개선 효과DiscountService 코드 → 한 줄도 수정 안 됨 / 신규 클래스 추가만으로 확장 완료

L Liskov Substitution Principle

리스코프 치환 원칙

  • 대체 가능성(Substitutability) : 부모 클래스의 인스턴스를 자식 클래스의 인스턴스로 대체해도 프로그램의 의미는 변하지 않고 문제없이 동작해야 한다.
  • 계약 준수 : 자식 클래스는 부모 클래스가 정의한 메서드의 원래 의도(사전 조건, 사후 조건 등)를 깨뜨려서는 안 된다.
  • 위반 신호 : 하위 타입에서 부모의 메서드를 무시하거나 강제로 예외(UnsupportedOperationException 등)를 던지는 경우가 대표적인 위반 사례다.
✕ BAD · 계약 위반
class Bird {
    public void fly() {
        // 날아오르는 기본 동작
    }
}

class Sparrow extends Bird { }

class Penguin extends Bird {
    public void fly() {
        throw new UnsupportedOperationException(
            "펭귄은 못 날아요");
    }
}

// 클라이언트 코드에서...
void letThemFly(List<Bird> birds) {
    for (Bird b : birds) b.fly(); // 펭귄 만나면 예외!
}
✓ GOOD · 계층 재설계
abstract class Bird {
    abstract void move();
}

interface Flyable {
    void fly();
}

class Sparrow extends Bird implements Flyable {
    void move() { fly(); }
    public void fly() { /* 날기 */ }
}

// 못 나는 새는 애초에 Flyable 미구현
class Penguin extends Bird {
    void move() { swim(); }
    void swim() { /* 헤엄치기 */ }
}

// 이제 컴파일 단계에서 fly() 오용 자체가 불가능
문제점부모 타입만 믿고 호출한 코드 → 런타임 예외로 붕괴 / 다형성 신뢰 깨짐
개선 효과기능 없는 하위 타입에 억지 구현 강요 X → 계층 구조 자체가 계약을 보장

I Interface Segregation Principle

인터페이스 분리 원칙

  • 특화된 인터페이스 : 범용적인 큰 인터페이스 하나보다, 클라이언트 목적에 맞게 분리된(Segregated) 여러 개의 인터페이스가 낫다.
  • 불필요한 의존 금지 : 클래스는 자신이 사용하지 않는 메서드에 의존하도록 강요받아서는 안 된다.
  • 효과 : 인터페이스를 작게 나누면 불필요한 구현 부담이 사라져 결합도(Coupling)를 낮추고 유연성을 확보할 수 있다.
✕ BAD · 뚱뚱한 인터페이스
interface Worker {
    void work();
    void eat();
    void sleep();
}

class HumanWorker implements Worker {
    public void work() { /* 근무 */ }
    public void eat()  { /* 식사 */ }
    public void sleep(){ /* 휴식 */ }
}

// 로봇은 밥도 안 먹고 잠도 안 자는데...
class RobotWorker implements Worker {
    public void work() { /* 작업 */ }
    public void eat() {
        throw new UnsupportedOperationException();
    }
    public void sleep() {
        throw new UnsupportedOperationException();
    }
}
✓ GOOD · 인터페이스 분리
interface Workable { void work(); }
interface Eatable   { void eat(); }
interface Sleepable { void sleep(); }

class HumanWorker
        implements Workable, Eatable, Sleepable {
    public void work()  { /* 근무 */ }
    public void eat()   { /* 식사 */ }
    public void sleep() { /* 휴식 */ }
}

// 로봇은 필요한 인터페이스만 구현
class RobotWorker implements Workable {
    public void work() { /* 작업 */ }
}
문제점사용 안 할 메서드까지 구현 강제 → 빈 구현체 또는 예외 남발
개선 효과필요한 기능 단위로만 구현 → 불필요한 결합 제거

D Dependency Inversion Principle

의존관계 역전 원칙

  • 추상화에 의존 : 변하기 쉬운 구체 클래스(Concrete Class)에 직접 의존하지 말고, 변하지 않는 인터페이스(추상화)에 의존해야 한다.
  • 의존성 역전(Inversion) : 상위 모듈과 하위 모듈 모두 추상화에 의존함으로써, 제어의 흐름이나 의존 방향을 유연하게 뒤집는다.
  • 효과 : 구현체를 외부에서 주입(Dependency Injection)받아 언제든 쉽게 교체할 수 있는 확장성 높은 시스템이 된다.
✕ BAD · 구현체 직접 의존
class MySqlOrderRepository {
    public void save(Order order) {
        // MySQL 저장 로직
    }
}

class OrderService {
    // 구체 클래스를 직접 new → 강한 결합
    private MySqlOrderRepository repository
            = new MySqlOrderRepository();

    public void order(Order order) {
        repository.save(order);
    }
    // MongoDB로 교체하려면 → 이 클래스 코드 수정 필수
}
✓ GOOD · 추상화에 의존
interface OrderRepository {
    void save(Order order);
}

class MySqlOrderRepository implements OrderRepository {
    public void save(Order order) { /* MySQL */ }
}

class MongoOrderRepository implements OrderRepository {
    public void save(Order order) { /* Mongo */ }
}

class OrderService {
    private final OrderRepository repository;

    // 생성자 주입 → 구현체는 외부에서 결정 (DI)
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public void order(Order order) {
        repository.save(order);
    }
}
