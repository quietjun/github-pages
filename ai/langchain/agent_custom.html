LangGraph Custom Agent & Conditional Edge Part 2: 커스텀 에이전트 설계 및 의사결정 제어

"Prebuilt 헬퍼(create_react_agent)를 사용하지 않고, StateGraph와 Conditional Edge를 활용하여 의사결정 뼈대(Plan)를 100% 직접 커스터마이징 설계하는 프로세스를 정리한다."

1. StateGraph를 이용한 Direct Graph (Thought ➔ Action)

🗺️

StateGraph 상태 그래프 오케스트레이터

에이전트의 전체 비즈니스 흐름을 노드(Node)와 엣지(Edge)의 결합으로 구조화하고, 스텝마다 누적 및 갱신되는 상태(State) 객체의 데이터 연결망을 총괄 제어하는 프레임워크의 핵심 클래스이다. Direct Graph를 포함한 모든 LangGraph 아키텍처는 이 StateGraph 위에서 동일하게 상태를 공유하며 동작한다.

🗺️ Direct Graph 패턴 (선형 체인) 시각화

Direct Graph(선형 체인) 패턴은 LLM의 판단 결과에 따른 동적 루핑이나 조건부 분기 없이, START 진입 후 Agent가 동작하고 무조건 지정된 Tools를 실행한 뒤 작업이 종료(END)되는 단순한 선형 그래프 구조이다.

💻 Direct Graph (단순 선형 체인) 구현 예시 코드

from langgraph.graph import StateGraph, START, END

# 1. StateGraph 선언 및 노드 추가
workflow = StateGraph(AgentState)
workflow.add_node("agent", call_model)
workflow.add_node("tools", tool_node)

# 2. 진입점 설정 및 단순 엣지(Edge) 무조건 순차 연결
workflow.add_edge(START, "agent")     # START 노드에서 agent 노드로 진입
workflow.add_edge("agent", "tools")   # 조건 판단 없이 무조건 tools로 제어권 이동
workflow.add_edge("tools", END)        # 도구 실행 후 무조건 최종 종료

# 3. 그래프 컴파일
app = workflow.compile()

2. 커스텀 의사결정 분기 메커니즘 기반의 ReAct Graph (Thought ➔ Action ➔ Observation)

개발자가 업무 도메인 로직이나 예외 처리를 정밀 제어하기 위해서는 그래프의 노드와 조건부 엣지를 직접 매핑하여 흐름을 통제해야 한다. LLM이 반환하는 도구 호출 정보 유무에 기반해 분기를 결정하는 구성요소는 다음과 같다.

🔄

Conditional Edge 조건부 의사결정 분기 뼈대

라우터 함수의 판별 결과를 수신하여 다음에 호출할 그래프 노드 경로(예: 다음 도구 노드 구동 또는 최종 종결 END)를 런타임에 동적으로 결정한다. ReAct Graph 패턴의 자율적인 순환과 분기 제어를 가능하게 만드는 핵심 축이다.

🗺️ LangGraph 커스텀 빌드 아키텍처 및 자율 순환 흐름

• Router (should_continue) LLM이 반환한 도구 호출 정보 유무를 해석하여 "tools" 또는 "END" 경로 문자열을 반환하는 제어 함수
• Conditional Edge (조건부 분기선) 라우터의 반환값에 매핑되는 노드로 실행 제어권을 즉각 점프시켜 주는 유동적 조건 분기 링크
• State Feedback Loop (순환 루프) 도구 노드(tools)의 실행 결과를 상태에 업데이트한 뒤, 다시 agent 노드로 회귀해 지속 판별하게 만드는 피드백 추론 고리

3. should_continue 라우터 및 조건부 엣지 구현

LangGraph 내부에서 조건부 분기 처리를 구현하는 실전 파이썬 코드이다. 라우팅 조건부 엣지를 그래프에 연결하여 자율 순환 루프를 완성한다.

💻 라우터 함수(should_continue) 및 조건부 엣지 바인딩 실전 코드

from langgraph.graph import StateGraph, START, END

# 1. 의사결정을 관장하는 라우터(Router) 함수 정의
def should_continue(state):
    last_message = state["messages"][-1]
    
    # LLM의 마지막 메시지에 외부 도구 호출(tool_calls) 지시가 포함되어 있는지 판단
    if last_message.tool_calls:
        return "tools"   # 도구 호출이 필요하면 tools 노드로 분기
    return "end"         # 도구 호출 지시가 없으면 최종 대화 종료

# 2. StateGraph 생성 및 노드 등록
workflow = StateGraph(AgentState)
workflow.add_node("agent", call_model)
workflow.add_node("tools", tool_node)

# 3. 에이전트 시작 진입점(Entry Point) 설정
workflow.add_edge(START, "agent")     # START 노드에서 agent 노드로 진입

# 4. 의사결정 분기 뼈대(Conditional Edge) 추가 (핵심)
workflow.add_conditional_edges(
    "agent",            # 분기 판단을 시작할 출발 노드
    should_continue,    # 다음 진행 노드를 결정할 라우터 함수
    {
        "tools": "tools",   # should_continue가 "tools" 리턴 시 tools 노드 실행
        "end": END          # should_continue가 "end" 리턴 시 작업 종료
    }
)

# 5. 도구 실행 완료 후 다시 agent 노드로 되돌아가는 순환 엣지 추가
workflow.add_edge("tools", "agent")

# 6. 그래프 컴파일
app = workflow.compile()

4. 설계 패턴 비교: Direct Graph vs ReAct Graph

단순 고정형 파이프라인에는 Direct Graph가 구조적으로 가볍고 예측이 명확하지만, 비정형 요청이나 에러 상황에서 LLM이 스스로 판단하여 동적으로 도구를 다시 구동하는 환류 루프(Feedback Loop) 처리를 하려면 조건부 엣지가 결합된 ReAct Graph 패턴이 필수적이다.

⚖️ 두 아키텍처의 핵심 속성 비교

비교 항목 Direct Graph 패턴 ReAct Graph 패턴
동작 모델 선형 체인 (DAG, 순차적인 단방향 흐름) 순환 그래프 (Node & Edge 기반 순환)
실행 경로 사전에 정해진 순서대로 실행 (A ➔ B ➔ 끝) Thought-Action 결과에 따라 경로가 동적으로 결정
복잡한 요청 대응 불가 (예상 밖의 시나리오 대응 한계) 가능 (오류 복구 및 조건부 루프 처리 최적화)
구현 복잡도 낮음 (구현 및 직관적 예측 용이) 높음 (Edge 설계 및 상태 관리 튜닝 필요)
권장 상황 단순 서류 추출, 정형화된 ETL 파이프라인 고객 상담 챗봇, 문제 해결형 분석 에이전트

5. 강의 핵심 요약

  • StateGraph 중심 뼈대: 노드(Node), 엣지(Edge), 상태(State) 결합을 통한 오케스트레이션 수행
  • Direct Graph 패턴: 조건부 분기 없이 START ➔ agent ➔ tools ➔ END로 직진하는 선형 체인 구조
  • Conditional Edge 분기: 라우터 함수(should_continue)가 도구 호출 여부를 판별하여 tools 또는 END로 동적 점프
  • ReAct 환류 루프: tools 실행 결과를 상태에 갱신하고 agent로 회귀하여 자율적 복구 및 문제 해결 가능
