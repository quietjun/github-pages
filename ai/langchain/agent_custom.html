LangGraph Custom Agent & Conditional Edge Part 2: 커스텀 에이전트 설계 및 의사결정 제어

"이번 포스트에서는 Prebuilt 헬퍼(create_react_agent)를 사용하지 않고, StateGraph와 Conditional Edge를 활용하여 의사결정 뼈대(Plan)를 100% 직접 커스터마이징 설계하는 방법을 실습한다."
01

커스텀 의사결정 분기 메커니즘

개발자가 복잡한 업무 도메인 로직이나 예외 처리를 정밀 제어하기 위해서는 그래프의 노드와 조건부 엣지를 직접 매핑하여 흐름을 통제해야 한다. LLM이 반환하는 도구 호출 정보 유무에 기반해 분기를 결정하는 설계 구성요소는 다음과 같다.

🛡️ Framework Core Backbone (양대 핵심 뼈대)
🗺️

StateGraph 상태 그래프 오케스트레이터

에이전트의 전체 비즈니스 흐름을 노드(Node)와 엣지(Edge)의 결합으로 구조화하고, 스텝마다 누적 및 갱신되는 상태(State) 객체의 데이터 연결망을 총괄 제어하는 프레임워크의 중심 뼈대 클래스이다.

🔄

Conditional Edge 조건부 의사결정 분기

라우터 함수의 판별 결과를 수신하여 다음에 호출할 그래프 노드 경로(예: 다음 도구 노드 구동 또는 최종 종결 END)를 런타임에 동적으로 결정한다.

🗺️ LangGraph 커스텀 빌드 아키텍처 및 자율 순환 흐름
• Router (should_continue) LLM이 반환한 도구 호출 정보 유무를 해석하여 "tools" 또는 "END" 경로 문자열을 반환하는 제어 함수이다.
• Conditional Edge (조건부 분기선) 라우터의 반환값에 매핑되는 노드로 실행 제어권을 즉각 점프시켜 주는 유동적 조건 분기 링크이다.
• State Feedback Loop (순환 루프) 도구 노드(tools)의 실행 결과를 상태에 업데이트한 뒤, 다시 agent 노드로 회귀해 지속 판별하게 만드는 피드백 추론 고리이다.
⚙️ Operational Mechanics (실제 작동 동작)
🧭
Router Function should_continue

에이전트의 현재 상태를 파싱해 도구 호출 지시 유무에 따라 다음 행선지 노드 이름을 판별해 반환하는 라우팅 함수이다.

🕹️
Control Flow 제어 구조 설계

단방향 체인을 탈피하여 에러 발생 시 피드백 및 롤백 루프를 그래프 선로 위에 유연하게 탑재하는 순환 제어 흐름이다.

📥
State Transition 의사결정 상태 전이

분기 결정이 종료된 후 갱신된 메시지 정보와 상태값을 다음 타겟 노드로 누락 없이 전송하는 상태 업데이트 전이이다.

02

should_continue 라우터 및 조건부 엣지 구현

LangGraph 내부에서 조건부 분기 처리를 구현하는 실전 파이썬 코드이다. 라우팅 조건부 엣지를 그래프에 연결하여 자율 순환 루프를 완성한다.

💻 라우터 함수(should_continue) 및 조건부 엣지 바인딩 실전 코드
from typing import Literal from langgraph.graph import StateGraph, END # 1. 의사결정을 관장하는 라우터(Router) 함수 정의 def should_continue(state) -> Literal["tools", "__end__"]: messages = state["messages"] last_message = messages[-1] # LLM의 마지막 메시지에 외부 도구 호출(tool_calls) 지시가 포함되어 있는지 판단 if last_message.tool_calls: return "tools" # 도구 호출이 필요하면 tools 노드로 분기 return END # 도구 호출 지시가 없으면 최종 대화 종료 # 2. StateGraph 생성 및 노드 등록 workflow = StateGraph(AgentState) workflow.add_node("agent", call_model) workflow.add_node("tools", tool_node) # 3. 에이전트 시작 진입점(Entry Point) 설정 workflow.set_entry_point("agent") # 4. 의사결정 분기 뼈대(Conditional Edge) 추가 (핵심) workflow.add_conditional_edges( "agent", # 분기 판단을 시작할 출발 노드 should_continue, # 다음 진행 노드를 결정할 라우터 함수 { "tools": "tools", # should_continue가 "tools" 리턴 시 tools 노드 실행 "__end__": END # should_continue가 "__end__" 리턴 시 작업 종료 } )
03

에이전트 구현 및 설계 패턴 비교

문제 요구사항의 복잡도에 따라 채택할 수 있는 그래프 아키텍처 패턴 분석이다.

// Direct Graph vs ReAct Graph 패턴 시각화
Direct Graph 패턴 (선형 체인) 사전에 배치된 순서대로 일직선 동작 후 즉시 종료
ReAct Graph 패턴 (순환 루프) Thought 결과에 따라 경로를 유기적으로 반복 판단

단순 고정형 파이프라인에는 Direct Graph가 구조적으로 가볍고 예측이 명확하며, 비정형 태스크나 조건부 롤백 처리가 동적으로 필요한 경우에는 ReAct Graph가 견고한 대안이다.

비교 항목Direct Graph 패턴ReAct Graph 패턴
동작 모델선형 체인 (DAG, 순차적인 단방향 흐름)순환 그래프 (Node & Edge 기반 순환)
실행 경로사전에 정해진 순서대로 실행 (A ➡️ B ➡️ 끝)Thought-Action 결과에 따라 경로가 동적으로 결정
복잡한 요청 대응불가 (예상 밖의 시나리오 대응의 한계)가능 (오류 복구 및 조건부 루프 처리 최적화)
구현 복잡도낮음 (구현 및 직관적 예측 용이)높음 (Edge 설계 및 상태 관리 튜닝 필요)
권장 상황단순 서류 추출, 정형화된 ETL 파이프라인고객 상담 챗봇, 문제 해결형 분석 에이전트
