Multi-Agent Collaboration Patterns Multi-Agent 시스템 협업 및 대표 디자인 패턴

복잡한 대규모 태스크를 단일 에이전트가 처리할 때 발생하는 정보 누락을 방지하고, 에이전트 간 역할 분담(Role-based Division)과 상태 공유(State Graph)를 통해 고품질 결과를 창출하는 다중 에이전트 협업 아키텍처이다.

"LangGraph 기반의 Planner-Worker 패턴, Reflection 패턴 및 Supervisor/Debate/Hierarchical 등 고급 멀티 에이전트 협업 디자인 패턴을 분석하고 구현한다."

1. 단일 Agent의 한계와 Multi-Agent 시스템의 필요성

단일 에이전트(Single Agent)는 페르소나와 도구(Tool) 목록이 복잡해질수록 다음과 같은 3가지 치명적인 한계점에 직면한다.

⚠️

1. 콘텍스트 과부하

너무 많은 도구 명세와 프롬프트 주입 시 LLM이 중요한 지시 사항을 누락함

🎯

2. 집중도 분산

계획 수립, 연산, 텍스트 생성을 한 번에 수행하여 출력물의 디테일이 저하됨

🌀

3. 오작동 및 무한루프

단일 추론 루프에서 도구 호출 판단 꼬임 시 스스로 정상 경로 이탈 현상 심화

💡 Multi-Agent 시스템 솔루션: 복잡한 문제를 여러 개의 작은 역할(Role)로 세분화하고, 각 역할을 전담하는 에이전트들을 StateGraph 상의 독립 노드로 정의하여 협업 구조로 풀어낸다.

2. Multi-Agent 핵심 패턴 설계 및 구현

각 패턴별 특징과 SVG 다이어그램, 그리고 실전 파이썬 소스코드를 탭으로 선택하여 대조한다.

계획 수립과 세부 실행을 물리적으로 분리하는 패턴이다. Planner는 상위 마일스톤(Plan)만 정의하고, Worker는 오직 계획 내용에만 집중하여 구체적 실행 결과를 서술한다.

💻 Planner-Worker 파이썬 구현 소스코드

from langgraph.graph import StateGraph, START, END
from typing import TypedDict, List

# 1. 협업 노드들이 공유할 상태구조 정의
class AgentState(TypedDict):
    user_request: str     # 사용자 질문
    plan: str             # Planner의 수립 계획
    result: str           # Worker의 실행 결과물
    reflection: str       # Reflection 검토 피드백
    final_result: str     # 최종 출력물
    reflection_count: int # 피드백 반복 횟수
    messages: List[dict]  # 에이전트 간 대화 기록

# 2. Planner Node 구현
def planner_node(state: AgentState) -> AgentState:
    print("📋 [Planner Agent] 계획 수립 중...")
    user_request = state["user_request"]
    planner_prompt = f"사용자 요청 {user_request}에 대해 실행 가능한 단계별 계획(Step 1, Step 2...)만 세워주세요."
    
    response = llm.invoke(planner_prompt)
    plan = response.content
    
    messages = state.get("messages", [])
    messages.append({"sender": "Planner", "content": plan})
    return {"plan": plan, "messages": messages}

# 3. Worker Node 구현
def worker_node(state: AgentState) -> AgentState:
    print("⚙️ [Worker Agent] 계획 실행 중...")
    plan = state["plan"]
    user_request = state["user_request"]
    worker_prompt = f"계획:\n{plan}\n\n위 계획의 각 단계를 구체적으로 실행하여 상세 결과를 도출하세요."
    
    response = llm.invoke(worker_prompt)
    result = response.content
    
    messages = state.get("messages", [])
    messages.append({"sender": "Worker", "content": result})
    return {"result": result, "messages": messages}

# 4. Planner-Worker 그래프 빌드
workflow = StateGraph(AgentState)
workflow.add_node("planner", planner_node)
workflow.add_node("worker", worker_node)

workflow.add_edge(START, "planner")
workflow.add_edge("planner", "worker")
workflow.add_edge("worker", END)

app = workflow.compile()

Worker가 완료한 결과물을 검토 노드(Reflection)로 라우팅하여 자율적으로 교정 피드백을 주는 구조이다. 의사결정 라우터 함수가 검토 결과를 보고 통과시키거나, 보완이 요구되면 다시 Worker로 돌려보내는 루프를 형성한다.

💻 Reflection Node 및 조건 분기 워크플로우 파이썬 코드

# 1. Reflection Node 구현
def reflection_node(state: AgentState) -> AgentState:
    print("🔍 [Reflection Agent] 결과 검토 중...")
    user_request = state["user_request"]
    plan = state["plan"]
    result = state["result"]
    count = state.get("reflection_count", 0)
    
    reflection_prompt = f"""
    원본 요청: {user_request}
    실행 계획: {plan}
    Worker의 실행 결과: {result}
    
    위 결과가 원본 요청을 충족하는지 검토하고 개선 필요 항목을 정리하세요.
    [형식]
    ## 검토 결과
    - 충족 여부: [충족/부분 충족/미충족]
    - 개선 필요: [피드백 내용]
    """
    
    response = llm.invoke(reflection_prompt)
    reflection = response.content
    
    messages = state.get("messages", [])
    messages.append({"sender": "Reflection", "content": reflection})
    
    return {
        "reflection": reflection,
        "final_result": reflection,
        "reflection_count": count + 1,
        "messages": messages
    }

# 2. 루핑 제어용 조건부 분기 함수 정의
def should_continue_reflection(state: AgentState) -> str:
    count = state.get("reflection_count", 0)
    reflection = state.get("reflection", "")
    
    if count >= 1: # 무한루프 방지를 위해 1회 검토 제한 설정
        return "end"
    if "충족 여부: 충족" in reflection:
        return "end"
    return "worker"

# 3. Reflection 패턴 워크플로우 구성 및 엣지 바인딩
workflow_reflection = StateGraph(AgentState)
workflow_reflection.add_node("planner", planner_node)
workflow_reflection.add_node("worker", worker_node)
workflow_reflection.add_node("reflection", reflection_node)

workflow_reflection.add_edge(START, "planner")
workflow_reflection.add_edge("planner", "worker")
workflow_reflection.add_edge("worker", "reflection")

# 조건부 엣지 등록: 검토 결과에 따라 Worker 재구동 또는 완료
workflow_reflection.add_conditional_edges(
    "reflection",
    should_continue_reflection,
    {
        "end": END,
        "worker": "worker"
    }
)

app_reflection = workflow_reflection.compile()

Planner-Worker vs Reflection 패턴 비교

프로젝트 아키텍처 요구 조건에 가장 적합한 멀티에이전트 패턴 구성을 판단하기 위한 기술적 대조 지표이다.

비교 항목 Planner-Worker 패턴 Reflection 패턴
의사결정 흐름 질문 ➔ 계획(Plan) 수립 ➔ 전체 실행 및 종료 선형 계획 수립 ➔ 실행 ➔ 자율 평가(피드백) ➔ 재실행 루프 순환형
제어 분기 메커니즘 조건부 분기 없음 (무조건 순차 제어) 라우터(should_continue) 함수에 의거한 조건부 분기 판단 필수
최대 장점 역할 분담으로 단일 LLM의 콘텍스트 부하 방지 및 속도 향상 자기 검토를 통한 피드백 환류로 최종 출력물의 품질 극대화
적합 테스크 절차가 명확하고 자율적 교정이 필수적이지 않은 작업 보고서 작성, 프로그래밍 코드 작성, 법률 검토 등 엄격 교정 작업

단순한 선형/환류 워크플로우를 넘어 복잡하고 유동적인 의사결정 체계를 가동하기 위한 고급 멀티에이전트 패턴 설계 방식이다.

1. Supervisor 패턴 (중앙 조정 제어)

중앙의 조정자(Supervisor LLM)가 현재 상태를 실시간 검토하여 다음에 실행할 전문 에이전트(Worker)를 동적으로 선별하는 Star(별 모양) 아키텍처이다.

2. Debate/Discussion 패턴 (상호 토론 및 합의)

서로 다른 페르소나나 판단 원칙(예: 찬성 vs 반대)을 가진 독립 에이전트들이 라운드 테이블식으로 의견을 순환 개진하며 LLM의 편향성을 자율 교정해 나가는 구조이다.

3. Hierarchical 패턴 (계층적 관리 구조)

중앙 최고 결정권자(Director) 산하에 독립 지휘망을 가진 중간 관리자(Team Lead Supervisor)를 배치하고, 그 산하에 실무 Worker들을 격리 배치하여 대규모 복합 태스크를 회사 조직화 형태로 수행하는 최상위 계층 구조이다.

3. 강의 핵심 요약

  • Multi-Agent 필연성: 콘텍스트 과부하 및 집중도 분산을 방지하기 위한 전문 역할 분담 아키텍처
  • Planner-Worker: 상위 계획 수립(Planner)과 세부 실행(Worker)을 물리적으로 이원화한 선형 파이프라인
  • Reflection 패턴: 검토 노드의 교정 피드백과 라우터 조건부 엣지를 결합하여 고품질 재실행 루프 형성
  • 고급 아키텍처: 동적 지휘(Supervisor), 편향 교정 토론(Debate), 대규모 조직형 계층(Hierarchical) 패턴으로 확장
