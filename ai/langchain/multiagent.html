Multi-Agent Collaboration Patterns Part 4: Multi-Agent 시스템 협업 및 대표 패턴

"복잡하고 방대한 테스크를 마주했을 때, 단일 에이전트는 성능 한계와 정보 누락을 보입니다. 이번 포스트에서는 LangGraph를 기반으로 계획과 실행을 이원화하는 Planner-Worker 패턴 및 결과의 완결성을 높이는 Reflection 패턴을 학습합니다."
01

단일 Agent의 한계와 Multi-Agent 시스템의 필요성

단일 에이전트(Single Agent)는 페르소나와 도구(Tool) 목록이 복잡해질수록 다음과 같은 치명적인 성능 저하를 겪는다.

  • 콘텍스트 과부하: 너무 많은 도구 명세와 긴 프롬프트가 주입되어 LLM이 중요한 지시 사항을 누락하는 현상 발생
  • 집중도 분산: 계획 수립, 예산 연산, 결과 텍스트 구체화 등 다양한 테스크를 한 번에 하려다 보니 결과물의 디테일 저하
  • 오작동 및 무한루프: 단일 추론 루프 안에서 도구 호출 판단이 꼬였을 때 스스로 정상 경로를 이탈하는 현상 심화

이에 대한 해결책이 Multi-Agent(다중 에이전트) 시스템이다. 복잡한 문제를 여러 개의 작은 역할(Role)로 세분화하고, 각 역할을 전담하는 에이전트들을 StateGraph 상의 노드로 정의하여 협업 구조로 풀어낸다.

💡 Multi-Agent 대표 디자인 패턴
  • Planner-Worker: 계획 수립자(Planner)가 일의 절차를 정하면, 실행자(Worker)가 각 단계를 개별 완료하는 선형 구조
  • Reflection: 생성자(Worker)의 출력물을 검토자(Reflection)가 정교하게 채점하고, 피드백을 통해 품질 기준을 만족할 때까지 재수행하는 순환 루프 구조
  • Supervisor: 중앙의 조정자(Supervisor)가 다음으로 실행될 적절한 에이전트를 동적으로 매핑 및 호출하는 구조
02

Planner-Worker 패턴 구현 (Thought ➡️ Action)

계획 수립과 세부 실행을 물리적으로 분리하는 패턴이다. Planner는 상위 레벨의 마일스톤(Plan)만 정의하고, Worker는 오직 그 계획 내용에 집중하여 디테일한 정보를 서술하므로 결과의 완결성이 향상된다.

💻 Planner-Worker 패턴 상태(State) 및 노드 파이썬 코드
from langgraph.graph import StateGraph, START, END from typing import TypedDict, List # 1. 협업 노드들이 공유할 상태구조 정의 class AgentState(TypedDict): user_request: str # 사용자 질문 plan: str # Planner의 수립 계획 result: str # Worker의 실행 결과물 reflection: str # Reflection 검토 피드백 final_result: str # 최종 출력물 reflection_count: int # 피드백 반복 횟수 messages: List[dict] # 에이전트 간 대화 기록 # 2. Planner Node 구현 def planner_node(state: AgentState) -> AgentState: user_request = state["user_request"] planner_prompt = f"사용자 요청 {user_request}에 대해 실행 가능한 단계별 계획(Step 1, Step 2...)만 세워주세요." response = llm.invoke(planner_prompt) plan = response.content messages = state.get("messages", []) messages.append({"sender": "Planner", "content": plan}) return {**state, "plan": plan, "messages": messages} # 3. Worker Node 구현 def worker_node(state: AgentState) -> AgentState: plan = state["plan"] user_request = state["user_request"] worker_prompt = f"계획:\n{plan}\n\n위 계획의 각 단계를 구체적으로 실행하여 상세 결과를 도출하세요." response = llm.invoke(worker_prompt) result = response.content messages = state.get("messages", []) messages.append({"sender": "Worker", "content": result}) return {**state, "result": result, "messages": messages} # 4. Planner-Worker 그래프 빌드 workflow = StateGraph(AgentState) workflow.add_node("planner", planner_node) workflow.add_node("worker", worker_node) workflow.add_edge(START, "planner") workflow.add_edge("planner", "worker") workflow.add_edge("worker", END) app = workflow.compile()
03

Reflection 패턴 추가 (Thought ➡️ Action ➡️ Observation)

Worker가 완료한 결과물을 검토 노드(`Reflection`)로 라우팅하여 자율적으로 교정 피드백을 주는 구조이다. 의사결정 라우터 함수가 검토 결과를 보고 통과시키거나, 보완이 요구되면 다시 Worker로 돌려보내는 루프를 형성한다.

💻 Reflection Node 및 조건 분기 워크플로우 파이썬 코드
# 1. Reflection Node 구현 def reflection_node(state: AgentState) -> AgentState: user_request = state["user_request"] plan = state["plan"] result = state["result"] count = state.get("reflection_count", 0) reflection_prompt = f""" 원본 요청: {user_request} 실행 계획: {plan} Worker의 실행 결과: {result} 위 결과가 원본 요청을 충족하는지 검토하고 개선 필요 항목을 정리하세요. 최종 결과 보완 텍스트도 함께 기재하세요. [형식] ## 검토 결과 - 충족 여부: [충족/부분 충족/미충족] - 개선 필요: [피드백 내용] ## 최종 개선 결과 [개선 보완된 최종 결과] """ response = llm.invoke(reflection_prompt) reflection = response.content messages = state.get("messages", []) messages.append({"sender": "Reflection", "content": reflection}) return { **state, "reflection": reflection, "final_result": reflection, "reflection_count": count + 1, "messages": messages } # 2. 루핑 제어용 조건부 분기 함수 정의 def should_continue_reflection(state: AgentState) -> str: count = state.get("reflection_count", 0) reflection = state.get("reflection", "") if count >= 1: # 무한루프 방지를 위해 1회 검토 제한 설정 return "end" if "충족 여부: 충족" in reflection: return "end" return "worker" # 3. Reflection 패턴 워크플로우 구성 및 엣지 바인딩 workflow_reflection = StateGraph(AgentState) workflow_reflection.add_node("planner", planner_node) workflow_reflection.add_node("worker", worker_node) workflow_reflection.add_node("reflection", reflection_node) workflow_reflection.add_edge(START, "planner") workflow_reflection.add_edge("planner", "worker") workflow_reflection.add_edge("worker", "reflection") # 조건부 엣지 등록: 검토 결과에 따라 Worker 재구동 또는 완료 workflow_reflection.add_conditional_edges( "reflection", should_continue_reflection, { "end": END, "worker": "worker" } ) app_reflection = workflow_reflection.compile()
04

Planner-Worker vs Reflection 패턴 비교

프로젝트 아키텍처 요구 조건에 가장 적합한 멀티에이전트 패턴 구성을 판단하기 위한 기술적 대조 지표이다.

비교 항목 Planner-Worker 패턴 Reflection 패턴
의사결정 흐름 사용자 질문 ➡️ 계획(Plan) 수립 ➡️ 전체 실행 및 종료 (선형) 계획 수립 ➡️ 실행 ➡️ 자율 평가(피드백) ➡️ 재실행 루프 (순환형)
제어 분기 메커니즘 조건부 분기 없음 (무조건 순차 제어) 라우터(`should_continue`) 함수에 의거한 조건부 분기 판단 필수
최대 장점 역할의 분담으로 단일 LLM의 콘텍스트 부하 방지 및 속도 향상 자기 검토를 통한 피드백 환류로 최종 출력물의 품질 극대화
적합 테스크 절차가 명확하고 복잡하지만, 자율적 교정이 필수적이지 않은 작업 보고서 작성, 프로그래밍 코드 작성, 법률 검토 등 엄격한 교정이 핵심인 작업
