AI AGENT ARCHITECTURE & DESIGN

목표를 향해 스스로 판단하고
행동하는 AI 에이전트(Agent)

AI 에이전트는 단순한 텍스트 응답 모델을 넘어, 주어진 목표를 달성하기 위해 적절한 도구를 선택(Tool-use)하고, 대화 맥락을 기억(Memory)하며, 사고 및 행동 과정(Plan/ReAct)을 자율적으로 설계하여 문제를 해결하는 시스템이다.

01

AI 에이전트의 4대 핵심 구성요소 (Core Components)

주어진 목표를 완수하기 위해 유기적으로 결합되어 동작하는 에이전트 아키텍처의 네 가지 핵심 기둥

🧠

LLM Brain (의사결정)

자연어 질문을 해석하고 문제를 단계별로 풀기 위한 최종 의사결정을 수행한다. (발전 흐름: 자연어 대화는 가능하나 시스템 외부 동작 및 정보 탐색 권한이 없는 정적 모델 단계)

부재 시: 의사소통 및 고차원적인 상황 판단 자체가 불가능하다.
🛠️

Tool Action (행동실행)

외부 DB 조회(RAG), API 호출 등 LLM의 지식 한계를 극복하여 현실적인 행동을 대행한다. (발전 흐름: 실시간 도구 연동을 통해 외부 시스템 조작 및 최신 지식 검색이 가능해진 단계)

부재 시: 실제 시스템 조작이 불가능하며 할루시네이션을 남발한다.
💾

Memory Context (맥락유지)

대화 히스토리 및 작업 세션 정보를 기억하여 멀티스텝 수행 과정에서 대화 흐름을 유지한다. (발전 흐름: 단발성 질의를 넘어 앞서 진행된 맥락과 세션 상태 체크포인트를 기억하는 단계)

부재 시: 주문번호 등 이전 대화에서 공유된 정보를 기억하지 못한다.
🧭

Plan Strategy (사고설계)

복잡한 사용자 요구사항을 달성하기 위해 자율적인 단계별 추론 및 도구 사용 순서를 설계한다. (발전 흐름: 관찰(Observation) 피드백에 기반해 사고(Thought)와 행동(Action)을 동적으로 설계하는 단계)

부재 시: 멀티스텝 작업 중 쉽게 무한 루프에 빠지거나 처리 순서가 꼬인다.
// 도구 바인딩 메커니즘과 독스트링의 비밀 (Tool Binding & Docstring)

LLM에 도구를 바인딩할 때 파이썬 함수에 작성하는 **독스트링(Docstring)과 타입 힌트**는 단순 주석이 아니라, AI의 판단을 제어하는 고도의 **프롬프트 엔지니어링**으로 작동합니다.

1. 함수 독스트링 (Docstring) 파이썬 함수의 """설명문"""은 JSON Schema의 description 필드로 자동 변환되어 LLM이 도구 사용 여부를 판단하는 핵심 기준이 됩니다.
2. 매개변수 타입 힌트 인자의 타입 지정(예: str, int)은 스키마의 type 정의로 맵핑되어 LLM이 도구 호출 시 규격에 맞는 형식의 데이터만 채워 넣도록 제한합니다.
3. 인자 설명 (Parameter Description) 독스트링 내의 Args: parameter_name: 설명 형식은 각 파라미터의 역할 정보로 맵핑되어 LLM이 어떤 형식의 세부 데이터를 넣어야 하는지 가이드합니다.
4. 프롬프트 제어 효과 도구가 불필요하게 자주 호출되거나 오작동할 때, 코드를 고치기보다 독스트링 내 예시나 제약 조건을 상세히 기술하여 AI의 행동을 교정할 수 있습니다.
02

ReAct (Reasoning + Acting) 프레임워크

추론(Thought)과 행동(Action)을 번갈아 수행하며, 관찰(Observation) 결과를 다음 추론에 반영하는 에이전트의 사고 아키텍처

ReAct 아키텍처 : 목표를 달성할 때까지 Thought → Action → Observation 루프를 순환 수행하며 노드가 강조됩니다.
⚡ INTERACTIVE MULTI-SCENARIO SIMULATOR

상황별 시나리오를 선택하여 에이전트의 사고 흐름과 도구 연동을 테스트합니다. 단계 진행 시 상단의 SVG 노드가 실시간 하이라이트됩니다.

시나리오 선택 (Select Scenario)
시나리오 A: 단순 정책 조회 (1-Step)
"배송 지연 보상 규정이 어떻게 돼?"
시나리오 B: 복합 쿠폰 발급 (Multi-Step)
"ORD001, ORD002 상태 조회 후 지연 건에 보상 쿠폰 발행"
진행 상황: 대기 중
시작 버튼을 누르면 에이전트의 Thought-Action-Observation 루프가 시작된다.
03

에이전트 구현 및 설계 패턴 비교

문제 요구사항의 복잡도에 따라 채택할 수 있는 그래프 아키텍처 패턴 분석

// Direct Graph vs ReAct Graph 패턴 시각화
Direct Graph 패턴 (선형 체인) 사전에 배치된 순서대로 일직선 동작 후 즉시 종료
ReAct Graph 패턴 (순환 루프) Thought 결과에 따라 경로를 유기적으로 반복 판단

단순 고정형 파이프라인에는 Direct Graph가 구조적으로 가볍고 예측이 명확하며, 비정형 태스크나 조건부 롤백 처리가 동적으로 필요한 경우에는 ReAct Graph가 견고한 대안입니다.

비교 항목Direct Graph 패턴ReAct Graph 패턴
동작 모델선형 체인 (DAG, 순차적인 단방향 흐름)순환 그래프 (Node & Edge 기반 순환)
실행 경로사전에 정해진 순서대로 실행 (A ➡️ B ➡️ 끝)Thought-Action 결과에 따라 경로가 동적으로 결정
복잡한 요청 대응불가 (예상 밖의 시나리오 대응의 한계)가능 (오류 복구 및 조건부 루프 처리 최적화)
구현 복잡도낮음 (구현 및 직관적 예측 용이)높음 (Edge 설계 및 상태 관리 튜닝 필요)
권장 상황단순 서류 추출, 정형화된 ETL 파이프라인고객 상담 챗봇, 문제 해결형 분석 에이전트
04

Trustworthiness (신뢰성 및 가드레일) 아키텍처

실무 상용 에이전트 배포의 최우선 고려 조건: 검증과 다중 필터링 설계

🛡️ 안전하고 신뢰할 수 있는 에이전트 파이프라인 설계

자율성이 부여된 AI 에이전트는 예기치 못한 도구 호출 및 오동작을 일으킬 수 있다. 따라서 보안 정책 강제 검증 및 입출력 단계별 다중 필터 차단 가드레일 설계가 필수적이다.
