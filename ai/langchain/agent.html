AI AGENT ARCHITECTURE & DESIGN

목표를 향해 스스로 판단하고
행동하는 AI 에이전트(Agent)

AI 에이전트는 단순한 텍스트 응답 모델을 넘어, 주어진 목표를 달성하기 위해 적절한 도구를 선택(Tool-use)하고, 대화 맥락을 기억(Memory)하며, 사고 및 행동 과정(Plan/ReAct)을 자율적으로 설계하여 문제를 해결하는 시스템이다.

이번 포스트에서는 자율적인 의사결정 루프를 수행하는 AI 에이전트의 4대 핵심 구성요소와 ReAct 패턴의 개념을 이해하고 동작 방식을 시뮬레이션해 본다.
01

AI 에이전트의 4대 핵심 구성요소 (Core Components)

주어진 목표를 완수하기 위해 유기적으로 결합되어 동작하는 에이전트 아키텍처의 네 가지 핵심 기둥이다.

🧠

LLM Brain (의사결정)

자연어 질문 해석 및 단계별 문제 해결을 위한 최종 의사결정 수행. (발전 흐름: 외부 시스템 조작 및 탐색 권한이 배제된 정적 자연어 처리 단계)

부재 시: 대화 및 고차원적 의사결정 불가능.
🛠️

Tool Action (행동실행)

외부 DB 조회 및 API 호출을 통해 모델의 지식 한계를 극복하고 조치 대행. (발전 흐름: 실시간 외부 도구 호출 기반 시스템 동적 조작 및 검색 단계)

부재 시: 현실적인 시스템 조작 불가 및 할루시네이션 남발.
💾

Memory Context (맥락유지)

대화 이력 및 작업 세션 정보를 저장하여 다단계 수행 흐름 연속성 확보. (발전 흐름: 대화 맥락 유지 및 중간 체크포인트를 기억하는 상태 보존 단계)

부재 시: 대화 내에 이미 제공된 키값이나 맥락 인식 불가능.
🧭

Plan Strategy (사고설계)

자율적 단계별 추론 및 최적의 도구 활용 호출 순서를 설계하고 조율. (발전 흐름: 실행 결과 피드백에 입각해 생각과 행동을 동적으로 갱신하는 단계)

부재 시: 중첩 다단계 작업 시 무한 루프 진입 및 제어 오류 발생.
02

도구 바인딩(Tool Binding) 메커니즘 및 코드 대조

파이썬 함수의 독스트링과 타입 선언이 LLM 호출 규격서(JSON Schema)로 매핑되는 실제 예시이다.

1. 도구 이름 (Function Name)

파이썬 함수명(예: get_order_status)이 스키마의 name 필드로 매핑되어 LLM의 직접적인 호출 식별자로 활용됨.

2. 매개변수 타입 힌트

매개변수 타입(예: str, int)이 스키마의 type 정의로 맵핑되어 적합한 자료형 입력을 강제함.

3. 함수 독스트링 (Docstring)

함수 내부의 """설명문"""이 스키마의 description 필드가 되어 LLM이 도구 목적을 판별하는 프롬프트로 기동됨.

4. 인자 설명

독스트링 내의 Args: parameter: 설명 포맷이 인자 설명서로 매핑되어 각 인자의 입력 목적을 LLM에 가이드함.
# @tool 데코레이터 적용 from langchain_core.tools import tool @tool def get_order_status(order_id: str) -> str: """특정 주문의 배송 상태를 조회합니다. Args: order_id: 주문 번호 (예: ORD001) """ return "배송 지연"
{ "name": "get_order_status", "description": "특정 주문의 배송 상태를 조회합니다.", "parameters": { "type": "object", "properties": { "order_id": { "type": "string", "description": "주문 번호 (예: ORD001)" } }, "required": ["order_id"] } }
03

ReAct (Reasoning + Acting) 프레임워크

추론(Thought)과 행동(Action)을 번갈아 수행하며, 관찰(Observation) 결과를 다음 추론에 반영하는 에이전트의 사고 아키텍처이다.

ReAct 아키텍처 : 목표를 달성할 때까지 Thought → Action → Observation 루프를 순환 수행하며 노드가 강조됩니다.
⚡ INTERACTIVE MULTI-SCENARIO SIMULATOR

상황별 시나리오를 선택하여 에이전트의 사고 흐름과 도구 연동을 테스트합니다. 단계 진행 시 상단의 SVG 노드가 실시간 하이라이트됩니다.

시나리오 선택 (Select Scenario)
시나리오 A: 단순 정책 조회 (1-Step)
"배송 지연 보상 규정이 어떻게 돼?"
시나리오 B: 복합 쿠폰 발급 (Multi-Step)
"ORD001, ORD002 상태 조회 후 지연 건에 보상 쿠폰 발행"
진행 상황: 대기 중
시작 버튼을 누르면 에이전트의 Thought-Action-Observation 루프가 시작된다.
💻 LangGraph 기반 ReAct 에이전트 생성 실전 코드
from langgraph.prebuilt import create_react_agent from langchain_openai import ChatOpenAI # 1. LLM 모델 객체 및 바인딩할 도구 리스트 정의 model = ChatOpenAI(model="gpt-4o") tools = [get_order_status, search_policy] # 2. ReAct 에이전트 생성 (CompiledStateGraph 객체 반환) agent = create_react_agent(model, tools) # 3. 에이전트 실행 response = agent.invoke({"messages": [("user", "ORD001 주문 상태를 확인하고 지연 시 조치 정책을 조회해줘.")]})
⚠️ 패키지 임포트 주의 (Import Warning) 기존 구형 LangChain의 from langchain.agents import create_react_agent는 전면 Deprecated(비권장) 되었으므로, 반드시 from langgraph.prebuilt import create_react_agent 경로로부터 가져와야 정상적으로 노드/엣지 기반의 견고한 최신 그래프 에이전트가 빌드된다.
04

에이전트 구현 및 설계 패턴 비교

문제 요구사항의 복잡도에 따라 채택할 수 있는 그래프 아키텍처 패턴 분석이다.

// Direct Graph vs ReAct Graph 패턴 시각화
Direct Graph 패턴 (선형 체인) 사전에 배치된 순서대로 일직선 동작 후 즉시 종료
ReAct Graph 패턴 (순환 루프) Thought 결과에 따라 경로를 유기적으로 반복 판단

단순 고정형 파이프라인에는 Direct Graph가 구조적으로 가볍고 예측이 명확하며, 비정형 태스크나 조건부 롤백 처리가 동적으로 필요한 경우에는 ReAct Graph가 견고한 대안이다.

비교 항목Direct Graph 패턴ReAct Graph 패턴
동작 모델선형 체인 (DAG, 순차적인 단방향 흐름)순환 그래프 (Node & Edge 기반 순환)
실행 경로사전에 정해진 순서대로 실행 (A ➡️ B ➡️ 끝)Thought-Action 결과에 따라 경로가 동적으로 결정
복잡한 요청 대응불가 (예상 밖의 시나리오 대응의 한계)가능 (오류 복구 및 조건부 루프 처리 최적화)
구현 복잡도낮음 (구현 및 직관적 예측 용이)높음 (Edge 설계 및 상태 관리 튜닝 필요)
권장 상황단순 서류 추출, 정형화된 ETL 파이프라인고객 상담 챗봇, 문제 해결형 분석 에이전트
05

Trustworthiness (신뢰성 및 가드레일) 아키텍처

실무 상용 에이전트 배포의 최우선 고려 조건인 검증과 다중 필터링 설계이다.

🛡️ 안전하고 신뢰할 수 있는 에이전트 파이프라인 설계

자율성이 부여된 AI 에이전트는 예기치 못한 도구 호출 및 오동작을 일으킬 수 있다. 따라서 보안 정책 강제 검증 및 입출력 단계별 다중 필터 차단 가드레일 설계가 필수적이다.

에이전트 보호 레이어 흐름도

보호 계층주요 역할 및 작동 방식검증 예시

도구 실행 전 검증 도구(API) 실행 직전, 비즈니스 요건 및 정책 준수 여부를 강제 검증함. 발급 금액 정책 한도(최대 2만원) 체크, 주문번호 존재 유무 확인
