💬 LLM Role 정리

System · User · Assistant — 세 가지 역할의 특징 구조와 충돌 발생 시 우선순위 동작 원리

1. 세 가지 Role

LLM API 호출 시 각 메시지는 정해진 역할(Role)을 지정받아 입력 블록으로 전달된다. 개발자는 페르소나 및 입력 구조에 맞게 각 Role을 배치한다.

🏛️ system
System
  • 👤
    작성자: 개발자 / 서비스 설계자
  • ⏱️
    적용 범위: 전체 대화 영역 동안 불변 유지
  • 📌
    핵심 용도: 페르소나 및 어조 설정, 답변 포맷 정의, 금지어 지정
  • 🔒
    안전성: 대화 최상단 고정, 일반적으로 일반 고객 미노출
🙋 user
User
  • 👤
    작성자: 서비스 이용자 / 시스템 파이프라인
  • ⏱️
    적용 범위: 해당 턴에 전송, 멀티턴 입력으로 누적
  • 📌
    핵심 용도: 명령 전달, 질문, 프롬프트 입력 및 컨텍스트 전달
  • 🔄
    반복성: 매 대화 교환 주기마다 생성
🤖 assistant
Assistant
  • 👤
    작성자: LLM 모델 인스턴스 (또는 인위적 Few-shot 가이드)
  • ⏱️
    적용 범위: 모델에 의해 생성, 대화 이력으로 축적
  • 📌
    핵심 용도: 답변 생성, 멀티턴 문맥 보존 및 대화 데이터 저장
  • ⚡
    Few-shot 활용: 가짜 대화 기록을 사전 주입하여 출력 양식 유도

2. 대화 흐름 구조

LLM은 상태를 자체 저장하지 않는 Stateless 방식으로 동작하므로, 대화를 기억하기 위해 이전 대화 기록 전체를 매 턴마다 누적하여 재입력해야 한다.

  • System 프롬프트는 항상 최상단에 고정되며 대화가 진행될수록 입력 윈도우 크기가 증가한다.
  • LLM은 매번 컨텍스트 윈도우 범위 이내의 대화 풀을 일괄적으로 수신해 계산한다.
  • 한계를 넘는 경우 오래된 메시지부터 버리거나(FIFO), 요약본으로 압축하는 기법을 쓴다.
  • 대화가 늘어날수록 입력 토큰 수가 증가해 요청 단가 역시 선형적으로 비례 상승한다.
system
user
assistant
※ 점선 상자는 API 호출 시 한 번에 전달되는 총 입력 묶음이다.
📤 1회차 요청 (API 전달 입력)
system
"너는 친절한 요리 도우미야. 항상 한국어로 답변하고, 레시피는 단계별로 설명해줘."
user · 턴 1
"김치찌개 만드는 법 알려줘"
↓ GENERATED
assistant · 턴 1
"김치찌개 레시피를 알려드릴게요! 재료: 김치 300g, 돼지고기 200g... 1단계: 김치와 고기를 볶습니다."
📤 2회차 요청 (이전 교환 전체 전송)
system
"너는 친절한 요리 도우미야..."
user · 턴 1
"김치찌개 만드는 법..."
assistant · 턴 1
"김치찌개 레시피..."
user · 턴 2 NEW
"고기 없이도 만들 수 있어?"
※ 반투명 박스 = 기존 누적 컨텍스트 / 테두리 강조 박스 = 신규 쿼리 질의문.
↓ GENERATED
assistant · 턴 2 NEW
"고기 없이도 개운하게 끓일 수 있어요! 육수를 내기 위해 멸치나 다시마를 쓰고 참기름에 김치를 충분히 볶아서 요리하세요."

3. 충돌 우선순위

System 프롬프트와 User 메시지 사이에 상반된 지시가 충돌하거나 악의적인 지시가 입력되는 경우, 모델 내부 정렬에 기초한 계층적 가중치 규칙이 적용된다.

우선순위 계층 지침

1
모델 안전 가이드라인 (최우선) 모델 배포사가 정렬 튜닝(RLHF 등)으로 심어둔 핵심 거부 규칙이다. System/User 프롬프트에 상관없이 불법, 탈옥(Jailbreak), 유해 질문 유입 시 거절 응답이 기동된다.
2
System 프롬프트 (2순위) 사용자 질의(User)보다 정책 우선권을 보유한다. 예컨대 System이 "번역 금지"를 수립한 상황에서 User가 "번역해줘"라고 명령해도 System 규칙이 압도하여 요청을 무시한다.
3
User 메시지 (3순위) 최하단 계층이다. 위의 1순위(모델 정책)와 2순위(System 설정 범위)의 울타리 규칙 내에서만 정상적으로 동작하며 응답이 생성된다.
